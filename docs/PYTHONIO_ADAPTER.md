# Python I/O Adapter

The design write-up for `pythonio-adapter`, generated by `dev/new-adapter` and filled in as the adapter is built, following
`docs/ADDING_AN_ENGINE_ADAPTER.md`. It is the adapter's counterpart of `docs/SPARK_ADAPTER.md`. The decision to build it, and
the reasoning behind each choice, is `docs/PYTHON_IO_ADAPTER_DESIGN.md` (with the two surveys before it,
`docs/PYTHON_ADAPTER_SURVEY.md` and `docs/SINK_RECORDS_SURVEY.md`). This document records what was built and what the build
found.

While `modules.json` says this adapter is `in-progress`, `TODO` and `❓` are expected. Setting it to `complete` makes
`.github/scripts/check_modules.py` fail until neither remains, so "done" means this document has no open item.

**Status: milestones 0 to 6 done; the first release waits on PyPI's one-time setup, and Google Cloud Storage, Azure and
a real HDFS cluster on tests.** The checker, `PythonIoCheck`, speaks the whole protocol (`open`, `read`, `write`,
`written`, `finish`, and dry-run mode) over Arrow's own type names, and builds as a native program that gives the same replies
as the JVM. The `invaract` Python package (`python/invaract`) drives it: reads and writes by name, staging and publishing,
the save modes, the settings, and the dry-run migration path. Every conformance scenario runs as a real Python job through
the package and comes out as the declaration promises, and the declaration's enforcement point is `staged-publish`.
`invaract-lint` (`lint/`) flags the reads and writes a job makes around the package. The user guide is written, and
`release-python.yml` builds, tests and (on a `python-v<version>` tag) publishes the wheels; nothing is on PyPI until a
maintainer has done docs/RELEASING.md's one-time setup and pushed the first tag.

## What it is

A Python job reads and writes through the `invaract` package by the names its contract gives (`invaract.read("orders")`,
`invaract.write(df, "report")`). The package does no checking. It starts the checker once per run and describes to it each
read and each write: the dataset's name, the format and save mode, each column's Arrow type, and the empty values each column
holds. The checker answers each request with a verdict, and the package publishes the staged outputs only when the run
finished and every answer was yes.

| File | Does |
|---|---|

| `PythonIoCheck` | the checker: `main` reads requests from standard input and writes one reply each to standard output; `Run` turns each request into what `VerificationPipeline` checks, or, in a dry run, into a draft contract |
| `PythonIoCapabilities` | loads `invaract-capabilities-pythonio.yaml` |

### The protocol

One request per line from the package, one reply per line from the checker, as the recorded cases
(`src/test/resources/protocol`) hold them. A column is `{"name", "type", "nullable", "nulls"}`: `type` is pyarrow's own name
for it (`str(field.type)`: `int64`, `large_string`, `list<item: struct<sku: string, qty: int32>>`,
`dictionary<values=string, indices=int8, ordered=0>`), `nullable` is Arrow's flag, and `nulls` how many empty values the data
holds, where the data has been seen.

| Request | The checker | Reply |
|---|---|---|
| `{"op": "open", "settings": {...}, "job": {...}, "check": false}` | reads the settings (the neutral names, from `INVARACT_*`), resolves the contract, location map and organisational policy, and refuses a contract it cannot check; with `runtimeDataQuality` on, the reply's contract gives each output's data checks (`RuntimeDataQuality.checks`: the field, the constraint type and its properties); with `"check": true`, a check (`invaract.check`): every declared input counts as read, with its declared columns and catalog, and a dry run is not checked | `{"ok": true, "mode": "enforce", "contract": {inputs and outputs, each with its location, format, save mode and fields}}`, or `"mode": "dry-run"` |
| `{"op": "read", "name": "orders", "schema": [...], "csv": {...}}` | refuses a name the contract does not declare (`UNDECLARED_INPUT`: the package has no location for it), and a `location` the job gives that is not the input's (`UNDECLARED_INPUT`); checks the columns against the input's, and the input's `catalog:` requirement against the read's `catalog`; records the read for every later write | `{"ok": true}` |
| `{"op": "write", "name": "report", "format": "parquet", "saveMode": "overwrite", "schema": [...], "partitionBy": ["region"], "partitionOverwriteMode": "static"}` | the pre-check, before anything is staged: location (the contract's, or the `location` the job gives, which must be the output's), format, save mode, catalog registration, the inputs read, the columns and their types; publishes an event only when it refuses; the layout (`partitionBy`, empty for none; `partitionOverwriteMode`, `static` when absent) against the output's partition keys (`OUTPUT_PARTITIONING_MISMATCH`) | `{"ok": true}` |
| `{"op": "write", "name": "report", "unverifiable": "why"}` | a table the package could not describe (no Arrow stream): `UNVERIFIABLE_WRITE` | refused |
| `{"op": "written", "name": "report", "nulls": {"total": 0}, "checks": [...]}` | the final check of a staged write, with the empty values each column turned out to hold: a required column that holds one is refused (decision 3); publishes the write's event; with `runtimeDataQuality` on, `checks` holds what the package found for each of the output's data checks, in the order `open` sent them (`{"failed": 2, "examples": ["-3"]}`), and a check with failing rows is refused (`RUNTIME_DATA_QUALITY_VIOLATION`); a package that reports a different number of checks is not checked | `{"ok": true}` |
| `{"op": "finish", "completed": true}` | refuses a completed run that never wrote a declared output; in a dry run, publishes the job's merged draft | `{"ok": true, "publish": true}` |

A refusal is `{"ok": false, "status": "refused", "violations": [...], "explanation": ...}`. A request the checker cannot check
(a missing contract file, an unknown setting, a malformed request, a `written` with no `write` before it) gets
`{"ok": false, "status": "not-checked", "reason": ...}`, which the package treats as a refusal, so nothing is published
unchecked.

**Why two requests per write.** The columns and their types are known before any data is written, so a write that cannot pass
is refused before the job spends time staging it. Whether a required column holds an empty value is known only once the data
has been written, batch by batch: pandas marks every column nullable (the native Python survey, probe 8), so Arrow's flag
cannot answer it. The pre-check judges every column as if it held no empty values, and publishes only a refusal; the
`written` check is the verdict on the whole write.

**`catalog`.** A read or write of a catalog table also carries the catalog it is registered in:
`"catalog": {"technology": "iceberg", "catalogName": "lake", "namespace": ["sales"], "table": "report"}`, which the package
sends for an Iceberg dataset (its location, `<catalog>.<namespace>.<table>`, names them), and as
`{"technology": "jdbc", "catalogName": <database>, "namespace": [<schema>], "table": <table>}` for a PostgreSQL table. The checker puts it on the plan's
read or write, where the contract's `catalog:` requirement is checked as on every engine (`catalog-*` cases). Files and Delta
tables, named by their path, carry none, so a requirement on them is never met. The catalog service's own address is not sent,
since a catalog URI can hold credentials.

**`location` with a contract in force.** A job migrated from a dry run may still say where it reads and writes
(`location=`). The checker then checks that location like any other, so an argument left behind cannot point a read or a write
somewhere the contract does not declare (`location-given-agrees`, `read-location-disagrees-refused`,
`write-location-disagrees-refused`).

**Dry-run mode** (`INVARACT_DRY_RUN=true`). There is no contract, so `read` and `write` carry the job's own `location` and
`format`. Every write is let through, each staged one gets a draft contract (`CONTRACT_INFERENCE`, with its self-check), and
`finish` merges them into one draft for the job, named after it (`DRY_RUN_SUMMARY`), as Spark's and Beam's dry runs do.

## Milestone 0: the checker as a native program

The design's gating question: can the existing Scala checker run where Python jobs run, with no Java there? The pass criteria
and the result (2026-11-01, GraalVM CE 21.0.2, Linux x86_64):

| Criterion | Result |
|---|---|
| The same verdicts as the JVM, over recorded cases | All 27 recorded cases give identical replies natively and on the JVM (`PythonIoProtocolCasesSpec` in the JVM, `native/cases.py` against the program). One more case is JVM-only (below). |
| Contract parsing, organisational policy, the built-in sinks | All exercised by the cases: a bad contract, a missing contract file, a policy refused and kept, `ref://` locations resolved and unresolved, and the file, HTTP, logging and fan-out sinks |
| Start-up well under a second | A whole run, start-up included, takes 6 to 15 ms natively, against about 0.45 s on the JVM. CI fails a case over 1 s |
| A size that suits a wheel | 41 MB, 14 MB compressed. CI fails above 50 MB compressed |

The build needed very little configuration. GraalVM's tracing agent, run over the cases on the jar, recorded the file sink's
constructor, two `java.sql` classes SnakeYAML looks up, and the capability declaration as a resource. The committed
configuration lists those, the other built-in sinks, and the slf4j provider. The build takes about 75 s and 3 GB of memory.

CI's `pythonio-native-checker` job repeats all of it on every run: `sbt test assembly`, `native-image`, the cases against the
program with the 1 s limit, and the size check. It uploads the program.

**What the native program cannot do** (design section 4): load a class named in configuration that was not built into it. That
covers a team's own notification sink, custom rule verifiers, custom policy evaluators, and a registry client named by
`INVARACT_REGISTRY_CLIENT_CLASS`. The `registry` case is therefore JVM-only: its stub client lives in the tests. A team that
needs its own plug-ins needs a build that includes them, or the Java route.

**With milestone 1** (2026-11-02) the protocol grew to 40 recorded cases: reads, the two-step write, Arrow's type names, empty
values in required columns, unverifiable writes and dry runs. The native program still gives the JVM's replies on all 39 that
it can run, with no change to its configuration (the dry run's YAML writing and its events needed none), at 44 MB and at most
31 ms a run.

## Milestone 1: the protocol

Milestone 1 (design section 12) is the checker's whole side of the protocol, tested with recorded descriptions and no Python:

- **`read`** checks each read as it is made, and the checker keeps the run's reads, so a `write` no longer carries them.
- **The two-step write** (`write`, then `written`) gives the early refusal and the data-based check of required columns
  that design section 5 and decision 3 call for.
- **Arrow's own type names.** The mapping (`ArrowSchemas`) moved from beam-adapter into verification-core, where both
  adapters share it, and gained `dataType` for one type name.
- **`unverifiable`** writes are refused (`UNVERIFIABLE_WRITE`), which made `failClosed.unverifiableWrites` partial: the kit's
  scenario for it now conforms (42 scenarios in all).
- **Dry-run mode** reuses the core's `ContractInference`, `DryRunSelfCheck` and `DryRunSummary`, so
  `reporting.dryRunInference` is supported.

## Type mapping

The package sends each column's type as pyarrow names it (`str(field.type)`), and the checker maps it with `ArrowSchemas`
(verification-core), the mapping the Beam Python adapter uses for a Parquet write's printed schema. The table is the Beam
Python adapter's (docs/BEAM_PYTHON_ADAPTER.md); the strings were recorded from pyarrow 25.0.1.

| Arrow (`str(field.type)`) | Contract type | Notes |

## Milestone 2: the package

Milestone 2 (design section 12) is the `invaract` package, in `python/invaract`, and its tests against the real checker:

- **The API** is the design's: `@invaract.job()` (or `with invaract.run():`), `invaract.read(name, as_=...)`,
  `invaract.write(frame, name)`, and the decorators `@invaract.reads` and `@invaract.writes`.
- **Writing.** Any object with `__arrow_c_stream__` is accepted. A pandas frame goes through `pa.Table.from_pandas` without its
  row index, and a Polars LazyFrame runs batch by batch. Polars and DuckDB releases from before the Arrow stream use their own
  conversion. Each write is described to the checker before anything is staged. It is then written batch by batch to a staging
  folder beside its location, with `not null` on each required column. A required column's first empty value ends the write,
  and the checker refuses it.
- **Publishing.** When the job returns and `finish` says to publish, each staged output is moved into place by a rename, per
  its save mode, with the previous version moved aside until every output is in place. A job that fails, or that catches a
  refusal and carries on, publishes nothing.
- **Reading.** Parquet or CSV, a file or a folder. Only the columns the contract lists are read, and CSV columns are read as the
  contract's types.
- **Settings** are the `INVARACT_*` variables named in `invaract/_settings.py`, forwarded by their neutral names.
  `PythonIoSettingsSpec` holds that list to the checker's. `INVARACT_CHECKER` names the checker program; it is the package's
  own variable, not a setting.
- **Exit status.** An uncaught `ContractViolation` ends the job with 1 (Python's own status for an uncaught exception). An
  uncaught `CheckNotRun` ends it with 2, set from `sys.excepthook` once the traceback is printed.
- **Tests.** 91 pytest tests: every refusal, the save modes, dry runs, the events, every frame library, the exit statuses, and
  the example job with each of probe 14's bugs. They pass against the jar and against the native program, on Python 3.10 to
  3.13, with the oldest supported libraries (pyarrow 15, pandas 2.2, Polars 1.0, DuckDB 1.0) and the newest (pyarrow 26,
  pandas 3.1, Polars 2.1, DuckDB 2.0). CI's `pythonio-python` job runs them against the native program on Python 3.10 with
  the oldest libraries, and on 3.13 with the newest.

## Milestone 3: conformance through real Python jobs

Milestone 3 (design section 12) runs the kit's scenarios as real Python jobs, and gives staging its own enforcement point:

- **`PythonIoPackageConformanceAdapter`** writes each scenario's job as JSON. `python/tests/conformance_job.py` runs it as a
  team's job would run: the contract, the options and the notification sink as `INVARACT_*` variables, and the checker as
  `PythonIoCheck` from the test run's own classpath. The job reads through `invaract.read`, joins, filters, groups and
  projects with pyarrow, and writes through `invaract.write` with the format and save mode it uses itself. The verdict is read
  back from its exit status (0, or 10 for a refusal) and the validation events its file sink wrote.
- **Inputs hold empty values.** The kit describes inputs only by their schemas, and other adapters make them empty. This
  adapter judges a required column by the empty values the data holds (decision 3), so each input gets one row with every
  column set and, for each column it lets be empty, one row where only that column is empty. Values are positive and equal
  row by row across inputs, so filters keep rows and joins match.
- **All 42 scenarios conform** as real jobs, the same as in-process. That held on pyarrow 25 and 26, and on pandas 2.3 and
  3.1. A sabotaged job (one that never writes) fails 20 scenarios, so the run tests the package and does not just pass.
  Without Python (`INVARACT_TEST_PYTHON` without pyarrow) the scenarios are canceled; under `INVARACT_CONFORMANCE_STRICT=true`,
  as CI's `pythonio-native-checker` job runs them, they fail.
- **`staged-publish`** (`EnforcementPoint.StagedPublish`): each write is checked before it is staged, and the outputs are
  published together only if the whole run passed. The user pages now say that for this engine, not `in-engine-blocking`'s
  "writes the job made before it have already happened".

## Milestone 4: the lint

Milestone 4 (design section 7) is `invaract-lint`, the main guard against reads and writes made outside the package (decision
5):

- **What it flags.** It flags a call by the name it resolves to through the file's imports, so an alias (`import pandas as
  pd`, `from pyarrow import parquet as pq`) is no way around it. There are four codes:
  - reads (`IVR001`);
  - writes (`IVR002`): pyarrow's writers, a frame's `to_*` and `write_*` *given a destination* (`df.to_csv()` alone returns
    text), `sink_*`, `open` in a mode that writes or one not spelled out, `Path.write_text`;
  - connections (`IVR003`): database drivers, `sqlalchemy`, cloud storage clients;
  - SQL that reads or writes files (`IVR004`): `COPY`, `ATTACH`, `read_parquet(...)`, a quoted path after `FROM`.
- **What it does not do.** It checks only that such calls are present, as the design asks. It does not follow names reached
  dynamically (`getattr`, `__import__`).
- **Exceptions.** A call is kept with `# invaract: allow` on any of its lines, which shows in review. The conformance job uses
  this for the two lines that make its inputs.
- **Running it.** `invaract-lint [paths]` exits 0, 1 (findings) or 2 (a file it cannot parse). `--format github` prints each
  finding as a pull-request annotation, and the README shows a pre-commit hook. It has no dependencies.
- **Tests.**
  - 71 pytest tests, on Python 3.10 to 3.13. They include the example job before it adopted the package (4 findings, the
    survey's probe 14) and after (none).
  - Mutation testing with `mutmut` (design section 10): 283 of 322 mutants killed (87.9%). The 39 that survive are argparse
    help and description texts, and equivalent mutants. For example, a broken-file count of -1 still exits 2, `"UTF-8"` is
    the same as `"utf-8"`, and the default path label `"<source>"` is only a name.
  - CI's `pythonio-lint` job runs the tests and lints the example and conformance jobs. It also runs `mutmut` with an 80% floor.

## Milestone 5: the user guide and the release

Milestone 5 (design section 10) is the user guide and what a release needs:

- **The guide.** docs-site's "Use Invaract with Python Jobs": installing, adopting the package in a job, a refused run, the
  dry-run migration, the lint, the settings, and formats and save modes. Every example is from a real run of the example
  job (`examples/orders_job`) or of its dry-run form. The configuration reference has a Python column, the troubleshooting
  page lists every `CheckNotRun` message, and the declaration names the guide and drops "in development".
- **The checker each wheel carries.** `_checker.command()` runs `INVARACT_CHECKER` if it is set, else the native checker at
  `invaract/bin/` (platform wheels), else the jar at `invaract/lib/` (the pure-Python wheel) with `JAVA_HOME`'s `java` or
  the one on the `PATH`. With a jar but no Java, or neither, the run stops with `CheckNotRun` naming what to install or set.
- **The wheels.** `.github/scripts/python_wheel.py` builds the package's wheel around one of the two and, for a native
  checker, retags it for the platform the program runs on: the newest `GLIBC_x.y` it names on Linux (`manylinux_x_y`), its
  minimum OS version on macOS (`macosx_<major>_0` from macOS 11 on, the form pip matches). A checker built on a newer
  runner image therefore narrows the tag rather than overstating it. On this environment's x86_64 Linux, a program
  needing glibc 2.34 was tagged `manylinux_2_34_x86_64` (what `objdump -T` reports), and pip installed it with its
  executable bit.
- **The release workflow.** `release-python.yml` builds the jar once, then on each of `ubuntu-latest`, `ubuntu-24.04-arm`,
  `macos-latest` and `macos-15-intel` the native checker, the protocol cases against it, and the wheel; the pure-Python wheel
  with Python 3.10 and Java 11 (the oldest of each supported); and `invaract-lint`. Every wheel is installed in a new
  virtual environment and runs the example job with no `INVARACT_CHECKER`: it must run the checker the wheel carries, publish
  a passing run and refuse a failing one. On a `python-v<version>` tag it publishes to PyPI (trusted publishing, the `pypi`
  environment) and attaches everything to a GitHub release; on a pull request that changes how the packages are built, it
  stops before publishing.
- **What the first run of the workflow showed** (this PR, 2026-11-03). On all four platforms the native checker gave the JVM's
  replies on all 42 recorded cases (`registry` skipped as JVM-only; median 9 to 38 ms a case), weighed 40 to 43 MB, and
  its wheel installed and ran the example job. The Linux wheels were tagged `manylinux_2_34_x86_64` and
  `manylinux_2_34_aarch64`. The macOS wheels were tagged `macosx_26_0_arm64` and `macosx_15_0_x86_64`: the linker records
  the runner's own release as the minimum, which would have kept the native wheel from every Mac older than the runner. The
  workflow now links them for macOS 11, checks each wheel's tag, and installs each native wheel on an older runner image
  (Ubuntu 22.04, macOS 15) before publishing.
- **One version.** The package, the checker and the lint are released under one tag, so `python_wheel.py version` refuses
  a release where they differ, and each `pyproject.toml` reads its package's `__version__` rather than stating it again.

## Milestone 6: tables and object storage

Milestone 6 (design section 12) is object storage, and Delta Lake and Iceberg outputs. Object storage has no rename, so the
design left it for a design of its own (section 5). Probes first (2026-11-03, deltalake 1.6.6, pyiceberg 0.12.0, pyarrow
26.0.1, moto 5.2.5 for S3):

- **delta-rs can commit later.** Parquet files written into a table's folder are invisible until a commit names them, and
  `create_table_with_add_actions` / `DeltaTable.create_write_transaction` commit given files in one transaction, append or
  overwrite. A table created this way keeps a required column not-null and refuses an empty value in it. The same on S3.
- **pyiceberg commits a transaction.** Writes inside an open transaction are invisible until it is committed; an abandoned
  one leaves the table as it was; `create_table_transaction` creates a table and its data in one commit. A catalog is
  configured by environment (`PYICEBERG_CATALOG__<NAME>__*`). The same with the warehouse on S3.
- **Reads need no settings of Invaract's own**: pyarrow and delta-rs take S3 from the standard `AWS_*` variables.

Two decisions followed, both the user's (2026-11-03): a Delta or Iceberg output that does not exist is created by the run
that passes, in the same commit; and a Parquet or CSV *output* on object storage was at first refused (readers could see a
copy-then-delete half done), then, the same day, allowed Spark-style, since writing Parquet to GCS or S3 is what teams
expect: staged on local disk, and at publish the old `_SUCCESS` removed, the files uploaded, the old ones deleted
(overwrite), `_SUCCESS` written last. HDFS, which has an atomic rename, stages and renames as a local disk does.

**Partitioned outputs (2026-11-04).** Three decisions, the user's: a contract declares partition keys with the Open Data
Contract Standard's own `partitioned`/`partitionKeyPosition` field keys (which Invaract had parsed past until then), and a job
may also say them (`invaract.write(..., partition_by=, partition_overwrite=)`), the checker holding the write's layout to the
contract's; what an `overwrite` replaces is the contract's choice, per output (`partitionOverwriteMode`, `static` by default, as
Spark's). The layout travels to the check as `CheckedWrite.partitioning`, not on `ir.Write`: it changes how the data is laid
out, not what the job computes, so the plan, its lineage and its fingerprint stay as they were. A new engine-neutral capability,
`check.partitioning`, says who checks it; Spark and Beam declare it unsupported for now (their writes do carry partition
columns, which the adapters do not hand over yet). Publishing a `dynamic` overwrite: plain files rename each written partition
folder into place (atomic per partition, not per output; a failure puts back the folders already replaced), object storage
deletes only the written partitions' old files, Delta commits the new files and `RemoveAction`s for the replaced partitions'
old ones in one commit (deltalake releases without `RemoveAction`, 1.0 to 1.6.0 among them, refuse it), Iceberg uses
`dynamic_partition_overwrite` (pyiceberg 0.9 has it). A Delta or Iceberg table that exists partitioned otherwise than the write
is not written.

**PostgreSQL tables (2026-11-04).** The user chose ADBC (`adbc-driver-postgresql`) over psycopg or SQLAlchemy: it speaks
Arrow, so a write's batches go to the server by `COPY` without a conversion, and a read comes back as an Arrow table. A table's
location is `postgresql://[user@]host[:port]/<database>/<schema>.<table>` (a password in it is refused: credentials come from
libpq's own `PG*` variables and `~/.pgpass`); its format is `jdbc`, the name Spark and Beam give a JDBC dataset, and the read or
write carries `"catalog": {"technology": "jdbc", "catalogName": <database>, "namespace": [<schema>], "table": <table>}`, as
Spark's `JDBCTableCatalog` registers one. Staging: each output opens its own connection and transaction for the run and copies
each write into a session-temporary table (`adbc_ingest(..., temporary=True)`), which no other session sees and the server drops
with the session. Publishing, in that transaction: create the table if missing (`LIKE` the staging table, then `SET NOT NULL`
on required columns), `TRUNCATE` it for an overwrite, `INSERT ... SELECT` the staged rows, drop the staging table, commit; a
refused or failed run rolls back. An existing table is never replaced, so its other columns, defaults, indexes and grants stay.
A PostgreSQL output is not written partitioned (declared partitioning on a database table is the table's own DDL, which the run
does not create). adbc 1.0 and 1.1 are not supported: their bulk ingest fails against PostgreSQL 16 ("COPY file signature not
recognized"); 1.2 to 1.4 refuse to close a connection with a cursor still open, which the publish avoids. Tested in CI against a
PostgreSQL 16 service on adbc 1.2.0 and the newest (`test_postgres.py`, skipped only when `INVARACT_TEST_POSTGRES` is unset), and
by the protocol case `postgres-table-registered`.

**pandas frames (2026-11-05).** The user's main audience is pandas. Probing everyday pandas writes against real runs found 10
of 18 refused or failing, and a frame read through `invaract.read` and written back unchanged refused (`long` with a missing
value reads as `float64`). pandas cannot hold several contract types (integers with missing values, dates, decimals of a given
precision, an empty column's type), so the package now writes a pandas frame's declared columns as the declared type when no
value changes (`_pandas.conform`): Arrow's checked conversion (a decimal's precision, an integer's range), then a conversion
back that must give every value as it was (a float as a decimal goes back by way of its text, since Arrow's own conversion is
not exact). Only within one kind of value (numbers, text, times), never adding or dropping a time zone; Polars, DuckDB and
Arrow frames are untouched, since they can hold the declared types and a mismatch there is the job's. A column left as it was
gets a note in pandas' terms, added to the refusal's explanation (`ContractViolation.add_notes`); a named index level the
contract declares is written as a column (a `groupby` result); an `object` column of mixed values raises a `TypeError` naming
it; `invaract.read(..., dtype_backend=)` takes pandas' own `numpy_nullable`/`pyarrow`. Nothing changes for the checker or the
protocol: it is told the converted schema, and judges it as before. Found on the way, and left as documented: a bare
top-level `type: int` is not `integer` (docs-site's contract format says so), for every engine.

**pandas, second pass (2026-11-06).** The user asked for every remaining pandas gap, and chose: a dry run writes named index
levels as pandas' `to_parquet` does (it dropped them, so a migrated `groupby` job lost its keys and the draft never declared
them); enforced runs still write only the levels the contract declares. Also: in a dry run a pandas column of `Decimal` values
is written at precision 38 and the scale its values have, so drafts stop declaring the narrowest precision one run needed;
`invaract.check(frame, name)` judges a frame as a write would and writes nothing (its own checker, opened with `"check":
true`, under which every declared input counts as read with its declared columns and catalog, so the frame is judged alone,
and with no `dryRun` or `notifyConfig`, so it publishes nothing); `invaract.read(..., chunksize=)` reads any input a batch at a
time (files and Delta through pyarrow datasets, Iceberg through `to_arrow_batch_reader`, PostgreSQL through ADBC's
`fetch_record_batch`), counting empty values in a first pass because the `read` request carries them before any data is
handed over; nested declared types (`array`, `map`, `struct`) are conversion targets too (a list of whole numbers held as
floats beside a missing one), sparse columns are written dense; duplicate names and `MultiIndex` columns raise a `TypeError`;
notes for required columns with missing values, `period` and `timedelta`. A `timedelta` stays unconverted: Arrow's
`duration` is not the contract's `interval` (a calendar interval; `ArrowSchemas` keeps them apart on purpose, as Spark's own
mapping does), and Parquet cannot hold Arrow's calendar intervals.

**CSV options (2026-11-06).** The user chose to put a CSV dataset's layout in the contract, engine-neutral, rather than in
the package alone: a dataset's `csv:` block, under Spark's own option names (`delimiter`/`sep`, `header`, `encoding`,
`quote`, `escape`, `nullValue`, `dateFormat`, `timestampFormat`), and a new capability, `check.csvOptions`, every adapter
declares. The package reads and writes with the declared options (`_csv`), a job's `csv=` in their place where it gives
any, and reports what it used: `read` and `write` carry `"csv": {...}`, which the checker compares with the declared options
(`CsvOptionsChecker`, both sides known, by meaning: `\t` is a tab, `latin1` is `ISO-8859-1`), reads at once and writes in the
shared evaluation (`CheckedWrite.formatOptions`, by location), and which a dry run's draft declares. Reading uses pyarrow's
CSV options, with dates and timestamps in a declared pattern read as text and parsed with `strptime` (Java patterns are
translated; fractions of a second and week numbers are refused); writing, when any option is declared, goes through Python's
`csv` module over Arrow's text for each value (pyarrow's writer cannot set a quote, an escape, an encoding or a null marker),
and with none declared stays pyarrow's. Spark and Beam declare the capability unsupported for now: Spark's CSV relations
carry the options, which the adapter does not hand over yet.

What was built:

- `_storage`: a location is local, or object storage by its URI scheme (`s3`, `s3a`, `gs`, `gcs`, `az`, `abfs`, `abfss`).
  Reads of Parquet and CSV go through pyarrow's own file systems, HDFS included.
- `_files`: plain-file outputs. `LocalFileOutput` is milestone 2's, unchanged; `HadoopFileOutput` does the same on HDFS
  through pyarrow's file system (staged beside the location, `move` into place); `ObjectStorageFileOutput` stages on local
  disk and copies at publish, `_SUCCESS` last. Any other URI scheme is refused.
- `_tables.DeltaOutput`: each write is a Parquet file staged uncommitted, in the table's folder when it is local, on local
  disk when it is on object storage (uploaded at publish); publishing commits them all in one transaction, creating the
  table if needed. `ignore` and `error` look at whether the table holds files.
- `_tables.IcebergOutput`: each write is held until publishing, which writes and commits it in one transaction (creating
  the namespace and table if needed), since pyiceberg writes a table in one piece. `error` and `ignore` look at the current
  snapshot's record count.
- Extras `invaract[delta]` (deltalake 1.0 or later) and `invaract[iceberg]` (pyiceberg 0.9 or later, which needs pyarrow
  17); without them, a table format stops the run with `CheckNotRun` naming the extra.
- Tests: `test_tables.py`, 60 tests, local, on S3 (moto in-process) and on HDFS through a local pyarrow file system
  standing in for it, including a real job writing to S3 that must exit. They pass on the oldest releases the extras allow
  (deltalake 1.0.0, pyiceberg 0.9.0, pyarrow 17.0.0, Python 3.10) and the newest; CI runs both, strictly.

## Friction log

- `dev/new-adapter` takes an engine name without a hyphen, so the design's `python-io-adapter` and engine `python-io` became
  `pythonio-adapter` and `pythonio`; the design now says so.
- The generated declaration marks every capability unsupported, which makes the checker refuse every contract with an output
  schema (`UNSUPPORTED_CONTRACT_FEATURE`). The declaration had to be written before the checker could be tried on a real
  contract.
- The kit's scenario `an-undeclared-second-write-is-blocked` expected a `MISSING_INPUT` that only per-write read attribution
  shows, which this adapter cannot have (D4 of the native Python survey). It was settled with a kit change, as D4 recommends:
  `Scenarios.partialExcuses` names, per scenario, the violations an adapter declaring a capability `partial` is excused from
  (here `MISSING_INPUT`, for `check.inputExistence`).
- The user pages' sentence for `in-engine-blocking` says a job's earlier writes have already happened; with staging they have
  not. Milestone 3 added the `staged-publish` enforcement point to `verification-core` (`EnforcementPoint.StagedPublish`, with
  its own wording in the kit's `CapabilityGuide`), and the declaration uses it. The engine stays labelled "in development"
  until the first release.
- Stryker4s leaves instrumented classes in `target/`; running the checker from that classpath afterwards fails with
  `NoClassDefFoundError: stryker4s/package$`. `sbt clean` first.
- A `/simplify` pass (2026-11-02) moved what the adapter had copied or worked around into verification-core: one way to
  refuse (`VerificationPipeline.reject`), a write's verdict without publishing it (`evaluateWrite`, so the pre-check no longer
  runs the pipeline twice), dry-run reporting shared with Beam (`DryRunReporting`, which also guards the final flush), loading
  a capability declaration (`AdapterCapabilities.load`, used by every adapter and the scaffold) and the settings' snake-case
  spelling (`ConfigSource.snakeCase`, shared with the Beam Python adapter).
- Milestone 0's protocol carried each write's reads and judged a required column by the frame's nullable flag. Both had to
  change once the conformance adapter played the package faithfully: the package learns the reads one at a time, and pandas
  sets the flag on every column. Milestone 1's `read` and `written` requests are the result; the recorded cases were
  regenerated for them.
- Milestone 2's package needed two things from the checker that milestone 1 had not given it: the inputs' declared columns in
  `open`'s reply (to read only those, and CSV with the contract's types), and a check of `location=` with a contract in force
  (the design's guard against an argument left behind after a migration). Both are checker changes with recorded cases.
- pandas' `__arrow_c_stream__` carries the row index as a column (`__index_level_0__`) once a filter has made it anything
  but 0, 1, 2, ...; the example job's audit was written with it. The package converts a pandas frame without its index.
- pyarrow 14 has no `RecordBatchReader.from_stream`, so the package needs pyarrow 15. Polars 1.0 and DuckDB 1.0 have no
  Arrow stream; the package falls back to their own `to_arrow()` and `arrow()`.
- A contract has no CSV delimiter field, so CSV is read and written with a comma (design section 5 said "the contract's
  delimiter").
- The design named Python 3.9 as the oldest supported release. CI's runners no longer offer it (it reached its end of life
  in October 2025), so the package requires 3.10, the oldest CI can test.
- The design placed the lint at `python/invaract_lint/`, beside the package. A second package needs its own `pyproject.toml`
  and root, so it is `lint/` instead.
- Run over the package's own code, the lint finds exactly the package's three pyarrow reads and writes (`_frames.read_table`,
  `_run._writer`). That is a check that it catches real I/O; the package is not a job, so it is not marked.
- Both conformance specs record their results as `target/conformance/<adapter>.json`, and both are the adapter `pythonio`, so
  the second overwrote the first. The package spec now writes to `target/conformance/package/`.
- Re-recording every case with `cases.py --record` overwrote the JVM-only `registry` case with a failure (its stub registry
  client is on the test classpath only). `--record` now skips JVM-only cases, whose replies are written by hand.
- The registry client's "not found" message says to add a jar "via spark-submit --jars", which is Spark's wording, in
  verification-core; a Python job sees it too. Left for a wording pass across adapters.
- The package's help text for `computeFingerprint` said a run with it is refused. Writing the guide's settings table from
  real runs showed it is not: like Beam, the run goes on and the checker logs that no fingerprint is published. Static data
  quality and role consistency are refused when the run opens (`UNSUPPORTED_CONTRACT_FEATURE`). The help text now says so.
- A dry run's draft lists, as each output's `derivedFrom`, every input read before it was written (D4): the example job's
  audit is drawn from the orders only, but the draft says the customers too, because they were read first. The guide tells
  the reader to correct it when reviewing the draft.
- The version was written in four places (each package's `pyproject.toml` and `__init__.py`). Each `pyproject.toml` now
  reads its package's `__init__.py`.
- deltalake 1.6's `DeltaTable.to_pyarrow_table()`, used on S3, leaves the process unable to exit (it hung until killed);
  `to_pyarrow_dataset().to_table()` does not. The package reads the second way, and a test runs a real job against S3 with
  a timeout.
- pyarrow's S3 file system recreates an empty "folder" object when it deletes the last file under a prefix, and
  `delete_dir` recreates the parent's; deleting a refused run's staged files left `report/` behind. A Delta output on object
  storage therefore stages on local disk and uploads only at publish, so a refused run never writes to the bucket.
- pyiceberg refuses a frame whose columns are nullable when the table's are required, even with no empty values; the
  package marks required columns not-null before writing, as it does for files.
- pyiceberg reads its `PYICEBERG_` variables once, when imported. A job's are set before it starts; the tests reload them.
- Milestone 2's plain-file output used `os` paths, so an `hdfs://` location made a local folder named `hdfs:` before pyarrow
  reached for HDFS, and publishing renamed local paths: HDFS outputs had never worked, and any other URI scheme was
  treated as a local path. Found when the user asked for Parquet on HDFS; `_files` now dispatches on the scheme and
  refuses one it does not know.
- After an overwrite, a Delta table keeps the replaced files for time travel until it is vacuumed; "nothing left behind"
  means no file that no commit ever named.

## Unverified items

- Google Cloud Storage and Azure: `gs://` and `abfss://` locations go through pyarrow, delta-rs and pyiceberg as S3 does,
  but no emulator runs them in CI yet (open in ROADMAP.md).
- A real HDFS cluster: the HDFS output is tested through pyarrow's file-system interface with a local file system standing
  in; pyarrow's own Hadoop file system (libhdfs) is not run in CI.
- Concurrent writers to one Delta table on real S3: delta-rs 1.x commits with S3's conditional writes, which moto accepted;
  not checked against AWS itself, nor two runs racing.
- The native program on a Mac older than macOS 15, and on Linux with glibc 2.34 exactly (RHEL 9): the oldest runner images
  CI offers are macOS 15 (GitHub retired macOS 14's on 2026-11-02; it ran there until then) and Ubuntu 22.04 (glibc 2.35).
  An Intel Mac older than macOS 15 likewise: macOS 15 is the only Intel runner image.
- The HTTPS path of the HTTP sink natively: the cases use plain HTTP to a local receiver (`--enable-url-protocols=http,https`
  is set for it).
