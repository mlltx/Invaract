# Beam Adapter

The design write-up for `beam-adapter`, generated by `dev/new-adapter` and filled in as the adapter was built, following
`docs/ADDING_AN_ENGINE_ADAPTER.md`. It is the adapter's counterpart of `docs/SPARK_ADAPTER.md`. The decision to build it, and the
reasoning behind each design choice (D1 to D9), is `docs/BEAM_ADAPTER_SURVEY.md`; this document records what was built and what
the build found. Where the two differ, this one is right, and the difference is in the friction log.

**Status: in progress.** The adapter checks a Beam pipeline against a contract before it is submitted and is held to the
conformance kit (38 of the 51 scenarios conform, the other 13 are skipped by its own declaration), but streaming and BigQueryIO are
not investigated (the operation surface below has them as open items), so `modules.json` keeps it `in-progress`.

## What it is

`InvaractRunner` is a Beam runner that executes nothing itself. A job names it (`--runner=com.invaract.beamadapter.InvaractRunner`);
Beam builds it through `fromOptions` and, when the job calls `run`, hands it the finished pipeline. It walks the pipeline's graph
(`Pipeline.traverseTopologically`), translates the reads and writes it recognises into an `ir.Plan`, hands each write to
`VerificationPipeline.verifyWrite`, and only then passes the pipeline to the real runner (`--invaractDelegate`, default
`DirectRunner`). A pipeline that breaks the contract is never submitted. The settings are Beam options (`--invaractContract`,
`--invaractDryRun`, `--invaractNotifyConfig`, `--invaractRegistryUrl`, `--invaractLocationMap`, `--invaractOrgPolicy`,
`--invaractRejectUndeclaredInputs`, ...), found by Beam through a `PipelineOptionsRegistrar` listed in `META-INF/services`, so a
job needs no code that knows about them. A job that picks its own runner in code, or never reads its command line, is not reached
that way; `InvaractBeam.verify(pipeline)` is the one line that covers it.

| File | Does |
|---|---|
| `BeamGraph` | the pipeline graph: steps, their input and output collections, display data, coders |
| `BeamTranslator` | graph to `ir.Plan`: recognised reads and writes, every other step an `UnknownPlan` that keeps what feeds it |
| `BeamSchemas` | Beam row schemas and Avro schemas to `LogicalSchema` |
| `BeamCheck` | the enforcement: translate, hand each write to `VerificationPipeline`, or infer a draft in dry-run mode |
| `InvaractBeam`, `InvaractRunner`, `InvaractBeamOptions` | the entry points and the attach surface |

## Engine investigation

One row per question, answered with evidence (a probe or test, or the engine's own source), never from memory. What could not be
checked is marked **unverified** and repeated under "Unverified items".

| # | Question | Finding | Evidence |
|---|---|---|---|
| 1 | Where can this engine be gated: inside it (blocking), before submission, or only observed? | Before submission. A wrapper runner receives the constructed pipeline in `run`, before any step executes, and can throw. Nothing inside a running pipeline can be intercepted. Declared `pre-submit-gate`. | `BeamAttachSpec` "zero-code install" (a blocked job writes nothing); survey section 3, "The hook" |
| 2 | What is knowable at that point: reads, writes, schema, plan, parameters? | Reads: the file pattern, from the read step's display data. Writes: the destination and the sink, but `FileIO.write` publishes neither (see friction log 1), so they are read from non-public members of `FileIO.Write` by reflection, confined to one method. Columns: from the collection's Avro coder or Beam row schema. Not knowable: the fields a filter, join or grouping uses (non-public), what a function does, the schema of the files on disk. | `BeamTranslatorSpec`; survey section 3; `BeamTranslator.fileIoWrite` |
| 3 | How could a platform attach this to a job it does not own? | `--runner=` plus `--invaract...` options registered through `PipelineOptionsRegistrar`. Works on an unmodified job. Does not reach a job that sets its runner in code or ignores its command line. | `BeamAttachSpec` (all of it); `config.zeroCodeInstall` is `partial` |
| 4 | How are datasets named, and how do they convert to the canonical `/`-separated location? | File paths. A read is located by the folder of its pattern (`in/orders/` plus a glob file name is `in/orders`); a `FileIO` write by its output directory; a `TextIO`/`AvroIO` prefix write by the prefix the job passed to `.to()`. Backslashes become `/`. The shared rule (a relative declared location matches any location ending in it) does the rest. | `BeamTranslatorSpec` "the folder a read pattern reads from"; `LocationMatching` |
| 5 | Which formats and catalog technologies does it have, and what are their canonical names? | `parquet`, `avro`, `text` (all canonical). A text writer publishes no delimiter, so a text write is `text`, and satisfies a declared `csv` or `json` too (D5). No catalog for file writes. | `BeamCheckSpec` "a text write satisfies..."; `Formats` |
| 6 | What are its write dispositions, and their defaults? | None for file writes: Beam's file sinks have no append/overwrite choice, so a job cannot state one. `check.saveMode` is unsupported. (BigQueryIO has dispositions; not investigated here.) | survey section 3, "BigQueryIO steps"; scenarios `output-save-mode-*` conform by refusing |
| 7 | How do its types map to `LogicalType`? | See "Type mapping". | `BeamSchemasSpec` |
| 8 | What does nullability mean? | Avro: a union with `null` is nullable, anything else is not. Beam rows: `FieldType.getNullable`. Both are the declared schema the job gives, not the files' real contents. | `BeamSchemasSpec`; scenario `output-nullability-mismatch` |
| 9 | What are its function names, especially the non-deterministic ones? | A Beam job calls Java methods, not named engine functions, so there is no catalog to map. `analysis.functionCatalog` and `analysis.fingerprint` are unsupported. | survey section 7.1 |
| 10 | What changes data without being a plain write? | Any function that calls out of the pipeline (an HTTP call, a JDBC insert) and any non-file IO. The fail-closed representative is a step that ends the pipeline without being a recognised write; a side effect in the middle of a pipeline is invisible to every pre-run check. | scenario `untranslatable-write-fails-closed`; `BeamCheckSpec` |
| 11 | Does it stream? Does it have a checkpoint or cache? | It streams (`PCollection.isBounded`), but no streaming scenario is run (open item). It has no checkpoint or cache that erases history, so `lineage.boundaryResolution` is not applicable. | survey section 3; "Operation surface" |
| 12 | What runs in CI with no secrets? | Beam's in-process `DirectRunner` over local Parquet files, the same level of evidence Spark has with `local[*]`. BigQueryIO graphs can be constructed offline, but nothing about a real BigQuery write is proven. | `BeamConformanceSpec` |

## Operation surface

Every shape of read, write and state change the engine has: ✅ covered (a permanent test), 🚫 fails closed (a test proving the
rejection), or ❓ not investigated. A ❓ is an open item, not a finished one.

| Operation | Disposition | Test |
|---|---|---|
| Bounded read, `ParquetIO.read` | ✅ | every conformance scenario; `BeamTranslatorSpec` |
| Bounded read, `TextIO.read` | ✅ | `BeamTranslatorSpec` "Parquet, text and Avro reads..." |
| Bounded read, `AvroIO.readGenericRecords` | ✅ | `BeamTranslatorSpec` |
| A team's composite around a read | ✅ | `BeamTranslatorSpec` "a team's composite around a read..." |
| `FileIO.write` through `ParquetIO.sink` | ✅ | every conformance scenario that writes |
| `FileIO.write` through `TextIO.sink` (the CSV shape) | ✅ | scenario `output-format-mismatch`; `BeamCheckSpec` text-family tests |
| `FileIO.write` through `AvroIO.sink` | ✅ | `BeamTranslatorSpec` |
| `FileIO.write` with a separate temporary directory | ✅ | `BeamTranslatorSpec` |
| `FileIO.write` through a sink it cannot name | ✅ (written where it lands, no format) | `BeamTranslatorSpec` |
| `TextIO.write`, `AvroIO.write` (prefix writes) | ✅ located by the prefix; 🚫 a text write of strings has no columns, so it is refused | `BeamTranslatorSpec`, `BeamCheckSpec` "a write whose data exposes no schema..." |
| Other file writes (`TFRecordIO`, `XmlIO`, ...) | 🚫 refused as unverifiable | `BeamTranslatorSpec` "a file write through a sink this adapter does not recognise..." |
| A step that ends the pipeline without a recognised write (any other IO, a `DoFn` with a side effect) | 🚫 | scenario `untranslatable-write-fails-closed`; `BeamCheckSpec` |
| A side effect in the middle of a pipeline | declared limit: no pre-run check can see it | survey section 9 |
| Several writes in one pipeline | ✅ each is checked | `BeamTranslatorSpec` |
| Join, grouping, filter, opaque function | ✅ kept as unknown steps that carry the reads beneath them (the fields they use are not public, so shape rules are refused) | scenarios `unrecognized-step-*`, `required-*`, `forbid-cross-join-*` |
| Row-level MERGE, UPDATE, DELETE; schema-change commands | n/a, Beam has none | declaration |
| Streaming file reads and writes (`FileIO.match().continuously`, `watchForNewFiles`) | ❓ | not investigated: needs a read shape the translator does not yet recognise and a streaming scenario that finishes in-process |
| `BigQueryIO` read and write | ❓ | not investigated: graphs build offline (survey probe), no adapter test; as a pipeline ending it is refused today |
| `KafkaIO`, `JdbcIO`, `Read.from(source)` | ❓ reads are not recognised as inputs; writes are refused by the rule above | not investigated |

## Friction log

Every undocumented decision, surprise, or guess made while building this adapter, as it happened. It is the input to improving
`docs/ADDING_AN_ENGINE_ADAPTER.md` and the add-an-adapter skill.

1. **The survey assumed Parquet has a write transform of its own; it does not.** `ParquetIO.read` is a transform whose display data states
   its file pattern, but a Parquet write is `FileIO.write().via(ParquetIO.sink(...))`, and `FileIO.write` publishes neither its destination
   nor its sink (its display data names only `FileIO$Write$ViaFileBasedSink`). The survey's "read it through `WriteFiles.getSink()`"
   gave the temporary directory, which is the destination only by default. The fix was reflection on `FileIO.Write`'s non-public
   `getOutputDirectory()` and `getSinkFn()`, confined to one method and failing closed. *For the guide:* question 2 should say to check the
   write's own display data, not infer it from the read's.
2. **The kit demanded analysis results from an adapter that had refused the scenario.** An adapter that declares
   `analysis.staticDataQuality` or `analysis.roleConsistency` unsupported must refuse those scenarios, but the kit still compared the
   verdicts they expect against what the adapter reported, so none could conform. Beam was the first adapter to hit it. Fixed in the
   kit (PR #147), with a test.
3. **Which test shows a capability is not obvious when the capability is a mode.** `reporting.dryRunInference` and
   `config.zeroCodeInstall` needed a real job run from `main` with command-line flags; a helper (`ExampleJob`) that knows nothing about
   Invaract was the answer, and it is also where the bypass is recorded as a test.
4. **A Scala companion `fromOptions` is found by Beam as the runner's static method, and a Scala trait with abstract getters and setters
   is accepted as a Beam options interface.** Both were unverified in the survey; both work (`BeamAttachSpec`).
5. **A glob in a comment starts a nested comment in Scala** (`/*` inside a doc comment). `in/orders/*.parquet` in a scaladoc broke the
   build with "unclosed comment".
6. **`TransformHierarchy.Node` is an inner class in Scala's eyes** (`TransformHierarchy#Node`), and `Filter.by` is ambiguous between
   `SerializableFunction` and `ProcessFunction` unless the argument is typed.
7. **Reading a class's static field initialises it.** The test that a configured class name is not initialised before it is checked
   had to record the initialisation in a system property, because inspecting a field would itself run the initialiser.
8. **Beam leaves a `.temp-beam` folder beside a `FileIO` write's files**; a test that lists the output directory must filter.
9. **Maven Central answered HTTP 429 from the development sandbox**; local resolution used Google's public mirror through an untracked
   `local-mirror.sbt`. CI is unaffected.
10. **Hadoop's file system needs native libraries on Windows**, which the CI matrix runs. The scenario inputs are therefore written with
    Parquet's own `LocalOutputFile`, and Beam's `ParquetIO` reads and writes through its own channels, so no Hadoop file system is touched.
11. **A location for a prefix write is a choice.** `TextIO.write().to("out/text")` writes `out/text-00000-of-00001`; the adapter reports the
    prefix as given (a contract declares `out/text`), not the folder.
12. **The mutation-testing CI job is not generated.** `check_modules.py` says the job is missing but not what it should say; it was
    copied from `mutation-testing-adapter-testkit`. *For the guide:* a template for it would remove a copy-and-edit step.
13. **`dev/new-adapter` numbers the write-up's contributor-docs order as the highest existing order plus one**, so a document added by
    hand to the same section takes the slot the next adapter expects and fails `test_new_adapter`. The survey now shares the guide's slot.
14. **The generator's own tests assumed one adapter.** `test_new_adapter` expected a new adapter to follow `spark-adapter` and the next
    contributor-docs order to be 9; with Beam registered both stopped being true. They now compute "the last published module" and "one past the
    last design doc" from the registry they are given.
15. **The survey's forecast was right about the count** (21 by checking, 17 by refusing safely, 13 skipped: all as forecast), and wrong
    in one design detail (item 1). The retrospective is in `docs/BEAM_ADAPTER_SURVEY.md`.

## Unverified items

What could not be checked against the engine, to be settled by the adapter's own tests.

- **Beam releases other than 2.77.0.** The adapter is built and tested against 2.77.0 only. The reflection in `BeamTranslator.fileIoWrite`
  depends on non-public members, and fails closed (the write is refused as unverifiable) if they change; a version matrix in CI, like
  Spark's, is the way to learn when.
- **Streaming.** No unbounded job has been run under the kit; `read.streaming` and `write.streaming` stay unsupported.
- **Production runners.** The wrapper hands over to `DirectRunner` in every test. Handing over to Dataflow or Flink with their own required
  options has not been tried.
- **A short runner name through `PipelineRunnerRegistrar`** (`--runner=Invaract`): not tried; the full class name works.
- **The portable pipeline form** (`PipelineTranslation.toProto`) as a way to read join and grouping fields: not probed, so the transformation-shape rules stay unsupported.
- **Windows and macOS.** The suite was run on Linux; the CI matrix covers the others.
