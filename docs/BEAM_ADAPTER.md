# Beam Adapter

The design write-up for `beam-adapter`, generated by `dev/new-adapter` and filled in as the adapter was built, following
`docs/ADDING_AN_ENGINE_ADAPTER.md`. It is the adapter's counterpart of `docs/SPARK_ADAPTER.md`. The decision to build it, and the
reasoning behind each design choice (D1 to D9), is `docs/BEAM_ADAPTER_SURVEY.md`; this document records what was built and what
the build found. Where the two differ, this one is right, and the difference is in the friction log.

**Status: complete.** The adapter checks a Beam pipeline against a contract before it is submitted and is held to the conformance
kit: 40 of the 51 scenarios conform (the streaming ones run to completion in-process, the save-mode and catalog ones write Beam's
in-memory BigQuery), and the other 11 are skipped by its own declaration (6 not applicable to Beam, 5 analyses declared unsupported).
Every shape in the operation surface below has a disposition backed by a test, it is tested on Beam 2.60 to 2.77 in CI, and it
hands over to a production runner (Flink). What remains is recorded as declared limits and as decisions for a reviewer
("Design decisions"), not as open items.

## What it is

`InvaractRunner` is a Beam runner that executes nothing itself. A job names it (`--runner=Invaract`, the name it registers with
Beam, or its full class name);
Beam builds it through `fromOptions` and, when the job calls `run`, hands it the finished pipeline. It walks the pipeline's graph
(`Pipeline.traverseTopologically`), translates the reads and writes it recognises into an `ir.Plan`, hands each write to
`VerificationPipeline.verifyWrite`, and only then passes the pipeline to the real runner (`--invaractDelegate`, default
`DirectRunner`). A pipeline that breaks the contract is never submitted. The settings are Beam options (`--invaractContract`,
`--invaractDryRun`, `--invaractNotifyConfig`, `--invaractRegistryUrl`, `--invaractLocationMap`, `--invaractOrgPolicy`,
`--invaractRejectUndeclaredInputs`, ...), found by Beam through a `PipelineOptionsRegistrar` listed in `META-INF/services`, so a
job needs no code that knows about them. A job that picks its own runner in code, or never reads its command line, is not reached
that way; `InvaractBeam.verify(pipeline)` is the one line that covers it.

| File | Does |
|---|---|
| `BeamGraph` | the pipeline graph: steps, their input and output collections, display data, coders |
| `BeamIO` | the one catalogue of recognised IO steps: Beam's class names, display-data keys and the two reflective reads, and how each IO's name for its data becomes a location (`BeamLocations`) |
| `BeamTranslator` | graph to `ir.Plan`: recognised reads and writes, every other step an `UnknownPlan` that keeps what feeds it, a read that states no location an `UnlocatedRead` |
| `BeamSchemas` | Beam row schemas, Avro schemas and BigQuery table schemas to `LogicalSchema` |
| `BeamCheck` | the enforcement: translate, hand each write to `VerificationPipeline`, or infer a draft in dry-run mode |
| `InvaractBeam`, `InvaractRunner`, `InvaractBeamOptions` | the entry points and the attach surface |

## Engine investigation

One row per question, answered with evidence (a probe or test, or the engine's own source), never from memory. What could not be
checked is marked **unverified** and repeated under "Unverified items".

| # | Question | Finding | Evidence |
|---|---|---|---|
| 1 | Where can this engine be gated: inside it (blocking), before submission, or only observed? | Before submission. A wrapper runner receives the constructed pipeline in `run`, before any step executes, and can throw. Nothing inside a running pipeline can be intercepted. Declared `pre-submit-gate`. | `BeamAttachSpec` "zero-code install" (a blocked job writes nothing); survey section 3, "The hook" |
| 2 | What is knowable at that point: reads, writes, schema, plan, parameters? | Reads: what each IO step's display data states (a file pattern, a BigQuery table or query, Kafka topics and servers, a JDBC URL and query or table, a Pub/Sub topic). Writes: the same for writes; `FileIO.write` publishes neither destination nor sink (friction log 1), so they are read from non-public members of `FileIO.Write` by reflection, and `JdbcIO.write` hides its URL behind its data-source provider (read the same way); both live in `BeamIO` only and fail closed. Columns: the dataset schema a Parquet or Avro read states, a BigQuery write's table schema, the collection's Avro coder or Beam row schema, and the rows a text parser (`JsonToRow`, `CsvIO.parseRows`) or formatter (`ToJson`, `CsvIO.writeRows`) works on. Not knowable: the fields a filter, join or grouping uses (not in display data, nor in the portable form: friction log 19), what a function does, the schema of the files on disk. | `BeamTranslatorSpec`, `BeamIOSpec`, `BeamTextFormatsSpec`; `BeamIO` |
| 3 | How could a platform attach this to a job it does not own? | `--runner=` plus `--invaract...` options registered through `PipelineOptionsRegistrar`. Works on an unmodified job. Does not reach a job that sets its runner in code or ignores its command line. | `BeamAttachSpec` (all of it); `config.zeroCodeInstall` is `partial` |
| 4 | How are datasets named, and how do they convert to the canonical `/`-separated location? | Files: a read is located by the folder of its pattern without its trailing glob segments (`in/orders/*.parquet`, `in/orders/date=*/part-*.parquet` and `in/orders/**` are all `in/orders`); a `FileIO` write by its output directory; a `TextIO`/`AvroIO`/`TFRecordIO` prefix write by the prefix passed to `.to()`. Everything else by its parts (`LocationMatching.fromParts`, D11): BigQuery `proj/ds/table` (`ds/table` with no project, a partition decorator dropped), Kafka `servers/topic`, JDBC `<url>/<table>`, Pub/Sub the resource path. The shared rule (a relative declared location matches any location ending in it) does the rest. | `BeamLocationsSpec`; `LocationMatching` |
| 5 | Which formats and catalog technologies does it have, and what are their canonical names? | `parquet`, `avro`, `text`, `csv` (CsvIO), `json` (ToJson), `bigquery`, `kafka`, `jdbc` (canonical), `tfrecord`, `pubsub` (not in the canonical list). A plain text writer publishes no delimiter, so a text write is `text` and satisfies a declared `csv` or `json` too (D5). Catalog: BigQuery tables, technology `bigquery`, namespace `[project, dataset]`; nothing else has one. | `BeamCheckSpec` "a text write satisfies...", `BeamIOSpec`; `Formats` |
| 6 | What are its write dispositions, and their defaults? | BigQueryIO's: `WRITE_APPEND`, `WRITE_TRUNCATE`, `WRITE_EMPTY` (the default) are `append`, `overwrite`, `error`. File, Kafka, JDBC and Pub/Sub writes have none, so a contract that declares a save mode for one is refused rather than passed unchecked (D13). `check.saveMode` is `partial`. | `BeamIOSpec` "a BigQuery table write is located..."; scenarios `output-save-mode-*` (run as BigQuery writes) |
| 7 | How do its types map to `LogicalType`? | See "Type mapping". | `BeamSchemasSpec` |
| 8 | What does nullability mean? | Avro: a union with `null` is nullable, anything else is not. Beam rows: `FieldType.getNullable`. Both are the declared schema the job gives, not the files' real contents. | `BeamSchemasSpec`; scenario `output-nullability-mismatch` |
| 9 | What are its function names, especially the non-deterministic ones? | A Beam job calls Java methods, not named engine functions, so there is no catalog to map. `analysis.functionCatalog` and `analysis.fingerprint` are unsupported. | survey section 7.1 |
| 10 | What changes data without being a plain write? | Any function that calls out of the pipeline (an HTTP call, a JDBC insert) and any IO the adapter does not recognise. The fail-closed representative is a step that ends the pipeline without being a recognised write; a side effect in the middle of a pipeline is invisible to every pre-run check. The read-side counterpart: a function that reads from outside is invisible too, and an IO built on `Impulse` (a splittable DoFn) is seen but not located. | scenario `untranslatable-write-fails-closed`; `BeamCheckSpec`, `BeamIOSpec` |
| 11 | Does it stream? Does it have a checkpoint or cache? | It streams (`PCollection.isBounded`): `FileIO.match().continuously()`, `TextIO.read().watchForNewFiles()`, Kafka and Pub/Sub reads, windowed writes. The graph is the same before submission whether a collection is bounded or not, so a stream is checked as a batch is; the kit's streaming scenarios run one to completion in-process (`Watch.Growth.afterTimeSinceNewOutput`). No checkpoint or cache erases history, so `lineage.boundaryResolution` is not applicable. | scenarios `streaming-*`; `BeamIOSpec` "a Kafka read..." |
| 12 | What runs in CI with no secrets? | Beam's in-process `DirectRunner` over local Parquet files (the same level of evidence Spark has with `local[*]`); Beam's own in-memory BigQuery (`FakeBigQueryServices`), on which a BigQuery write really runs; a local Flink mini-cluster for the production-runner hand-over. Kafka, JDBC and Pub/Sub graphs are constructed, never run against a service. The suite runs on Beam 2.60, 2.65, 2.70 and 2.77 (`beam-version-matrix`). | `BeamConformanceSpec`, `BeamProductionRunnerSpec`; `supported-beam-versions.properties` |

Nullability: Avro `["null", T]` and a nullable Beam field are nullable; everything else is not.

A BigQuery write's declared table schema maps as `docs/MULTI_ENGINE_ADAPTERS.md`'s type table says: `INT64`/`INTEGER` `long`,
`FLOAT64`/`FLOAT` `double`, `NUMERIC` `decimal(38,9)` (or its declared precision and scale), `BIGNUMERIC` `decimal(p,s)` only when
`p <= 38` (otherwise `OtherType("bignumeric")`), `DATE` `date`, `DATETIME` `timestamp_ntz`, `TIME` `time`, `TIMESTAMP` `timestamp`,
`JSON` `json`, `GEOGRAPHY` `geography`, `INTERVAL` `interval`, `RECORD`/`STRUCT` `struct`, `RANGE` `OtherType("range")`. Mode
`REQUIRED` is not nullable, `REPEATED` is a non-null array of the element type, `NULLABLE` (or none) is nullable (`BeamLocationsSpec`).

## Design decisions

D1 to D9 are the survey's (`docs/BEAM_ADAPTER_SURVEY.md`). These were taken while closing the open items; each is reversible in one
place, and the ones marked **decision needed** are for a reviewer to confirm or change.

- **D10. A write whose file format cannot be told is refused when the contract declares a format.** The core skips a comparison
  when the actual side is unknown, so a custom sink would otherwise pass any declared format. `BeamCheck.refusal`.
- **D11. Non-file datasets are located by their parts** (`LocationMatching.fromParts`): BigQuery `proj/ds/table` (`ds/table` when
  the job states no project, since its default project is not known), Kafka `servers/topic`, JDBC `<url>/<table parts>`, Pub/Sub the
  resource path. A relative declaration (`ds/table`, `orders`) matches them anywhere; an absolute one pins them. `BeamLocations`.
- **D12. A read from outside the pipeline that states no location is seen, not ignored** (a BigQuery or complex JDBC query,
  `Read.from` an unknown source, an `Impulse`-driven source, `matchAll`, a Kafka topic pattern). It is an `UnknownPlan` of source type
  `UnlocatedRead`, which the core treats as a place a declared input may be read unseen: a declared input it may hide is reported
  unverifiable (report-only) rather than missing, and with `rejectUndeclaredInputs` the write is refused, because an undeclared
  input cannot be ruled out. Refusing every such job was the alternative; it would block every job that reads a BigQuery query.
- **D13. A contract that declares a save mode for a write that states none is refused**, for the reason D10 is.
- **D14. Decision needed: steps that end the pipeline but only report on it.** A step that consumes only a recognised write's own
  result (the file names a `FileIO` write returns, a BigQuery `WriteResult`) or a metrics or logging step whose output nobody uses
  is refused as an unverifiable write, by the survey's D6 rule. Real jobs do both (notify-on-write, count-and-log). Options:
  (a) keep refusing (today); (b) let a step through that consumes only a write's result, since it sees file names, not the data;
  (c) an allow-list of step names a platform trusts, an engine-neutral setting in `InvaractConf`. Recommended: (b) and (c).
- **D15. A JDBC query's table is taken only from a plain `SELECT ... FROM <one table>`** (no join, sub-query, set operation or
  comma list); anything else is an `UnlocatedRead` (D12). No SQL parser is pulled in. `BeamLocations.singleTableOf`.
- **D16. The production runner proven is Flink**, in a local mini-cluster, on the Flink line Beam publishes for the release under
  test (1.18 before Beam 2.65, 1.19 from it). Dataflow cannot run without a Google Cloud project, so its hand-over is the same
  code path (`PipelineRunner.fromOptions` on the delegate's class) without a test of its own.
- **D17. Decided: a declared output no write lands on refuses the job.** If a contract says the job writes an output and it does
  not, that is a contract break. Beam sees the whole pipeline before it runs, so `BeamCheck` calls the new engine-neutral
  `VerificationPipeline.requireOutputsWritten` with every write's location, right after the unverifiable-step gate and before any
  write is checked: one `MISSING_OUTPUT` per declared output nothing lands on, one FAILED event, nothing started. A pipeline with
  no recognised write at all is refused the same way (it used to pass with a warning). The new capability `check.outputsWritten`
  (not blocking, since every contract declares outputs) is `supported` here and `unsupported` on Spark, which checks one write at
  a time and cannot know a write will never come; the kit's `declared-output-never-written` scenario holds it. The three
  `derivedFrom` scenarios became single-output contracts, so no scenario but that one has a job that skips a declared output.
- **D18. Decided: a dataset may declare no columns.** A write of plain strings (a dead-letter folder of error lines, a log export)
  exposes no columns. The contract format now lets a dataset leave `schema` out (or list no fields): its content is not governed,
  `SchemaChecker` compares nothing for it, and `ContractValidator` warns so the omission is never silent. A Beam write with no
  columns is refused only when the output it lands on declares columns (`BeamCheck.declaresColumns`); in dry-run mode such a write
  gets a draft whose output declares none (`INFERRED_DEGRADED`, saying why), rather than being skipped. Still refused, and for the
  job to fix rather than the contract: a BigQuery write of `TableRow`s into an existing table that names no schema
  (`CREATE_NEVER`), whose columns exist but only BigQuery knows them (`withSchema`, or rows with a Beam schema and
  `useBeamSchema()`, fixes it).
- **D19. Decision needed: plan-shape rules for Beam's schema transforms.** `Filter.whereFieldName(s)`, `Group.byFieldNames`,
  `Join.innerJoin(...).using(...)` and `CoGroup` name the fields they use, which is what `required_filter_columns`,
  `required_group_by`, `required_join_columns` and `forbid_cross_join` check. None of them has a public getter (checked with
  `javap` on 2.77.0), so reading them means reflecting into private state, as the adapter already does for a JDBC URL and a
  decimal's precision. Options: (a) keep `rules.planShape` unsupported (today); (b) read the schema transforms' fields by
  reflection, gated by the version matrix and failing closed when reflection fails, and declare `rules.planShape` partial: a
  filter or join written as a plain function stays opaque, so a rule requiring one would reject it. Recommended: (b), since
  the rules are column lists and schema transforms are how Beam users who care about columns write these steps.
- **D20. A key-value pair of plain values is the columns `key` and `value`.** Kafka's own record model, and the columns a Spark
  job writes to a Kafka topic, so one contract describes a Kafka output on either engine. The types come from the pair's coders
  (string, the integer widths, double, float, boolean, bytes); `NullableCoder`, which KafkaIO always uses, makes a column
  nullable. A pair holding an object, a Kafka read with metadata (`KafkaRecord`) and a `writeRecords()` of `ProducerRecord`s
  expose no columns, so such a write is refused (D7). `BeamSchemas.fromCoder`.
- **D21. A classic template's runtime parameters are not locations.** A path given as a `ValueProvider` with no value while the
  pipeline is built (a classic Dataflow template's parameter) is shown in display data as the provider itself
  (`RuntimeValueProvider{propertyName=inputFile, ...}`). It was taken as a path (an empty read location, a write "to" the
  provider's text). Now a read from one is an `UnlocatedRead` naming the parameter (D12) and a write to one is refused as
  unverifiable, naming it: the check runs before the values exist. A Flex Template builds its pipeline with the values, so it
  is checked like any job. `BeamIO.isRuntimeParameter`.

## Friction log

Every undocumented decision, surprise, or guess made while building this adapter, as it happened. It is the input to improving
`docs/ADDING_AN_ENGINE_ADAPTER.md` and the add-an-adapter skill.

1. **The survey assumed Parquet has a write transform of its own; it does not.** `ParquetIO.read` is a transform whose display data states
   its file pattern, but a Parquet write is `FileIO.write().via(ParquetIO.sink(...))`, and `FileIO.write` publishes neither its destination
   nor its sink (its display data names only `FileIO$Write$ViaFileBasedSink`). The survey's "read it through `WriteFiles.getSink()`"
   gave the temporary directory, which is the destination only by default. The fix was reflection on `FileIO.Write`'s non-public
   `getOutputDirectory()` and `getSinkFn()`, confined to one method and failing closed. *For the guide:* question 2 should say to check the
   write's own display data, not infer it from the read's.
2. **The kit demanded analysis results from an adapter that had refused the scenario.** An adapter that declares
   `analysis.staticDataQuality` or `analysis.roleConsistency` unsupported must refuse those scenarios, but the kit still compared the
   verdicts they expect against what the adapter reported, so none could conform. Beam was the first adapter to hit it. Fixed in the
   kit (PR #147), with a test.
3. **Which test shows a capability is not obvious when the capability is a mode.** `reporting.dryRunInference` and
   `config.zeroCodeInstall` needed a real job run from `main` with command-line flags; a helper (`ExampleJob`) that knows nothing about
   Invaract was the answer, and it is also where the bypass is recorded as a test.
4. **A Scala companion `fromOptions` is found by Beam as the runner's static method, and a Scala trait with abstract getters and setters
   is accepted as a Beam options interface.** Both were unverified in the survey; both work (`BeamAttachSpec`).
5. **A glob in a comment starts a nested comment in Scala** (`/*` inside a doc comment). `in/orders/*.parquet` in a scaladoc broke the
   build with "unclosed comment".
6. **`TransformHierarchy.Node` is an inner class in Scala's eyes** (`TransformHierarchy#Node`), and `Filter.by` is ambiguous between
   `SerializableFunction` and `ProcessFunction` unless the argument is typed.
7. **Reading a class's static field initialises it.** The test that a configured class name is not initialised before it is checked
   had to record the initialisation in a system property, because inspecting a field would itself run the initialiser.
8. **Beam leaves a `.temp-beam` folder beside a `FileIO` write's files**; a test that lists the output directory must filter.
9. **Maven Central answered HTTP 429 from the development sandbox**; local resolution used Google's public mirror through an untracked
   `local-mirror.sbt`. CI is unaffected.
10. **Hadoop's file system needs native libraries on Windows**, which the CI matrix runs. The scenario inputs are therefore written with
    Parquet's own `LocalOutputFile`, and Beam's `ParquetIO` reads and writes through its own channels, so no Hadoop file system is touched.
11. **A location for a prefix write is a choice.** `TextIO.write().to("out/text")` writes `out/text-00000-of-00001`; the adapter reports the
    prefix as given (a contract declares `out/text`), not the folder.
12. **The mutation-testing CI job is not generated.** `check_modules.py` says the job is missing but not what it should say; it was
    copied from `mutation-testing-adapter-testkit`. *For the guide:* a template for it would remove a copy-and-edit step.
13. **`dev/new-adapter` numbers the write-up's contributor-docs order as the highest existing order plus one**, so a document added by
    hand to the same section takes the slot the next adapter expects and fails `test_new_adapter`. The survey now shares the guide's slot.
14. **The generator's own tests assumed one adapter.** `test_new_adapter` expected a new adapter to follow `spark-adapter` and the next
    contributor-docs order to be 9; with Beam registered both stopped being true. They now compute "the last published module" and "one past the
    last design doc" from the registry they are given.
15. **The survey's forecast was right about the count** (21 by checking, 17 by refusing safely, 13 skipped: all as forecast), and wrong
    in one design detail (item 1). The retrospective is in `docs/BEAM_ADAPTER_SURVEY.md`.
16. **`Create.of` is built from a source, or from an `Impulse`, depending on the release and the coder.** The first unlocated-read rule
    flagged `Create.of` (a `Read.from(CreateSource)`) as an outside read, and the `Impulse` rule then hid every file write, because
    Beam's own `WriteFiles` contains a `Create`; and `Read.from(CountingSource...)` is itself built from an `Impulse`. The fix names
    the steps that make data in the job (`BeamIO.isInJobData`, a `Read.from` of their sources included) and leaves their insides out
    of every IO search. *For the guide:* probe what the engine's own built-in transforms expand to before classing a
    primitive as a read.
17. **Version-specific details stay out of the adapter's main code.** Beam vendors Guava under a package that changes between
    releases (`v32_1_2_jre` in 2.77); naming it in `InvaractRunnerRegistrar` would have broken the version matrix. The test fixtures
    hit the same thing with Parquet's `LocalOutputFile` (missing from the Parquet Beam 2.60 brings).
18. **Probes of common pipeline shapes** (a scratch spec printing the graph and the translation; not committed), with what each found:
    01 a partitioned glob read was located at `orders/date=*` (fixed); 02 a recursive `**` read (fine); 03 `FileIO.writeDynamic`
    (fine, its output directory); 04 a compressed, suffixed text write (fine); 05 `Flatten` of two reads (both reads seen); 06 a
    multi-output `ParDo` feeding two writes (each checked); 07 a step consuming a write's file names and 08 a dangling metrics step
    (both refused, D14); 09 `ValueProvider` paths known at construction (fine); 10 `gs://` paths (fine); 11 a projected Parquet read
    reported the projection as the dataset's columns (fixed); 12 `Partition` (fine); 13 a side input from a second read (the read is
    seen); 14 a text `writeDynamic` (fine); the IO probes found the `FileIO.match()` read idiom, which hid its read entirely (fixed),
    the schema-aware text transforms (fixed), BigQuery partition decorators (fixed) and `Impulse`-driven sources (fixed).
19. **The portable form does not name a transform's fields either.** `PipelineTranslation.toProto` carries a schema transform's
    configuration as a serialised Java function, and its display data only names the function's class, so a filter's, join's or
    group-by's fields are no more visible there than in the graph. `rules.planShape` stays unsupported. (A group-by's key schema
    does name its fields, but a filter's never appear, so the capability could not be claimed even as partial.)
20. **Stryker refuses a `break` threshold above its `low` one.** The adapter pinned `break` at 90 with the generated `low` of 80,
    so the whole-module run on `main` failed before mutating anything (the PR's incremental run passes its own thresholds and did not
    notice). Fixed by raising the bands. *For `dev/new-adapter`:* the generated comment should say the bands must stay above `break`.
21. **A BigQuery write can be run in CI with no Google Cloud project.** Beam ships an in-memory BigQuery (`FakeBigQueryServices`,
    in the main `beam-sdks-java-io-google-cloud-platform` jar), so the save-mode and catalog scenarios write a real table there instead of
    being refused.
22. **Beam SQL needs no special case.** A query is an opaque step whose output has a schema; the tables a query defines for itself
    expand into the IO transforms they name (a text table into `TextIO`), which the translator already recognises. A probe that used
    `p:d.report` as a BigQuery table met Beam's own refusal of a one-letter project id while building display data; the adapter
    fails closed on that (no display data, so the write is unverifiable), which is what a real job with a bad table name would see.
23. **The second probe pass (after the gaps closed).** Each shape below became a permanent test. Fixed: a classic template's runtime
    parameters were taken as paths (D21); every Kafka write was refused for exposing no columns (D20); a reader handed files by in-job
    data made a declared input "missing" instead of unverifiable; a Pub/Sub write of `ToJson` rows had no columns; Beam's dry run
    published no job summary and no self-check (both now shared with Spark in `verification-core`). Fine as they were: `Wait.on` a
    write's result, `Partition`, `Flatten`, `watchForNewFiles`, BigQuery's Storage Read and Write APIs, Pub/Sub subscriptions, an
    unknown IO (Bigtable read unlocated, Spanner write refused), `FileIO.write().withNaming(...)` with no directory (refused).
    Found to be a decision: plan-shape rules from schema transforms (D19), whose fields have no public getter.
24. **A file write's columns were the records', not the file's.** `FileIO.write().via(ParquetIO.sink(schema))`,
    `AvroIO.sink(schema)` and `AvroIO.writeGenericRecords(schema)` write their files with the schema they are given, which can
    leave out columns the records carry; the adapter reported the records' columns, so a contract requiring a column the file
    lacks would have passed. The columns are now the sink's (`getJsonSchema`, read like the sink class already is) or the Avro
    write's own (`schema` in its display data). Found with D17/D18's probe pass; a buggy `populateDisplayData` in a user
    transform was confirmed harmless (the step just has no display data).

## Unverified items

What could not be checked against the engine, to be settled by the adapter's own tests.

- **Beam releases outside 2.60 to 2.77.** The suite passes on 2.60.0, 2.65.0, 2.70.0 and 2.77.0 (`beam-version-matrix`); a release
  that changes the IO class names or the members `BeamIO` reads by reflection makes those steps fail closed, and the matrix is where
  that shows up first.
- **Runners other than the DirectRunner and Flink.** Dataflow, Spark and Samza hand-over is the same code path, not tested on its own (D16).
- **Kafka, JDBC and Pub/Sub against a real service.** Their graphs are constructed in the tests, never run; what is checked is what the
  graph states before submission, which does not depend on the service.
