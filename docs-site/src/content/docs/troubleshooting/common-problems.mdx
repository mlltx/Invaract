## `./dev/test` exits non-zero

Work through this in order:

1. **Check the console output** — the script names which of its 7 steps failed.
2. **Review the report**:
   ```bash
   cat demo/output/report.json | jq .
   ```
   Look at `status`, `contractVerification` (is this an engine rejection, or something
   else?), and `error`.
3. **Check the web UI** (`./dev/report`) for the Contract Verification and Plugin Events
   sections.
4. **Narrow down where the problem is**:
   - Verification/translation issue → run `cd spark-adapter && sbt test` before assuming
     it's the demo transformation.
   - A `MISSING_OUTPUT_FIELD`/`OUTPUT_FIELD_TYPE_MISMATCH`/similar violation → your
     contract and your job's actual output disagree; see
     [Reference → Violation Types](/reference/violation-types/).
   - `UNVERIFIABLE_WRITE` → your job writes via a shape Invaract doesn't recognize; see
     below.

## A write is rejected with `UNVERIFIABLE_WRITE`

This means Invaract found a command that changes data but couldn't translate it into a
recognized write — so it refused to guess, and rejected it. This is deliberate; see
[Fail-Closed by Default](/concepts/fail-closed/).

Check whether your write goes through a shape listed in
[Reference → Connector Support](/reference/connector-support/). If it doesn't
(a DataSourceV2 catalog write, or `MERGE`/`UPDATE`/`DELETE` outside the connectors this
covers), support for it may not exist yet.

A statement that removes or moves a table's data names the table in the message rather than a
Spark class. There are three cases:

- **`DROP TABLE`, `TRUNCATE TABLE` or `ALTER TABLE ... DROP PARTITION` on a table the contract
  does not declare**, such as a job that begins `DROP TABLE IF EXISTS top_customers` before
  rebuilding it. Declare the table as an output: the statement is allowed on a declared output
  that may be overwritten (no `saveMode`, or `saveMode: overwrite`). The job must then write
  it too, or it ends with `MISSING_OUTPUT`. See
  [Fail-Closed by Default](/concepts/fail-closed/#statements-that-remove-data).
- **`ALTER TABLE ... SET LOCATION`, `ADD PARTITION ... LOCATION` or `RENAME TO` on a declared
  output.** The output would hold data no checked write produced, or stop existing under the
  name the contract gives. Write the output with a query instead, or change the contract's
  location in the same change.
- **A column change Invaract could not work out** on a declared output (rare; it depends on a
  Spark method that may differ in a Spark release Invaract has not been tested with).

On Beam, the same violation names the step that ends the pipeline without a recognized
write. If that step only reports (it sends metrics or a notification, and writes no governed
data), a platform can let it through with the
[trusted steps setting](/reference/configuration/#making-the-checks-stricter).

## A write is rejected as "too deeply nested"

```
[UNVERIFIABLE_WRITE] 'DeeplyNestedPlan' ... this write's plan is too deeply nested for Invaract to verify
```

The write's plan is so deep (thousands of chained steps, typically a loop of `withColumn` or
`union` calls) that even Invaract's retry, on a thread with a very large stack, could not walk
it. Rather than let the write through unchecked, Invaract refuses it. Shorten the plan before
writing: call `.checkpoint()` or `.localCheckpoint()` part way through the loop, or write an
intermediate table and read it back. Queries that write nothing (`count()`, `show()`) are never
refused for this.

## A rule check is rejected with `RULE_UNVERIFIABLE_DML`

Your contract declares a DML rule (`merge_condition`, `forbid_unconditional_delete`, or
`allowed_update_columns`) against an operation Invaract recognizes as real DML but can't
extract the specific fact that rule needs from — today, this is known to happen for
Iceberg's merge-on-read `UPDATE`. See
[Enforce Row-Level DML Rules](/guides/enforcing-dml-rules/) for exactly which
combinations are covered per connector.

## `InaccessibleObjectException` running `sbt test` directly on JDK 17+

<Aside type="caution">
Spark reflectively accesses JDK-internal classes (`sun.nio.ch.DirectBuffer`, via
`org.apache.spark.storage.StorageUtils`) that JDK 17+'s module system closes by default.
</Aside>

`spark-submit`'s own launch scripts inject the required `--add-opens` flags
automatically, which is why `./dev/test`'s primary path needs no changes. If you invoke a
module's tests directly (`sbt test` inside `spark-adapter` or `plugin`) or use `dev/test`'s
`java -cp` fallback path (used when `spark-submit` isn't on `PATH`), those flags are
already set in `spark-adapter/build.sbt`/`plugin/build.sbt`/`dev/lib.sh` — if you're
invoking Spark some other way and hit this error, add the same flag set yourself (see
`dev/lib.sh` for the full list).

## Contract parses but is rejected as invalid

A document can be syntactically valid YAML and still fail `ContractValidator` — missing
`outputs`, a duplicate field name, an empty schema. Check `INVALID_CONTRACT` in your
violations list, and see
[Reference → Contract Format](/reference/contract-format/#validator-checks) for
the full list of checks.

## Something in the contract seems to be ignored

Invaract reads only the keys it knows and keeps the rest, because a contract may carry
anything the Open Data Contract Standard or your own team defines. A misspelt key is
therefore not an error: `nulable: false` is kept and ignored, and the field stays nullable.
When a job starts with a contract, Invaract logs a warning for each key spelt close to one
it reads, and for each other thing the contract validator warns about, such as a field type
or format it doesn't recognize:

```
WARN AttachSetup$: Invaract: contract orders@1.0.0: [Warning] outputs[0].schema.fields[0].nulable: Unknown key 'nulable' is ignored. Did you mean 'nullable'?
WARN AttachSetup$: Invaract: contract orders@1.0.0: [Warning] outputs[0].format: format 'parqet' is not one of the canonical formats (avro, bigquery, csv, delta, excel, feather, hive, hudi, iceberg, jdbc, json, kafka, orc, parquet, table, text); it can only match an adapter that reports exactly this string, so the same contract may fail on another engine. Did you mean 'parquet'?
```

Search the job's log for `Invaract: contract` to find them. A contract fetched from a
[registry](/guides/using-a-contract-registry/) is checked the same way, except for
misspelt keys: those are found only in a contract read from a file.

## A setting is refused with "must be true or false"

Every setting that switches something on (`dryRun`, `rejectUndeclaredFields`,
`computeFingerprint`, ...) takes `true` or `false`, in any case. Anything else, such as
`yes` or `1`, is refused when the job starts, naming the setting:

```
'spark.invaract.dryRun' must be true or false, not 'yes'.
```

A notification config's `sink.enabled` is held to the same rule, and the message names the
file. A value Invaract can't read is never quietly taken to mean `false`.

## The job stops with "Invaract does not read 'spark.invaract.…'"

A `spark.invaract.*` setting is misspelt, or isn't one Invaract has. The message names the
setting you probably meant:

```
Invaract does not read 'spark.invaract.rejectUndeclaredInput'. Did you mean 'spark.invaract.rejectUndeclaredInputs'?
```

Fix the spelling where the job is launched. The names are case-sensitive, as all Spark settings
are: `spark.invaract.dryrun` is refused, `spark.invaract.dryRun` is read. Every setting is listed
in [Configuration Settings](/reference/configuration/). In dry-run mode the same message is only
a warning, and the misspelt setting has no effect.

## A location doesn't match even though it "looks right"

A declared location matches the place the job reads or writes when it is that place, or the
end of it starting at a `/`; slashes, a `file:` prefix and `s3a://`/`s3://` don't matter. See
[Reference → Contract Format](/reference/contract-format/#location-matching) for the rule and
examples. The usual reasons it still doesn't match:

- **Case.** `Orders` doesn't match `/data/orders`.
- **A full path against a cluster URL.** `/data/orders` doesn't match
  `hdfs://nn:8020/data/orders`: write `data/orders`, or the whole URL.
- **A dotted table name.** `gold.orders` is one segment and never matches the table. Write
  `gold/orders` (see [Tables](/reference/contract-format/#tables)).
- **A partition's folder of an output.** A read of `/data/orders/date=2024-01-01` counts as a
  read of a declared input `orders` ([Reading part of an input](/reference/contract-format/#reading-part-of-an-input)),
  but a write into it is a write somewhere other than a declared output `orders`.

The violation names the location the job actually used, so compare the two from there.

## `ClassNotFoundException: ...SupportsNonDeterministicExpression` installing the enforcement rule

This means you're running a Spark version below this project's verified floor. Invaract's
Delta Lake support depends on `delta-spark` 3.3.3, which requires a class
(`SupportsNonDeterministicExpression`) that Spark only introduced in **3.5.6** — on an
older 3.5.x patch (3.5.1–3.5.5), installing the enforcement rule into a Delta-extended
`SparkSession` throws this exception before your job's own code runs at all.

Upgrade to Spark 3.5.6 or later. See
[Reference → Spark Version Support](/reference/spark-version-support/) for the exact
verified range, and — if you're on a version recent enough to also install
`ContractEnforcementRule`'s own runtime compatibility guard — check your job's logs for
an `Invaract is running against Spark ...` warning naming the version it actually
detected, which points at the same page.

## `does not support truncate in batch mode` / `TableCapabilityCheck` writing to Delta

This is a Delta Lake/Spark version mismatch, not a bug in your job or your contract.
`delta-spark` releases before 3.3.3 (3.3.0–3.3.2, and the entire 3.2.x line) were built
against an older Spark line than this project's supported Spark floor — running one of
those `delta-spark` releases against a newer Spark session hits exactly this
`TableCapabilityCheck` failure on an ordinary Delta write. There is currently no
`delta-spark` release below **3.3.3** that works with this project's supported Spark
range at all.

Pin `delta-spark` to 3.3.3. See
[Reference → Connector Support](/reference/connector-support/#spark-connectors) for
the current verified Delta version, and (same as above) check for an
`Invaract is running against Delta Lake ...` warning in your job's logs if you're on a
version new enough for the runtime compatibility guard to have run.

## Dry-run reports `SKIPPED_UNRECOGNIZED` for a write that works fine

With a [notification sink](/guides/dry-run-mode/#report-dry-run-results-to-a-sink-to-roll-invaract-out-across-many-jobs)
configured, dry-run mode reports every write-shaped command it couldn't infer a contract from.
Running this through `spark-sql` is a real example:

```sql
CREATE TABLE orders_archive (id INT, value INT) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';
LOAD DATA LOCAL INPATH '/tmp/invaract-example/data/orders.csv' INTO TABLE orders_archive;
```

```
"'LoadDataCommand' may write data but Invaract has no translation for it; with a contract active, enforcement would reject it as an UNVERIFIABLE_WRITE"
```

The statement itself works. The point is what enforcement would do with it: Invaract has no
translation for that command, so with a contract active it would reject it as an
[`UNVERIFIABLE_WRITE`](#a-write-is-rejected-with-unverifiable_write). Dry-run is telling you
so now, before you turn enforcement on. Write the table with the DataFrame API or `INSERT INTO`,
or check [Connector Support](/reference/connector-support/) for the shape you need.

A `DROP TABLE`, `TRUNCATE TABLE` or `ALTER TABLE ... DROP PARTITION` is reported
`SKIPPED_UNSUPPORTED` instead, not as a blocker: enforcement allows it on a declared output that
may be overwritten (see [Fail-Closed by Default](/concepts/fail-closed/#statements-that-remove-data)).

## Dry-run reporting prints a warning and no events arrive

If `spark.invaract.notifyConfig` can't be loaded, dry-run mode doesn't fail your job. It logs
one warning, and falls back to logging the inferred contract:

```
WARN AttachSetup$: Invaract dry-run mode: could not set up the notification sink named by 'spark.invaract.notifyConfig=/etc/invaract/notify.properties' (java.lang.IllegalArgumentException: 'spark.invaract.notifyConfig' names '/etc/invaract/notify.properties', which is not a file that exists.); falling back to logging inferred contracts. The job is not affected.
```

The cause is in the parentheses: here, a path that doesn't exist on the machine where the
driver runs. In a cluster deploy mode that is the cluster, not your laptop, so make sure the
file is shipped there (for example with `--files`). A `sink.class` that doesn't exist
(`Class '...' was not found: check the name, and that its jar is on the job's classpath`), or a
sink whose own required property is missing, is reported the same way. When Invaract is
enforcing a contract rather than in dry-run mode, each of these stops the job at start-up
instead, with the same message.

## Spark: `Contract file not found` in cluster mode

```
Contract file not found: /path/to/contract.yaml. If a Spark job runs in cluster mode, ship the file with --files and name it by its file name.
```

With `--deploy-mode cluster` the driver runs on a machine of the cluster, where the path you
gave does not exist. Name the file by a URI the cluster can read
(`--conf spark.invaract.contract=s3a://bucket/contracts/orders.yaml`), or ship it with
`--files /path/to/contract.yaml` and set `spark.invaract.contract=contract.yaml`. See
[Where the contract file can live](/guides/installing-the-enforcement-rule/#where-the-contract-file-can-live).

## Spark: the job runs, but nothing is checked

No `CONTRACT_VALIDATION` events, no `Invaract` lines in the driver log, and writes to places
the contract does not declare go through. Invaract was never installed in the session. With
`spark.sql.extensions` alone, Spark only logs one warning when it cannot load a class:

```
WARN SparkSession: Cannot use com.invaract.sparkadapter.InvaractSparkSessionExtension to configure session extensions.
```

That happens when the class name is misspelt or the jar is not on `--jars`. It also happens
with no warning at all when the job's own code sets `spark.sql.extensions` (for Delta Lake or
Iceberg), which replaces the list `spark-submit` gave. Attach Invaract with
`--conf spark.plugins=com.invaract.sparkadapter.InvaractSparkPlugin` instead: a plugin Spark
cannot load stops the job, and the plugin adds Invaract to whatever extensions the job sets.
See [Install the Enforcement Rule on Spark](/guides/installing-the-enforcement-rule/).

If Invaract is installed but only reports (`CONTRACT_INFERENCE` events, no blocking), the job's
configuration has turned on `spark.invaract.dryRun`. A platform can stop that by pinning the
setting: see [Lock Settings for a Platform](/guides/locking-settings-for-a-platform/).

## Beam: the pipeline runs, but nothing is checked

`--runner=Invaract` (Java) or `--runner=invaract_beam.InvaractRunner` (Python) only takes
effect if the job builds its options from its command line and doesn't set a runner in code
afterwards. A job that does either runs on its own runner and Invaract never sees it: no log
line, no events. The Java guide's
[When the command line cannot reach the job](/guides/using-invaract-with-apache-beam/#when-the-command-line-cannot-reach-the-job)
shows the one-line check to add for such a job.

## Beam Python: `CheckNotRun`

The pipeline was not submitted because the check could not be made. The message says why:

| Message starts | Fix |
|---|---|
| `Invaract could not start its checker (java: ...)` | Install Java 11 or later where the job is submitted, or point `--invaract_java` at it. |
| `Invaract has no checker to run` | Build the checker jar (`cd beam-adapter && sbt assembly`) and set `INVARACT_BEAM_CHECKER_JAR` or `--invaract_checker_jar`. |
| `--invaract_check_only=... must be true or false` | Use `true` or `false`. |
| `--invaract_delegate names InvaractRunner itself` | Name the runner the job should really run on, for example `DataflowRunner`. |
| `Invaract could not check the pipeline, ...` | The checker's own reason follows, for example a contract file it can't read or a setting it doesn't know. |

A job submitted from a machine without the package stops earlier, with
`ModuleNotFoundError: No module named 'invaract_beam'`: install it there
([What a job needs](/guides/using-invaract-with-beam-python/#what-a-job-needs)).

## Python jobs: `CheckNotRun`

The job stopped with exit status 2, and published nothing, because a check could not be made.
The message says why:

| Message starts | Fix |
|---|---|
| `Invaract has no native checker for this platform, so it runs its checker with Java, and found none` | Install Java 11 or later where the job runs (`JAVA_HOME`, or `java` on the `PATH`), or set `INVARACT_CHECKER`. |
| `Invaract has no checker to run on this platform` | The package was installed without a checker (from a source checkout, for example). Install it from PyPI (`pip install invaract`), or set `INVARACT_CHECKER`. |
| `Invaract could not start its checker (...)` | `INVARACT_CHECKER` names a program that cannot be started. |
| `Invaract's checker stopped (exit status ...)` / `Invaract's checker answered '...' with ...` | The checker ended, or wrote something that is not a reply. If `INVARACT_CHECKER` is set, check that it runs Invaract's own checker (the native program, or `java -jar invaract-pythonio-checker-<version>.jar`); the checker's own error is on the job's standard error. |
| `Invaract could not check 'open': ContractParseException: Contract file not found: ...` | The contract `@invaract.job` or `INVARACT_CONTRACT` names is not there, relative to the folder the job runs in. |
| `Invaract cannot yet write '...' as ...` | The output's format or save mode is one the package does not write. The message lists the ones it does ([Formats, save modes and locations](/guides/using-invaract-with-python/#formats-save-modes-and-locations)). |
| `Invaract cannot write files to ...` | The location is on a file system Invaract does not write to. It writes to local and mounted file systems, HDFS and object storage ([Files, tables and object storage](/guides/using-invaract-with-python/#files-tables-and-object-storage)). |
| `Invaract needs the ... package to read or write ...` | Install the extra the message names, for example `pip install "invaract[delta]"`, `"invaract[avro]"` or `"invaract[postgres]"`. |
| `Invaract reads and writes jdbc only as PostgreSQL (postgresql://...) and SQLite (sqlite:///...) tables` | A `jdbc` dataset's location names a [PostgreSQL](/guides/using-invaract-with-python/#postgresql-tables) or [SQLite](/guides/using-invaract-with-python/#sqlite-tables) table. |
| `an Iceberg location is <catalog>.<namespace>.<table>` | Name an Iceberg dataset's location by its catalog, namespace and table, for example `lake.sales.report`. |
| `Invaract has nowhere to read '...' from` / `Invaract has nowhere to write '...'` | In a dry run, every read and write needs its `location=` ([Start from a job with no contract](/guides/using-invaract-with-python/#start-from-a-job-with-no-contract)). |
| `Invaract could not describe the table handed to invaract.write('...')` | `invaract.write` takes a pandas, Polars or DuckDB frame, a Polars LazyFrame, or a pyarrow Table or RecordBatchReader. |

## Python jobs: a job ends with status 2 and "opened no run"

```text
Invaract: this job read or wrote data and opened no run, so nothing checked it (INVARACT_REQUIRE_RUN=enforce).
  orders_job.py:3 `pandas.read_parquet` reads data outside invaract: read it with invaract.read(<name>), or mark the line `# invaract: allow`
```

The platform requires every job that touches data to open a run, and this one did not. Open one around the job's work,
with `@invaract.job()` on its entry point or `with invaract.run():`, and read and write through `invaract.read` and
`invaract.write`. If what it touched is expected (a log, a file it ships with), mark the line `# invaract: allow - <why>`
or ask the platform to name it in `INVARACT_STRICT_ALLOW`. If the message ends "with INVARACT_STRICT=off what it did is
not known", the platform turned the watch off, so every job that opens no run counts, whatever it did. See [Require a
run](/guides/using-invaract-with-python/#require-a-run).

## Python jobs: "Invaract could not tell whether this job completed"

The platform opens jobs' runs (`INVARACT_AUTO_RUN=true`), and this job ended with a bare `raise SystemExit(...)`, which
the start-up hook cannot tell from a crash on Python 3.12 and later, so its outputs were not published. End the job with
`sys.exit(<status>)`, or have the platform start it with `python -m invaract <job>`. See [How Invaract knows the job
completed](/guides/using-invaract-with-python/#how-invaract-knows-the-job-completed).

## Python jobs: "no contract says what the job may do"

```text
invaract.errors.CheckNotRun: Invaract opens this job's run (INVARACT_AUTO_RUN=true), and no contract says what the job may do: set INVARACT_CONTRACT, or INVARACT_DRY_RUN=true to observe it
```

Auto-run holds a job to a contract, and none is set for this one. Set `INVARACT_CONTRACT` for the job (each job has its
own), or `INVARACT_DRY_RUN=true` to only see what it reads and writes. See [Let Invaract open the
run](/guides/using-invaract-with-python/#let-invaract-open-the-run).

## Python jobs: strict mode reports a file the job is meant to write

With `INVARACT_STRICT` on, every file the job opens to write outside the invaract package is a finding, and that
includes files that are not datasets: a log (`logging.FileHandler("job.log")`), a status page, a marker file. With
`enforce`, the job is refused where it opens the file:

```text
[UNGOVERNED_DATA_ACCESS] `open` in main (job.py:10:15) writes data outside Invaract, so no check sees it (IVR002 open-write-mode, seen as the job ran: opened /srv/jobs/orders/job.log to write (mode 'a'))
```

Say that it is expected, in one of two ways. For one job, mark the line that opens it, with the reason:

```python
handler = logging.FileHandler("job.log")  # invaract: allow - the job's own log
```

For every job on a platform, name what is let through in `INVARACT_STRICT_ALLOW` (patterns matched against the file's
path, comma-separated): `INVARACT_STRICT_ALLOW=*.log,logs/*`. Either way the file is still reported, as an exception
with its reason, so the list of what jobs write around their contracts stays visible. A scratch file in the temporary
folder is never a finding: use `tempfile` for working files. See [Watch what the job does as it
runs](/guides/using-invaract-with-python/#watch-what-the-job-does-as-it-runs).

## Python jobs: strict mode reports a file the job reads

With `INVARACT_STRICT` on, data read with a library's reader instead of `invaract.read` is a finding, and that includes
files that are not the job's inputs: a lookup table shipped with the job, a list of holidays. With `enforce`, the job is
refused where it reads the file:

```text
[UNGOVERNED_DATA_ACCESS] `pandas.read_csv` in regions (jobs/load.py:5:12) reads data outside Invaract, so no check sees it (IVR001 pandas-read, seen as the job ran: read lookup/regions.csv)
```

If the file is data the job depends on, declare it as an input in the contract and read it with `invaract.read`: that
is what the finding is for. If it is not a dataset, say so in one of the two ways above: a marker on the line
(`# invaract: allow - a table shipped with the job`), or a pattern in `INVARACT_STRICT_ALLOW` (`lookup/*`). A plain
`open(path)` to read is never reported, nor is a read from a buffer in memory or from a scratch file in the temporary
folder.

## Beam: a check-only run in CI fails before Invaract runs

Beam validates some steps itself before handing the pipeline to any runner, including in a
check-only run. A Java BigQuery read or write looks its dataset up in BigQuery, and wants
`--tempLocation`; a Python file read checks that its pattern matches a file. Give the build
what Beam asks for, or build those steps without validation. The
[Java](/guides/using-invaract-with-apache-beam/#check-a-pipeline-in-ci-without-running-it) and
[Python](/guides/using-invaract-with-beam-python/#check-a-pipeline-in-ci-without-running-it)
guides say exactly what each IO needs.

## Still stuck

1. Look up the violation in [Violation Types](/reference/violation-types/), and check
   [What Each Engine Checks](/reference/what-each-engine-checks/) for whether your engine can make
   the check at all.
2. Open an issue on [GitHub](https://github.com/mlltx/Invaract/issues) with the full
   violation message: it says what the contract expects, what the job contains, and why
   they disagree.
