The full shape `OrgPolicyParser`/`OrgPolicyValidator` accept. See
[Enforce an Organizational Policy](/guides/enforcing-organizational-policy/) for a guided
introduction.

## Document shape

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/mlltx/Invaract/main/contract/schema/invaract-org-policy.schema.json
version: "1.0"

policies:
  - id: catalog-required
    type: require_catalog
    technology: hive
    scope: outputs
    description: "All outputs must be registered in a discoverable catalog."
  - id: pii-flag-required
    type: require_field
    name: pii_reviewed
    fieldType: boolean
    scope: outputs
  - id: snake-case-fields
    type: field_naming_convention
    pattern: "^[a-z][a-z0-9_]*$"
    mode: warn
  - id: owner-required
    type: require_extension
    key: owner
    description: "Every contract must declare an owning team."
  - id: dataset-described
    type: require_dataset_description
  - id: sunset-date-if-deprecated
    type: require_extension_if
    ifKey: status
    ifValue: deprecated
    thenKey: sunsetDate
    description: "A deprecated contract must declare its sunset date."

inject:
  rules:
    - type: forbid_unconditional_delete
  minVerificationOptions:
    rejectUndeclaredFields: true

exemptions:
  - contractId: legacy_customer_orders
    policyIds: [catalog-required]
    reason: "predates policy; migration tracked in JIRA-1234"
    reviewBy: "2026-12-01"

customPolicyTypes:
  require_approved_location_prefix: com.acme.governance.RequireApprovedLocationPrefix
```

## Top-level fields

| Key | Required | Meaning |
|---|---|---|
| `version` | yes | Free-form revision identifier for this document — your own tracking, not compared against a contract's `ContractVersion`. |
| `policies` | no | The policy rules themselves — see below. |
| `inject` | no | Rules/options this policy contributes to every governed contract — see [Rule/option injection](#injectrulesinjectminverificationoptions). |
| `exemptions` | no | Platform-controlled exceptions — see [Exemptions](#exemptions). |
| `customPolicyTypes` | no | Maps a `type:` name outside the built-in set to a `CustomPolicyEvaluator` class — see [Custom policy types](#custom-policy-types). |

## Policy rule fields (`policies[]`)

| Key | Required | Meaning |
|---|---|---|
| `id` | yes | Stable identifier, referenced by `exemptions` and shown in violation messages. Must be unique within the document. |
| `type` | yes | Policy kind — see [Policy types](#policy-types) below. |
| `description` | no | Human-readable explanation, appended to violation messages for self-service remediation. |
| `scope` | no | `inputs`, `outputs`, or `all` (default). Which of a contract's datasets this rule applies to. |
| `when` | no | `{ sensitivityTag: <tag> }` — narrows `scope` further to only datasets with at least one field (recursively) carrying that [sensitivity tag](/reference/contract-format/#sensitivity-tags). |
| `mode` | no | `enforce` (default) blocks a write before any plan is analyzed. `warn` only publishes a notification event and never blocks — the safe-rollout mechanism for a newly-introduced rule. |

Every other key on a policy rule is type-specific and captured verbatim, the same way a
contract's own `rules:` entries work.

## Policy types

| Type | Properties | Checks |
|---|---|---|
| `require_catalog` | `technology` (optional) | The dataset declares `catalog.required: true`, optionally matching a specific `technology`. |
| `require_field` | `name` (required), `fieldType` (optional) | The dataset's schema declares a top-level field named `name` — not recursive into nested structs — optionally of `fieldType` (checked case-insensitively). |
| `field_naming_convention` | `pattern` (required) | Every field name in the dataset's schema — recursing into nested struct `properties` — fully matches the regular expression `pattern`. A partial match doesn't satisfy it. |
| `require_extension` | `key` (required), `value` (optional) | The **contract itself** declares `key` in its top-level `extensions` map (e.g. `extensions: { owner: data-platform-team }`), optionally pinning `key` to an exact `value` (case-sensitive). A key present but mapped to YAML `null` counts as absent. |
| `require_format` | `formats` (required) | The dataset declares `format` as one of `formats` — a single string (`formats: delta`) or a list (`formats: [delta, iceberg]`) — matched case-insensitively. A dataset with no `format` at all does not satisfy this. |
| `require_dataset_description` | *(none)* | The dataset declares a non-blank `description`. |
| `require_extension_if` | `ifKey` (required), `ifValue` (optional), `thenKey` (required), `thenValue` (optional) | A conditional `require_extension`: only once the **contract itself** already satisfies `ifKey` (optionally `=ifValue`) must it also satisfy `thenKey` (optionally `=thenValue`). A contract not satisfying the `if` condition at all produces no violation. |

A policy `type` matching neither this set nor a [`customPolicyTypes`](#custom-policy-types)
entry is recorded but never checked — the same permissive behavior an unrecognized contract
`rules[].type` already has, though `OrgPolicyValidator` now reports it as a Warning (not an
Error) since `customPolicyTypes` makes this shape more likely to be a typo than intentional.
A known type with malformed or missing properties for its shape (e.g. `require_field` with
no `name`) is an `OrgPolicyValidator` Error, not silently ignored.

<Aside type="caution" title="require_field's type pin is fieldType, not type">
A policy rule's own kind (`require_field`) is itself spelled `type:` at the same mapping
level. SnakeYAML doesn't reject a document with two `type:` keys — it silently keeps only
the last one, which would overwrite the rule's own kind rather than raise anything. The
type pin therefore uses the distinct key `fieldType`.
</Aside>

<Aside type="note" title="require_extension and require_extension_if check the whole contract, not a dataset">
`require_catalog`, `require_field`, `field_naming_convention`, `require_format`, and
`require_dataset_description` each check one dataset at a time, honoring `scope`/`when`.
`require_extension` and `require_extension_if` are different: they check the contract
document as a whole, exactly once, so `scope`/`when` have no effect on either — setting
either produces an `OrgPolicyValidator` Warning (not an Error; the rule still evaluates
correctly), since it's likely not what the author intended.
</Aside>

<Aside type="tip" title="require_extension_if answers 'only if' requirements">
`require_extension` can require a key to exist, but can't make that requirement depend on
another key's value. `require_extension_if` fills that gap — e.g. only a contract whose
`extensions.status` is `deprecated` needs to also declare `extensions.sunsetDate`; a
contract that isn't deprecated is entirely unaffected by the rule, not merely exempted
from it.
</Aside>

## Custom policy types

`customPolicyTypes` maps a `type:` name your document uses to the fully-qualified class
name of a `com.invaract.contract.CustomPolicyEvaluator` implementation — the escape hatch
for a policy type outside the built-in set above, with no Invaract source change needed.
See [Write your own policy type](/guides/enforcing-organizational-policy/#write-your-own-policy-type)
for a full worked example.

```yaml
customPolicyTypes:
  require_approved_location_prefix: com.acme.governance.RequireApprovedLocationPrefix
```

| Key | Meaning |
|---|---|
| `customPolicyTypes.<type>` | Fully-qualified class name of a `CustomPolicyEvaluator` (public no-arg constructor required), resolved reflectively and cached — one instance per class name, reused across every rule/contract that names it. |

```scala
trait CustomPolicyEvaluator {
  def evaluate(contract: Contract, rule: PolicyRule): List[PolicyViolation]
}
```

`OrgPolicyEvaluator` only consults `customPolicyTypes` for a `type:` outside the seven
built-in ones — a `customPolicyTypes` key matching a built-in `type` is dead (the built-in
always wins; `OrgPolicyValidator` warns on this). `PolicyExemption` coverage and `mode:
enforce`/`warn` splitting still apply automatically to a custom type's violations, exactly
like a built-in one.

<Aside type="note" title="Composes with spark.invaract.orgPolicy for free">
A `customPolicyTypes` entry is just more content in the same YAML document
`spark.invaract.orgPolicy=<path>` already names — the evaluator class itself is supplied
via `--jars`, the same as any other Invaract extension jar. No new `spark-submit` flag, no
job source change.
</Aside>

| `OrgPolicyValidator` outcome | When |
|---|---|
| Error | `customPolicyTypes.<type>` has an empty class name, or names a class that doesn't resolve (missing, no public no-arg constructor, doesn't implement `CustomPolicyEvaluator`). |
| Warning | `customPolicyTypes.<type>` collides with a built-in `type` (dead — the built-in always wins). |
| Warning | A policy rule's `type` matches neither a built-in type nor a `customPolicyTypes` entry (it will never be evaluated). |

## `inject.rules`/`inject.minVerificationOptions`

| Key | Meaning |
|---|---|
| `inject.rules` | A list of ordinary [DML rule](/guides/enforcing-dml-rules/) entries (`{type, ...properties}`, the same shape a contract's own `rules:` uses) merged into every governed contract's `rules` before verification runs. A rule the contract already declares isn't duplicated. |
| `inject.minVerificationOptions` | A map of `VerificationOptions` flag name (`rejectUndeclaredInputs`, `rejectUndeclaredFields`, `computeFingerprint`) to `true` — ORed onto a job's own options. A flag a job left `false` can be forced `true` by policy; the reverse never happens. An unrecognized key (e.g. a typo) is rejected — `ContractEnforcementRule` fails loudly rather than silently ignoring it. |

## Exemptions

| Key | Required | Meaning |
|---|---|---|
| `contractId` | yes | The `Contract.id` this exemption covers. |
| `policyIds` | yes | Which policy rule `id`s (at least one) this exemption suppresses, for this `contractId` only. |
| `reason` | yes | Why the exemption exists — required, for auditability. |
| `reviewBy` | no | An ISO-8601 date (`YYYY-MM-DD`). Once passed, the exemption stops applying and the violation it was suppressing re-surfaces. Omitted means it never expires. |

<Aside type="tip" title="Exemptions live in the policy file, not the contract">
A contract's own author can't grant themselves an exemption — that would defeat the
purpose of an organization-wide rule. Only whoever owns the policy document can.
</Aside>

## Enforce mode vs. warn mode

| `mode` | Blocks a write? | Published event |
|---|---|---|
| `enforce` (default) | Yes — throws before any plan is analyzed | A `FAILED`-status `ContractValidationEvent`, if a sink is configured |
| `warn` | Never | A `PASSED`-status `ContractValidationEvent` still carrying the violation, if a sink is configured |

## Attaching a policy

| Mechanism | How |
|---|---|
| `spark-submit --conf` | `--conf spark.invaract.orgPolicy=/path/to/org-policy.yaml` — attachable to any job that already installs `ContractEnforcementRule.forContract`, with no change to that job's source. |
| Standalone lint | `sbt "contract/runMain com.invaract.contract.cli.OrgPolicyLintCli org-policy.yaml contracts/"` — no Spark involved, for a contracts repository's own CI/pre-commit gate. |

### Standalone lint: exit codes and flags

| Exit code | Meaning |
|---|---|
| `0` | Every discovered contract satisfies every `enforce`-mode rule, in every layer. A `warn` violation still prints but never fails the run. |
| `1` | The base policy or any overlay is invalid, a contract fails to parse, or no contract files were found. |
| `2` | Usage error — too few arguments, a malformed `--warn-expiring-within-days` value, or `--overlays` with no value. |

| Flag | Meaning |
|---|---|
| `--warn-expiring-within-days N` | Reports any exemption (in any layer) whose `reviewBy` falls within the next `N` days — before it lapses, not after. Defaults to `30`; never affects the exit code, since the exemption is still fully in force. |
| `--overlays overlay1.yaml,overlay2.yaml` | Lints against the full [layered stack](#policy-layering) a governed job would actually run under, not just the base — see below. |

See [Enforce an Organizational Policy](/guides/enforcing-organizational-policy/) for both,
worked through in full, and [Violation Types](/reference/violation-types/) for
`ORG_POLICY_VIOLATION`.

## Policy layering

A stricter business-unit (or team) policy can compose with a looser org-wide baseline,
without the business unit's document duplicating or replacing anything the org-wide one
already declares. An overlay is not a different document shape — it's an ordinary
`OrgPolicy` YAML document, in every respect identical to the base, layered on top of it.

```
spark-submit \
  --conf spark.invaract.orgPolicy=/policies/org-wide.yaml \
  --conf spark.invaract.orgPolicyOverlays=/policies/bu-finance.yaml,/policies/team-payments.yaml \
  ...
```

| Key | Meaning |
|---|---|
| `spark.invaract.orgPolicy` | The org-wide base layer — unchanged from the single-document case above. |
| `spark.invaract.orgPolicyOverlays` | Optional, comma-separated, ordered list of additional `OrgPolicy` documents layered on top of the base. Requires `spark.invaract.orgPolicy` to also be set — an overlay with no base is rejected rather than silently treated as one. |

Each layer is evaluated independently and the violations are unioned, so a stack of
layers is always *at least as strict* as any one layer alone:

- **A layer can only add, never loosen.** There is no mechanism for an overlay to
  override, replace, or loosen a rule an earlier layer declares. A business unit
  wanting a stricter version of a check the org-wide layer already has (e.g. tightening
  `warn` to `enforce`) adds its own additional rule of that type — both rules are then
  evaluated and unioned, the same as any other pair of rules.
- **A layer's exemptions cover only that layer's own policies.** An overlay's
  `exemptions` can grant an exception to a rule *that same overlay* declares, but it is
  structurally incapable of exempting a rule the org-wide layer (or any other layer)
  declares — `OrgPolicyValidator` rejects an exemption naming a policy id its own
  document doesn't declare, and each layer's exemptions are only ever checked against
  that layer's own policies. Only the document that owns a rule can grant an exemption
  for it.
- **Custom policy types stay per-layer.** Each layer resolves its own `customPolicyTypes`
  against only its own map, so two layers can independently use the same `type:` name
  for unrelated `CustomPolicyEvaluator` classes without colliding.

<Aside type="tip" title="A policy id repeated across layers is a Warning, not a problem">
Each layer evaluates independently, so a repeated `id` across layers doesn't cause
shadowing or misattributed exemptions. It's still worth avoiding, though — a human
reading two violations both attributed to `catalog-required` can't tell which layer
produced which. Prefix a layer's own rule ids (e.g. `bu-finance-catalog-required`)
rather than relying on `id` alone to distinguish them.
</Aside>

### Linting a layered stack

```
sbt "contract/runMain com.invaract.contract.cli.OrgPolicyLintCli --overlays bu-finance.yaml,team-payments.yaml org-policy.yaml contracts/"
```

The same base-first, comma-separated convention as the conf key — useful for a business
unit's own CI to lint its contracts against org-wide + its own overlay, with the same
argument shape `spark-submit` would take. Every policy document (base and overlays
alike) is excluded from the contract sweep, the same as the single-document case.
