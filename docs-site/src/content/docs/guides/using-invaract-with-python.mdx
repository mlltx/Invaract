This guide makes a plain Python job (one that reads and writes files with pandas, Polars, DuckDB or pyarrow, with no
Spark or Beam underneath) keep to a data contract. The job reads and writes through the `invaract` package by the names
its contract gives; every read and write is checked as it happens, and the job's outputs are published together, only
if the whole run passed. The contract is the same YAML you [write for Spark](/guides/writing-a-contract/).

<Aside type="caution" title="What this does and does not check">
Invaract checks what a Python job reads and writes: which datasets, where, in which format and save mode, and with which
columns and types (including that a required column holds no empty value). It cannot read what your own Python code
does between a read and a write, so the transformation-shape rules (`required_filter_columns`, `required_join_columns`,
`required_group_by`, `forbid_cross_join`), custom rules, static data-quality proofs and role consistency are refused
with `UNSUPPORTED_CONTRACT_FEATURE` rather than checked. It reads and writes **files** (Parquet, CSV, JSON lines, ORC,
Avro, Feather and Excel) on local and mounted file systems, HDFS and object storage, **Delta Lake and Iceberg tables**, and **PostgreSQL and SQLite tables** (see
[Files, tables and object storage](#files-tables-and-object-storage)). The full
list, in plain words, is in [What Each Engine Checks](/reference/what-each-engine-checks/).
</Aside>

## How it works

Unlike Spark and Beam, where Invaract is attached from the command line, a Python job adopts Invaract once, in its code:
each read and write that named a path names the dataset instead, and the contract says where it is. The change is the
same for every job, and small:

```python
orders = pd.read_parquet("data/in/orders")          # before
orders = invaract.read("orders")                     # after

report.to_parquet("data/out/report/part-0.parquet")  # before
invaract.write(report, "report")                     # after
```

When the job starts, the package starts Invaract's checker, the same verification code the other engines use, and
describes each read and write to it: the dataset's name, its columns, their types and how many empty values each holds.
It never sends the data itself. Each write is checked before it is written, and written to a staging folder beside its
location. When the job returns, every staged output is published (moved into place); if anything was refused, nothing
is. So a run that breaks its contract leaves the outputs exactly as they were before it started.

After that one change, a platform configures the job from outside it, with `INVARACT_*` environment variables: which
contract, where events go, which policy applies (see [The settings](#the-settings)).

## Install the package

```bash
pip install "invaract[pandas]"      # or invaract[polars], or plain invaract for pyarrow alone
```

Add `delta`, `iceberg`, `postgres` or `sqlite` for Delta Lake, Iceberg, PostgreSQL or SQLite tables, and `avro` or `excel` for Avro files
or Excel workbooks: `pip install "invaract[pandas,delta]"`.

It needs Python 3.10 or later and pyarrow 15 or later (installed with it); for pandas, 2.2 or later, and for Polars, 1.0
or later.

The checker comes with the package. On **Linux** (x86_64 and aarch64) with glibc 2.34 or later (Ubuntu 22.04, Debian 12,
RHEL 9 and later) and on **macOS 11 or later** (Apple silicon and Intel), pip installs a wheel that carries the checker as
a native program: nothing else is needed. On any other platform it installs a wheel that carries the checker as a Java
program, so **Java 11 or later** must be installed there (`JAVA_HOME`, or `java` on the `PATH`). Set `INVARACT_CHECKER` to run a checker of your own instead (see
[Python-only settings](/reference/configuration/#python-only-settings)).

## Adopt it in a job

<Steps>

1. Write the contract: every input the job reads and every output it writes, with its location, format, save mode and
   columns. This is the contract of the example job in the repository (`pythonio-adapter/python/examples/orders_job`),
   which reads orders and customers and writes a revenue report and an audit list:

   ```yaml
   id: orders_report
   version: "1.0.0"
   inputs:
     - name: orders
       location: data/in/orders
       format: parquet
       schema:
         fields:
           - { name: order_id,    type: long,   required: true }
           - { name: customer_id, type: long,   required: true }
           - { name: amount,      type: long,   required: true }
           - { name: status,      type: string, required: true }
     - name: customers
       location: data/in/customers.csv
       format: csv
       schema:
         fields:
           - { name: customer_id, type: long,   required: true }
           - { name: region,      type: string, required: true }
   outputs:
     - name: report
       type: DATA_ASSET
       location: data/out/report
       format: parquet
       saveMode: overwrite
       derivedFrom: [orders, customers]
       schema:
         fields:
           - { name: region, type: string, required: true }
           - { name: total,  type: long,   required: true }
     - name: audit
       type: DATA_ASSET
       location: data/out/audit
       format: parquet
       saveMode: overwrite
       derivedFrom: [orders]
       schema:
         fields:
           - { name: order_id, type: long,   required: true }
           - { name: status,   type: string }
   ```

   No contract yet? Start with a [dry run](#start-from-a-job-with-no-contract), which writes one for you.

2. Mark the job's entry point with `@invaract.job`, naming the contract. Everything the function reads and writes is one
   run:

   ```python
   import invaract

   @invaract.job("contract.yaml")
   def main():
       paid = load.paid_orders()
       build.audit(paid)
       invaract.write(build.report(paid, load.customers()), "report")
   ```

   A script with no entry-point function uses `with invaract.run("contract.yaml"):` around its body instead.

3. Replace each read and write with the dataset's name. `invaract.read(name)` returns a pandas DataFrame; pass
   `as_="polars"`, `"polars-lazy"` or `"arrow"` for another kind. Only the columns the contract lists are read, and a CSV
   input's columns are read as the contract's types. `invaract.write(frame, name)` takes a pandas, Polars or DuckDB
   frame, a Polars LazyFrame, or a pyarrow Table or RecordBatchReader. A pandas frame is written as the contract declares
   it wherever that changes no value (see [pandas frames](#pandas-frames)). The
   decorators `@invaract.reads(...)` and `@invaract.writes(...)` do the same for a function's arguments and its result:

   ```python
   def paid_orders():
       orders = invaract.read("orders")       # was pd.read_parquet("data/in/orders")
       return orders[orders["status"] == "paid"]

   @invaract.reads("customers")               # was pd.read_csv("data/in/customers.csv")
   def customers(customers):
       return customers

   @invaract.writes("audit")                  # was audit.to_parquet("data/out/audit/part-0.parquet")
   def audit(paid):
       return paid[["order_id", "status"]]
   ```

   Nothing else in the job changes: the transformations between the reads and the writes stay as they are.

4. Check that nothing still reads or writes around the package, with [`invaract-lint`](#find-reads-and-writes-around-the-package).

</Steps>

Run the job as before (`python main.py`). It reads, writes and exits with status 0, and both outputs are published, each
as one file named after the run: `data/out/report/part-de1def6d403e493d-00001.parquet` and
`data/out/audit/part-de1def6d403e493d-00001.parquet`.

## A job that breaks its contract

If the report's `total` is no longer what the contract declares (here the contract was changed to say `string`), the
write of the report is refused, the job stops with exit status 1, and neither output is published, the audit included.
After Python's traceback, the reason:

```text
invaract.errors.ContractViolation: Contract violation: 'orders_report@1.0.0' rejected this transformation. Write aborted.

What the contract expects:
  input  'orders' at data/in/orders: order_id: long, customer_id: long, amount: long, status: string
  input  'customers' at data/in/customers.csv: customer_id: long, region: string
  output 'report' at data/out/report (derived from orders, customers): region: string, total: string
  output 'audit' at data/out/audit (derived from orders): order_id: long, status: string (optional)

What the plan contains:
  Write(data/out/report, format=parquet, saveMode=overwrite)
  └─ UnknownPlan(the job's own Python code)
     ├─ Read(data/in/orders)
     └─ Read(data/in/customers.csv)

Why it violates the contract (1 violation):
  1. [OUTPUT_FIELD_TYPE_MISMATCH] field 'total' declares type 'string' but the actual OUTPUT schema has type 'long'

How to correct it:
  1. Cast 'total' to 'string' in the transformation, or update the contract to declare 'long' if the new type is intentional.
```

"The job's own Python code" stands for everything between the reads and the write, which Invaract does not look into.
The exception is `invaract.ContractViolation`, and the exit status 1 lets a scheduler tell a refused run from a crash.
If the check could not be made at all (no checker for the platform, a contract that cannot be read, a format the package
cannot write), the exception is `invaract.CheckNotRun`, the exit status is 2, and nothing is published either.

## pandas frames

pandas cannot hold some of the types a contract declares: an integer column with a missing value is `float64`, a date is
a `datetime64` at midnight, a decimal is an `object` column of `Decimal` values of whatever precision they happen to have,
and a column with no values has no type. So Invaract writes each column of a pandas frame as the type the contract
declares for it, **when no value changes**:

| pandas holds | the contract declares | written as declared when |
|---|---|---|
| `float64` (integers with a missing value) | `long`, `integer`, `short`, `byte` | every value is a whole number that fits |
| `int64` | `integer`, `short`, `byte` | every value fits |
| `int64`, `float32` | `double`, `float` | every value is exact in it |
| `datetime64` | `date` | every value is at midnight |
| a time zone other than UTC | `timestamp` | always: the same moments, in UTC |
| `Decimal` values, `float64`, `int64` | `decimal(p,s)` | every value fits `p` and `s` exactly (a float, as the nearest float to a decimal: `19.99`, not `0.1 + 0.2`) |
| `category` | the type of its values | as for those values |
| lists, dicts (`object`) | `array<...>`, `map<...>`, `struct<...>` | every value converts back unchanged (a list of whole numbers held as floats beside a missing one, `[1.0, NaN]`, is written as `array<long>`) |
| no values at all (a column of `None`, an empty frame) | any type | always |
| a sparse column | its values' type | always: it is written as its values |

Otherwise the column is written as pandas holds it, and the write is refused as a type mismatch, as it would be anyway.
Values of another kind are never converted (numbers and text, true/false and numbers), and a time zone is never added or
dropped: datetimes without a zone are not a moment in UTC until the job says so.

**Index keys are columns.** A named index level the contract declares as a column is written as that column, so a
`groupby` result is written with its keys, without `reset_index()`. Any other index is pandas' bookkeeping and is not
written. In a [dry run](#start-from-a-job-with-no-contract), with no contract yet, every named index level is written, as
pandas' own `to_parquet` writes it, so the draft declares the keys the job wrote before.

This job counts orders a day per region; `day` is a `datetime64`, `revenue` a `float64` sum, and both keys are in the
index:

```python
orders["day"] = orders["ordered_at"].dt.normalize()
daily = orders.groupby(["day", "region"]).agg(
    orders=("amount", "size"), revenue=("amount", "sum"), first_at=("ordered_at", "min"))
invaract.write(daily, "daily")
```

Against a contract declaring `day: date`, `region: string`, `orders: long`, `revenue: decimal(12,2)` and
`first_at: timestamp`, the write is refused, and the explanation ends with what pandas has to do with it:

```
Why it violates the contract (1 violation):
  1. [OUTPUT_FIELD_TYPE_MISMATCH] field 'first_at' declares type 'timestamp' but the actual OUTPUT schema has type 'timestamp_ntz'

How to correct it:
  1. Cast 'first_at' to 'timestamp' in the transformation, or update the contract to declare 'timestamp_ntz' if the new type is intentional.

In pandas:
  - 'first_at' (datetime64[us] in pandas) is not written as timestamp: its datetimes have no time zone, and the contract's type is a moment in UTC: say which zone they are in, for example df['first_at'].dt.tz_localize('UTC'), or declare the field timestamp_ntz
```

With `daily["first_at"] = daily["first_at"].dt.tz_localize("UTC")` before the write, it passes, and the file written has
the contract's types: `day: date32`, `region: string`, `orders: int64`, `revenue: decimal128(12, 2)`,
`first_at: timestamp[us, tz=UTC]`.

Some frames cannot be a table at all, and the write raises a `TypeError` saying which column and why, before anything is
checked or staged: a column pandas holds as `object` with values of more than one kind (text and numbers), two columns
with one name, and columns with more than one level of names (a `MultiIndex`; flatten them first).

Other notes a refusal can carry: a required column holding missing values (pandas' `NaN`, `None`, `NaT` and `pd.NA` all
count) says how to fill or drop them; a `period` column says to convert it with `.dt.to_timestamp()`; a `timedelta`
column, which no contract type holds (`interval` is a calendar interval of months, days and time), says to store it as a
number, for example `.dt.total_seconds()`.

**Checking a frame without writing it.** `invaract.check(frame, name)` judges a frame exactly as `invaract.write` would,
against the contract's output `name`, and writes nothing: for a notebook, or the job's own tests. It raises the same
`ContractViolation`, with the same pandas notes, and returns `None` when the frame would pass. It is a question about one
frame, not a run: the job's reads do not matter, it publishes no events, and inside a run it uses the run's contract
without counting as one of its writes. Outside a run, name the contract with `contract=` or `INVARACT_CONTRACT`.

```python
def test_the_report_keeps_its_contract():
    invaract.check(build_report(sample_orders()), "report", contract="contract.yaml")
```

For a frame with a missing `region` and a `total` of `20.5`, against `region: string` (required) and `total: long`
(required), it raises (real output, the end of the explanation):

```
Why it violates the contract (1 violation):
  1. [OUTPUT_FIELD_TYPE_MISMATCH] field 'total' declares type 'long' but the actual OUTPUT schema has type 'double'

How to correct it:
  1. Cast 'total' to 'long' in the transformation, or update the contract to declare 'double' if the new type is intentional.

In pandas:
  - 'region' holds 1 missing value(s) (NaN, None, NaT or pd.NA in pandas), and the contract requires a value in every row: fill them (df['region'].fillna(...)) or drop those rows (df.dropna(subset=['region']))
  - 'total' (float64 in pandas) is not written as long: 20.5 is not a whole number, or is out of range (a whole-number column with missing values is float64 in pandas, and is written as an integer as it is); round it in the job if that is intended
```

**Reading.** `invaract.read(name)` returns pandas' default dtypes, in which an integer column with a missing value is
`float64`; written back, it is written as the integer the contract declares. To keep it an integer in the job, pass
`dtype_backend`, as pandas' own readers take it: `"numpy_nullable"` gives `Int64`, `boolean` and `string` columns,
`"pyarrow"` gives `ArrowDtype` columns. `@invaract.reads(..., dtype_backend=...)` takes it too.

**Reading in chunks.** For an input larger than memory, `invaract.read(name, chunksize=100_000)` returns the input as
frames of that many rows each, one at a time, as pandas' `read_csv(chunksize=...)` does (the last one shorter), for any
input: files, Delta, Iceberg, PostgreSQL and SQLite tables. The checker is told the input's missing values before any chunk is
handed over, so the input is read twice: once to count them, once for the chunks; neither holds it whole. Writing in
chunks needs nothing new: each `invaract.write` of the same output in one run adds to what is staged.

```python
with invaract.run("contract.yaml"):
    for chunk in invaract.read("orders", chunksize=100_000):
        invaract.write(summarise(chunk), "report")
```

Frames of other libraries (Polars, DuckDB, pyarrow) hold the declared types themselves, so they are written as they are:
a Polars `Float64` column against a `long` declaration is refused.

## Start from a job with no contract

Dry-run mode writes the contract for you. Replace each read and write, keeping its path as `location=`, and run the job
with `INVARACT_DRY_RUN=true`: it reads and writes exactly where it did before, nothing is refused, and a draft contract is
inferred from what it actually read and wrote.

```python
@invaract.job()
def main():
    orders = invaract.read("orders", location="data/in/orders")
    customers = invaract.read("customers", location="data/in/customers.csv")
    paid = orders[orders["status"] == "paid"]
    invaract.write(paid[["order_id", "status"]], "audit", location="data/out/audit")
    report = paid.merge(customers, on="customer_id").groupby("region", as_index=False).agg(total=("amount", "sum"))
    invaract.write(report, "report", location="data/out/report")
```

```bash
INVARACT_DRY_RUN=true INVARACT_NOTIFY_CONFIG=notify.properties python job.py
```

With a [notification sink](/guides/notification-sinks/) configured, each write's draft is published as a
`CONTRACT_INFERENCE` event, and when the job returns one `DRY_RUN_SUMMARY` event merges them into one contract. For the
job above, its `mergedContractYaml` begins (real output; the columns of each dataset follow in the same form):

```yaml
id: job___main__.main
version: 0.1.0
status: draft
inputs:
- name: orders
  location: data/in/orders
  format: parquet
  schema:
    fields:
    - name: order_id
      type: long
      required: true
      nullable: false
```

A pandas frame is written in a dry run as pandas' own `to_parquet` writes it: every named index level is a column, so a
`groupby` result keeps its keys. A column of `Decimal` values, whose precision pandas does not know, is written with the
widest precision (38) at the scale its values have, rather than the narrowest one run's values needed, so the draft
declares `decimal(38,2)`, not `decimal(3,2)`; narrow it if the data has a known precision. pandas holds an integer column
with a missing value as `float64` and a date as a `datetime64`, so the draft declares them `double` and `timestamp_ntz`:
change them to the integer type and `date` they are (writes are then held to those, as [pandas frames](#pandas-frames)
says), or give the columns pandas' `Int64` dtype before the dry run.

Review the draft before you commit it. Its id is the job's entry point; give it a real one. Each output's `derivedFrom`
lists every input read before that output was written (here the audit is listed as derived from the customers too,
because they were read first): keep only the inputs it really comes from. Then commit the contract, name it in
`@invaract.job` (or with `INVARACT_CONTRACT`), and remove the `location=` arguments. The draft declares the format each
input was read in, so the contract holds later reads to it. With a contract in force, a `location=` or `format=` that
disagrees with it is refused, a `format=` before anything is read. See [Dry-run mode](/guides/dry-run-mode/) for more on turning a draft into
a contract.

## Find reads and writes around the package

The package checks every read and write that goes through it. One that does not (a `pd.read_csv` left behind, a
`to_parquet` added later) is not checked. `invaract-lint` finds them before the job runs:

```bash
pip install invaract-lint
invaract-lint jobs/
```

On the example job as it was before it adopted Invaract, it finds every read and write:

```text
jobs/orders/build.py:2:5: IVR002 `paid[['order_id', 'status']].to_parquet` writes data outside invaract: write it with invaract.write(<frame>, <name>), or mark the line `# invaract: allow`
jobs/orders/load.py:4:14: IVR001 `pd.read_parquet` reads data outside invaract: read it with invaract.read(<name>), or mark the line `# invaract: allow`
jobs/orders/load.py:8:12: IVR001 `pd.read_csv` reads data outside invaract: read it with invaract.read(<name>), or mark the line `# invaract: allow`
jobs/orders/main.py:8:5: IVR002 `paid.merge(load.customers(), on='customer_id').to_parquet` writes data outside invaract: write it with invaract.write(<frame>, <name>), or mark the line `# invaract: allow`
4 read(s) or write(s) outside invaract
```

It exits 0 when it finds nothing, 1 when it finds something, and 2 when a file cannot be parsed, so it can gate a CI
build or a pre-commit hook. It flags reads (`IVR001`) and writes (`IVR002`) through pandas, Polars, pyarrow and DuckDB,
database and storage connections (`IVR003`), and SQL that reads or writes files (`IVR004`), matching each call by the
name it resolves to through the file's imports, so an alias is no way around it. A call kept on purpose is marked on its
line, ideally with the reason:

```python
lookup = pd.read_csv("lookup/regions.csv")  # invaract: allow - a table shipped with the job, not a dataset
```

`invaract-lint --format github jobs/` prints each finding as an annotation on the pull request's diff.

## The settings

Every Invaract setting is an environment variable of the job, spelled `INVARACT_<SETTING>` (a switch is
`INVARACT_DRY_RUN=true`), so a platform can set them for a job it does not own:

| Variable | What it does |
|---|---|
| `INVARACT_CONTRACT` | The contract to enforce: a file path, or `registry://<id>@<version>` ([Use a Contract Registry](/guides/using-a-contract-registry/)). Overrides the one `@invaract.job` names. |
| `INVARACT_DRY_RUN=true` | Infer a contract from the job's writes instead of enforcing one ([above](#start-from-a-job-with-no-contract)). |
| `INVARACT_NOTIFY_CONFIG` | Where validation events go ([Notification Sinks](/guides/notification-sinks/)). |
| `INVARACT_LOCATION_MAP` | How `ref://` locations resolve ([Resolve Dataset Locations](/guides/resolving-dataset-locations/)). |
| `INVARACT_ORG_POLICY`, `INVARACT_ORG_POLICY_OVERLAYS` | Organizational policy layered on the contract ([Enforce Organizational Policy](/guides/enforcing-organizational-policy/)). |
| `INVARACT_REJECT_UNDECLARED_FIELDS=true` | Refuse an output column the contract does not declare. |
| `INVARACT_RUNTIME_DATA_QUALITY=true` | Check every row the job writes against its outputs' declared value constraints, before anything is published ([Check Data Values at Run Time](/guides/checking-data-values-at-run-time/)). |
| `INVARACT_REGISTRY_URL`, `INVARACT_REGISTRY_CLIENT_CLASS` | The contract registry. |
| `INVARACT_CHECKER` | The command that runs the checker, instead of the one the package carries. |

A read of an input the contract does not declare is always refused, since every read names the input it reads. Every
setting, with its spelling on the other engines, is in [Configuration Settings](/reference/configuration/).

## Formats, save modes and locations

- **Formats**: for reading and writing, files in `parquet`, `csv`, `json`, `orc`, `avro`, `feather` and `excel`, and
  Delta Lake (`delta`), Iceberg (`iceberg`), PostgreSQL and SQLite tables (`jdbc`). A read or write uses the format the job
  names (`format=`), then the one the contract declares for the dataset, which a `format=` must agree with
  (`INPUT_FORMAT_MISMATCH` for a read, `OUTPUT_FORMAT_MISMATCH` for a write); otherwise the one the location's extension names (`.json`, `.jsonl`, `.orc`, `.avro`,
  `.feather`, `.xlsx`, `.csv`), `jdbc` for a `postgresql://` or `sqlite://` location, and Parquet for any other. See the
  [file formats](#file-formats) below.
- **CSV layout**: a CSV dataset is read and written with its contract's `csv:` options (delimiter, header, encoding,
  quote, escape, the text for a missing value, date formats); `invaract.read(..., csv={...})` and
  `invaract.write(..., csv={...})` give them for a job with no contract yet. See
  [Read and Write CSV as Declared](/guides/csv-options/).
- **Save modes**: `overwrite` replaces what is at the location, `append` adds to what is there, `error` refuses the write
  if the location already holds data, and `ignore` publishes nothing if it does. A write uses the save mode the contract
  declares, or `overwrite`.
- **Locations** of file outputs are folders on a local or mounted file system, on HDFS (`hdfs://`) or on object
  storage (`s3://`, `gs://`, `abfss://`). How they are published depends on which; see below.
- **Required columns**: a column the contract marks `required: true` must hold no empty value; the file or table written
  then states the column as not null.
- **Partitions**: an output whose contract marks fields `partitioned: true` is written partitioned by them, Hive-style
  (`region=north/`) or as the table's own partitions, and an `overwrite` replaces every partition or only those written, as
  its `partitionOverwriteMode` says. `invaract.write(..., partition_by=[...], partition_overwrite="dynamic")` says it in the
  job; a write laid out otherwise than the contract declares is refused. See [Partition Outputs](/guides/partitioning-outputs/).

### File formats

Each format has the name Spark gives it, so one contract means the same thing for a Python job and a Spark job:

| Format | What it is | Read and written |
|---|---|---|
| `parquet` | Parquet | with the types the files hold |
| `csv` | comma-separated text, or as the contract's `csv:` options say | as the contract types each column |
| `json` | JSON lines: one object per line, as Spark's `json` source writes | as the contract types each column; an empty value is left out of its line, dates are `yyyy-MM-dd`, timestamps ISO 8601, decimals numbers |
| `orc` | ORC | with the types the files hold (pyarrow has no ORC support on Windows) |
| `avro` | Avro, needs `invaract[avro]` | with the types the files hold: an optional column is a union with `null`; dates, timestamps and decimals are Avro's logical types; the record is named `topLevelRecord`, as Spark names it |
| `feather` | Arrow's own file format, which pandas' `to_feather` writes | with the types the files hold |
| `excel` | `.xlsx` workbooks, needs `invaract[excel]` | the first sheet, its first row naming the columns, as the contract types each column; a timestamp with a time zone is written in UTC, as a cell holds none, and a binary or nested column is refused |

Every format is written partitioned the same way, Hive-style (`region=north/`).

## Files, tables and object storage

How an output is published when the job returns depends on where it lives:

| Output | Staged during the run | Published when the job returns |
|---|---|---|
| Files, local or mounted file system | in a hidden folder beside the location | renamed into place: all at once |
| Files, HDFS (`hdfs://`, `viewfs://`) | in a hidden folder beside the location, on HDFS | renamed into place: all at once |
| Files, object storage (`s3://`, `gs://`, `az://`, `abfss://`) | on the job's local disk | copied into place, `_SUCCESS` written last (see below) |
| Delta Lake or Iceberg table, anywhere | uncommitted | one commit: all at once |
| PostgreSQL table | in a temporary table, in the run's own transaction | one transaction: all at once |
| SQLite table | in a database file of its own, on the job's local disk | one transaction: all at once |

In every case nothing is published unless the whole run passed, and a refused or failed run leaves the output as it was.

**Plain files on object storage** are published the way Spark and Hadoop publish them, because object storage has no
rename: first the old `_SUCCESS` marker is removed, then the run's files are uploaded, then (for `overwrite`) the old
files are deleted, and `_SUCCESS` is written last. A reader that waits for `_SUCCESS`, as Spark and most schedulers can,
sees a complete output. A reader that does not can see old and new files together for as long as the publish takes, and
a job that crashes part way through publishing leaves them so, without `_SUCCESS`. When readers must never see that, write
a Delta or Iceberg table instead. Deleting files on object storage leaves empty "folder" markers (`report/`), as
Hadoop's own S3 client does; readers ignore them.

**HDFS** goes through pyarrow's Hadoop file system, so the job needs Hadoop's client libraries (`libhdfs`, with
`HADOOP_HOME` and `CLASSPATH` set) where it runs, as any pyarrow access to HDFS does.

A location on any other kind of file system (`ftp://`, ...) is refused before anything is written (`CheckNotRun`).

### Tables

A Delta Lake or Iceberg output is written in **one commit, when the job returns**, and only if the whole run passed. Until
then no reader of the table sees anything of the run, and a refused or failed run leaves the table exactly as it was. If
the table does not exist yet, the run that passes creates it, with the contract's columns, in that same commit.

```yaml
outputs:
  - name: report
    type: DATA_ASSET
    location: s3://analytics/sales/report     # a Delta table: its path or URI
    format: delta
    saveMode: overwrite
    schema:
      fields:
        - { name: region, type: string, required: true }
        - { name: total,  type: long,   required: true }
  - name: audit
    type: DATA_ASSET
    location: lake.sales.audit                # an Iceberg table: <catalog>.<namespace>.<table>
    format: iceberg
    saveMode: append
```

- **Delta Lake** tables are named by their path: a local folder, or a URI on object storage (`s3://bucket/path`). An
  `overwrite` replaces the table's rows in the new commit; the files it replaced stay until the table is vacuumed, as with
  any Delta write.
- **Iceberg** tables are named `<catalog>.<namespace>.<table>`. The catalog is configured as pyiceberg configures any
  catalog, so a platform sets it from outside the job: environment variables such as
  `PYICEBERG_CATALOG__LAKE__TYPE=glue`, or a `.pyiceberg.yaml` file. A catalog type needs its own pyiceberg extra
  (`pip install "pyiceberg[glue]"`). The run creates a missing namespace, then the table. An Iceberg output is held in
  memory until the job returns, since pyiceberg writes a table's data in one piece.
- **Catalog registration**: an Iceberg table is registered in its catalog, so a contract's `catalog:` requirement is
  checked against it ([Require Catalog Registration](/guides/requiring-catalog-registration/)): the technology is
  `iceberg`, `catalogName` is the pyiceberg catalog's name, then the namespace and the table. A requirement the table does
  not meet refuses the read or write (`OUTPUT_CATALOG_MISMATCH`, `INPUT_CATALOG_MISMATCH`). Files and Delta tables are
  named by their path and registered in no catalog, so a contract that requires a registration refuses them
  (`MISSING_OUTPUT_CATALOG_REGISTRATION`):

  ```yaml
  - name: report
    location: lake.sales.report
    format: iceberg
    catalog: { required: true, technology: iceberg, catalogName: lake, namespace: [sales], table: report }
  ```
- **Credentials and endpoints** come from each service's usual sources; Invaract has no settings of its own for them:
  - **S3**: `AWS_*` environment variables, `~/.aws`, an instance role.
  - **Google Cloud Storage**: `GOOGLE_APPLICATION_CREDENTIALS`, or the machine's own Google credentials.
    `STORAGE_EMULATOR_HOST` points files at an emulator, as it does every Google client library.
  - **Azure**: a location is `az://<container>/<path>` with `AZURE_STORAGE_ACCOUNT_NAME` set, or
    `abfss://<container>@<account>.dfs.core.windows.net/<path>`. `AZURE_STORAGE_ACCOUNT_KEY` gives the account's key;
    without one, Azure's default credential is used (a managed identity, `AZURE_CLIENT_ID`/`AZURE_CLIENT_SECRET`/
    `AZURE_TENANT_ID`, the Azure CLI's login). These are the variables delta-rs reads too, so one set serves files and
    Delta tables. Azure needs pyarrow 16 or later.
  - **HDFS**: Hadoop's client libraries where the job runs (above).
- A Delta output anywhere but the local file system (object storage or HDFS) is staged on the job's local disk and
  uploaded when the job returns, just before its commit, so a refused run never writes to the store.
- An **Iceberg warehouse on Azure** is written `abfss://<container>@<account>.dfs.core.windows.net/<path>`, not `az://`, as
  pyiceberg names Azure; pyiceberg reaches it through `adlfs` (`pip install "pyiceberg[adlfs]"`), configured with its
  `adls.*` catalog properties.
- **Tested end to end** on every push, against S3 (moto), Google Cloud Storage (fake-gcs-server), Azure (Azurite) and a
  single-node HDFS cluster: plain files, partitioned outputs and Delta and Iceberg tables. The one combination not tested is a
  Delta table on Google Cloud Storage, which no emulator can serve.

### PostgreSQL tables

A PostgreSQL table is read and written through [ADBC](https://arrow.apache.org/adbc/)'s PostgreSQL driver
(`pip install "invaract[postgres]"`, which needs version 1.2 or later). Its location names the server, the database, and
the table, in its schema:

```yaml
outputs:
  - name: report
    type: DATA_ASSET
    location: postgresql://etl@db.internal:5432/sales/finance.report   # <table> alone is in the public schema
    format: jdbc
    saveMode: overwrite
    schema:
      fields:
        - { name: region, type: string, required: true }
        - { name: total,  type: long }
```

- **Credentials** never go in the location; one that holds a password is refused before anything is written
  (`CheckNotRun`). They come from where every PostgreSQL client finds them: `PGPASSWORD`, `PGUSER`, a `~/.pgpass` file,
  `PGSSLMODE`, and the rest of libpq's environment. A query string in the location (`?sslmode=require`) is passed on to
  the driver.
- **Writing**: each output has its own connection and transaction for the whole run. Its rows are copied into a
  temporary table that only that connection sees. When the job returns and the whole run passed, one transaction creates
  the table if it does not exist (with the staged columns, a `required: true` column as `NOT NULL`), empties it for an
  `overwrite` (`TRUNCATE`; readers wait for the transaction rather than see the table half replaced), inserts the staged
  rows, and commits. A refused or failed run rolls back, so the table is left exactly as it was, and a table that did not
  exist is not created. An existing table is kept as it is: its other columns, defaults, indexes and grants stay.
- **Save modes** are as for any output: `append` adds rows, `error` refuses a table that holds rows, `ignore` publishes
  nothing to one that does.
- **Reading**: an input reads the columns the contract lists (all of them when it lists none), each converted to the
  contract's type where it declares one, so a `numeric` column declared `decimal(10,2)` arrives as a decimal.
- **Catalog registration**: a PostgreSQL table is registered in the `jdbc` catalog, its `catalogName` the database, its
  namespace the schema, so a contract can require it
  ([Require Catalog Registration](/guides/requiring-catalog-registration/)):

  ```yaml
  catalog: { required: true, technology: jdbc, catalogName: sales, namespace: [finance], table: report }
  ```
- A PostgreSQL output is not written partitioned: a write with partition columns is refused (`CheckNotRun`).
- Schema and table names are plain identifiers (letters, digits, `_` and `$`, not starting with a digit); Invaract
  quotes them, so they are matched case-sensitively, as written.

### SQLite tables

A SQLite table is read and written through ADBC's SQLite driver (`pip install "invaract[sqlite]"`, which needs version
1.2 or later). Its location names the database file and the table, the way SQLAlchemy names a SQLite database:
`sqlite:///` and a path relative to the job's working directory, or `sqlite:////` and an absolute path, then `/` and the
table:

```yaml
outputs:
  - name: report
    type: DATA_ASSET
    location: sqlite:///data/shop.db/report   # sqlite:////var/lib/shop.db/report for an absolute path
    format: jdbc
    saveMode: overwrite
    schema:
      fields:
        - { name: region, type: string, required: true }
        - { name: total,  type: long }
```

- **Writing**: an output's rows are written to a database file of its own on the job's local disk, so the target
  database is neither locked nor changed during the run. When the job returns and the whole run passed, one transaction
  on the target creates the table if it does not exist (a `required: true` column `NOT NULL`), empties it for an
  `overwrite`, inserts the staged rows, and commits. A refused or failed run leaves the database exactly as it was, and
  does not create one that did not exist. An existing table keeps its other columns and defaults.
- **Types**: SQLite keeps each value as an integer, a real number, text or bytes, whatever its column says. Invaract
  writes a boolean as 0 or 1, and a date, a timestamp (ISO 8601, with `Z` for one with a time zone) and a decimal (exactly)
  as text. Reading converts each column the contract types back to that type; a timestamp written by another program
  without an offset is taken to be in UTC.
- **Reading** opens the database read-only, and reads the columns the contract lists (all of them when it lists none). A
  missing database or table is an error, and is not created.
- **Catalog registration**: a SQLite table is registered in the `jdbc` catalog, its `catalogName` the file's name
  without its extension, its namespace `main`:

  ```yaml
  catalog: { required: true, technology: jdbc, catalogName: shop, namespace: [main], table: report }
  ```
- A SQLite output is not written partitioned, and its table name is a plain identifier, as for PostgreSQL.
