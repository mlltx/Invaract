[Write a Contract](/guides/writing-a-contract/) walks through authoring one by hand,
field by field. If you don't have a contract yet and just want to see what your
transformation actually reads and writes, dry-run mode does that for you: run your job
with no contract at all, and Invaract prints one back — built from the job's real inputs
and outputs — that you can copy into a file, review, and use with
[the enforcement rule](/guides/installing-the-enforcement-rule/) from then on.

<Aside type="note" title="A starting point, not a finished contract">
Dry-run mode infers *structure* — locations, formats, save mode, field names/types/
nullability — never business rules. It has no way to know your MERGE must always match
on `customer_id`, or that a `DELETE` should never run unconditionally; add those by hand
once you have a contract to add them to. Every inferred field is also marked `required:
true`, since it genuinely was present in this run — review that against what you actually
intend before treating it as a finished document.
</Aside>

## Try it against the demo job

<Steps>

1. ### Run the demo with no contract supplied

   ```bash
   ./dev/dry-run
   ```

   This builds all 5 modules the same way `./dev/test` does, then runs `DemoJobHarness`
   with `--dry-run` and no contract argument at all.

2. ### Read the inferred contract

   The run prints something like:

   ```yaml
   Dry-run mode: no contract was supplied, so nothing was enforced.
   Inferred contract, from this run's actual inputs/outputs — copy it into a file, review it,
   and pass it as the contract argument to use the normal (enforced) mode:

   id: inferred_contract
   version: 0.1.0
   status: draft
   inputs:
   - name: input
     location: /home/user/.../demo/input/sample.csv
     schema:
       fields:
       - name: id
         type: integer
         required: true
         nullable: true
       - name: value
         type: integer
         required: true
         nullable: true
   outputs:
   - name: output
     location: /home/user/.../demo/output/dry_run_result.parquet
     format: parquet
     schema:
       fields:
       - name: id
         type: integer
         required: true
         nullable: true
       - name: value
         type: integer
         required: true
         nullable: true
       - name: value_squared
         type: integer
         required: true
         nullable: true
       - name: value_tier
         type: string
         required: true
         nullable: false
     saveMode: overwrite
     derivedFrom:
     - input
   ```

   `derivedFrom` names exactly the inputs this write was observed reading, so when you
   later merge several inferred drafts into one multi-output contract, each output keeps
   naming only the inputs that feed it (see
   [Map Outputs to Their Inputs](/guides/mapping-outputs-to-inputs/)). A write that read
   nothing gets `derivedFrom: []`. Inferred input names are positional per write
   (`input`, `input_1`, `input_2`, ...), so they mean different things in different
   drafts — [merge them with `MergeDraftsCli`](#merging-drafts-from-a-job-with-several-writes)
   rather than by hand.

   `location` is the absolute `file:`-scheme-stripped path Spark actually reported for this
   run (see [Contract Format](/reference/contract-format/)'s "Location matching") — replace
   it with a portable, relative path (`demo/input/sample.csv`) once you copy this into a real
   contract file. `value_tier` is inferred `nullable: false` because both branches of its
   `CASE WHEN` produce a non-null literal.

   Save that to a file (`id`, `version`, and `status` are placeholders — replace them once
   you know what this contract should really be called), and you have a real starting
   point for [Write a Contract](/guides/writing-a-contract/) to refine.

</Steps>

## Using it in your own job

Dry-run mode installs the same way as real enforcement — a `SparkSessionExtensions` check
rule, at session construction time — just with no contract to enforce. Attach it the same
way [installing the enforcement rule itself](/guides/installing-the-enforcement-rule/) does:

```bash
spark-submit \
  --conf spark.sql.extensions=com.invaract.sparkadapter.InvaractSparkSessionExtension \
  --conf spark.invaract.dryRun=true \
  --jars invaract-spark-adapter-0.10.0.jar \
  my-job.jar
```

`spark.invaract.contract` is ignored entirely in this mode — there's no job code here to
hand an inferred `Contract` to, so `InvaractSparkSessionExtension` logs it at `WARN`
instead, the same information printed below:

```
WARN InvaractSparkSessionExtension: Invaract dry-run mode (spark.invaract.dryRun=true):
inferred contract from this session's real inputs/outputs - copy it into a file, review
it, and set spark.invaract.contract to it to switch to enforced mode:
id: inferred_contract
...
```

## Report dry-run results to a sink, to roll Invaract out across many jobs

Logging a draft is enough for one job you're looking at. To onboard a fleet — collect
every job's inferred contract in one place, and learn how safe it is to turn enforcement on
for each — point dry-run mode at a [notification sink](/guides/notification-sinks/) by
adding `spark.invaract.notifyConfig`, exactly as for enforcement. Nothing in the job
changes:

```bash
spark-submit \
  --conf spark.sql.extensions=com.invaract.sparkadapter.InvaractSparkSessionExtension \
  --conf spark.invaract.dryRun=true \
  --conf spark.invaract.notifyConfig=/etc/invaract/dry-run.properties \
  --conf spark.invaract.jobId=orders_nightly \
  --conf spark.invaract.job.metadata.team=orders \
  --files /etc/invaract/dry-run.properties \
  --jars invaract-spark-adapter-0.10.0.jar \
  my-job.jar
```

With a sink configured, dry-run mode stops logging the draft and instead publishes two
kinds of event:

- **`CONTRACT_INFERENCE`**, one per write dry-run mode met — including the writes it
  *couldn't* infer a contract from, which plain logging never mentioned.
- **`DRY_RUN_SUMMARY`**, once, when the application ends — how many writes landed in each
  status, plus every draft from the run merged into one contract.

### The statuses

| `status` | Meaning | What to do with it |
|---|---|---|
| `INFERRED` | A contract was inferred and nothing about it is in doubt. | Candidate for your contract repository. |
| `INFERRED_DEGRADED` | A contract was inferred, but from a plan Invaract could only partly see: an unresolved `.checkpoint()`/cache boundary (inputs behind it are missing), a resolution that had to guess, or row-level DML (`MERGE`/`UPDATE`/`DELETE`, where the draft describes the target's current schema and the operation's own logic isn't inferred). `diagnostics` says which. | Review before trusting. |
| `SKIPPED_UNSUPPORTED` | A state-changing procedure `CALL`. Dry-run mode infers a contract from a write's output schema, and a procedure call has none. | Nothing to infer; enforcement would verify the resulting table state. |
| `SKIPPED_UNRECOGNIZED` | A command that may write data but that Invaract has no translation for. With a contract active, enforcement would **reject** it as an `UNVERIFIABLE_WRITE`. | **A blocker for turning enforcement on** for this job. |
| `INFERENCE_ERROR` | Inference itself threw. The job was unaffected. | Report it. |

A job that ran but wrote nothing Invaract recognizes reports `NO_WRITES_OBSERVED` in the
summary — the only place that outcome is visible, since there's no write to attach an
event to. Treat it as "not enough information", not as "safe".

### The self-check

Every inferred draft is verified against the very write it came from, under the options
enforcement would use (so your `spark.invaract.rejectUndeclaredFields` and friends count).
The event's `selfCheck` is `PASSED` when turning enforcement on with that contract would
not have blocked this write, and `FAILED` (with `selfCheckViolations`), `INVALID` or
`ERROR` otherwise. That is a better readiness signal than the count of successes: a draft
that doesn't pass its own write isn't something to promote.

### What's in an event

```json
{"eventType": "CONTRACT_INFERENCE", "status": "INFERRED", "selfCheck": "PASSED",
 "writeLocation": "s3a://lake/orders_daily", "contractYaml": "id: orders_nightly\n...",
 "fingerprints": {...}, "diagnostics": [],
 "job": {"jobId": "orders_nightly", "appName": "orders", "applicationId": "application_...",
         "sparkVersion": "3.5.1", "user": "etl", "attributes": {"team": "orders"}, ...}}
```

`job.jobId` comes from `spark.invaract.jobId` — set it. Spark's own app name is often
different on every run under a scheduler, so it can't tell you "this is the same job as
last night"; the `fingerprints` field identifies the transformation itself, which makes
repeat runs recognizable. Every `spark.invaract.job.metadata.<key>=<value>` conf entry
arrives as `job.attributes.<key>`; nothing else from your Spark configuration is sent.

The `DRY_RUN_SUMMARY`'s `mergedContractYaml` is the job's drafts merged exactly as
[`MergeDraftsCli`](#merging-drafts-from-a-job-with-several-writes) does, named for the job.
If two writes disagree about a location's schema, `mergeStatus` is `CONFLICT` and
`mergeConflicts` lists them; no contract is guessed at.

### Sending successes and problems to different places

Use the `FanOutNotificationSink` described in
[Configure a Notification Sink](/guides/notification-sinks/#send-events-to-more-than-one-place)
to send the clean drafts to your contract repository's endpoint and the rest to a
different one:

```properties
sink.enabled=true
sink.class=com.invaract.sparkadapter.notification.FanOutNotificationSink
sink.property.sinks=repository,triage
sink.property.repository.class=com.invaract.sparkadapter.notification.HttpNotificationSink
sink.property.repository.property.url=https://contracts.corp.internal/inferred
sink.property.repository.property.bearerTokenEnv=INVARACT_TOKEN
sink.property.repository.statuses=INFERRED
sink.property.triage.class=com.invaract.sparkadapter.notification.HttpNotificationSink
sink.property.triage.property.url=https://triage.corp.internal/invaract
sink.property.triage.statuses=INFERRED_DEGRADED,SKIPPED_UNSUPPORTED,SKIPPED_UNRECOGNIZED,INFERENCE_ERROR
```

The end-of-run summary always reaches every target, so each destination still learns that
the job ended.

<Aside type="note" title="Dry-run never gets in the job's way">
Inference, the self-check and publishing are each failure-isolated: a sink that is down or
a plan shape Invaract hasn't seen costs a log line, never a query. Delivery to an HTTP
endpoint is asynchronous, and at application end the sink is given up to ten seconds to
finish what it already accepted, so a short job doesn't lose its last events. Each
`SparkSession` a job creates reports on its own; a job that spawns child sessions sends one
summary per session.
</Aside>

## Need a custom callback?

Call `ContractEnforcementRule.dryRun` yourself when you want to do something with the
inferred contract besides logging it — write it to a specific file, publish it somewhere,
merge it with an existing draft. See [Install and Configure Invaract Explicitly in
Code](/guides/calling-invaract-explicitly/#infer-a-contract-with-a-custom-callback).

`ContractEnforcementRule.dryRun` never throws and never blocks a write, under either
mechanism — there's no contract to violate. It only calls its callback (or, in the
conf-driven path, logs) when the analyzed plan is a write Invaract recognizes (see
[Connector Support](/reference/connector-support/)); a `.count()`, a plain read, or an
unrecognized write shape produces nothing — unless a sink is configured, which also
reports the writes it couldn't infer from (see above). If your job performs more than one write, the
callback fires once per recognized write — capture the one you want by overwriting a
mutable cell, the same way [the explicit-code example](/guides/calling-invaract-explicitly/#infer-a-contract-with-a-custom-callback)
does.

## Merging drafts from a job with several writes

A job with several writes prints one draft per write. Save each draft to its own file
(a directory of them works too), then merge them into one multi-output contract with the
`contract` module's command line — no Spark involved:

```bash
cd contract
sbt "runMain com.invaract.contract.cli.MergeDraftsCli --id customer_pipeline --version 1.0.0 drafts/"
```

Given two drafts — one write reading `data/orders.csv`, another reading
`data/customers.csv` and `data/orders.csv` (as its `input` and `input_1`) — it prints:

```yaml
inputs:
- name: orders
  location: data/orders.csv
  ...
- name: customers
  location: data/customers.csv
  ...
outputs:
- name: orders_report
  location: out/orders_report.parquet
  ...
  derivedFrom:
  - orders
- name: customer_totals
  location: out/customer_totals.parquet
  ...
  derivedFrom:
  - orders
  - customers
```

What the merge does, and what it refuses to guess:

- **Inputs are one per location.** The same location read by several writes becomes one
  input, named after its location (`data/orders.csv` → `orders`; a catalog table
  `main.sales.orders` → `orders`; a clash gets `_2`, `_3`, ...). Each output's
  `derivedFrom` is rewritten to those names.
- **Conflicting schemas are an error, not a pick.** If two drafts saw the same location
  with different schemas (say, one was inferred before the source changed), the command
  prints every conflict, exits `1`, and writes nothing. Re-run the stale write and merge
  again.
- **Outputs stay distinct by location.** Two writes to one location merge only if they
  agree on its schema.
- **A write that read nothing** keeps `derivedFrom: []`.
- The merged contract is checked with the same validation as any contract file, and parses
  back with the normal parser. `--output merged.yaml` writes it to a file instead of
  standard output; `--id` defaults to `merged_contract`, `--version` to `0.1.0`.

From code, `ContractDraftMerger.merge(drafts, id, version)` does the same on parsed
`Contract`s and returns either the merged contract or the list of conflicts.

## Checkpoints

If your job calls `.checkpoint()` between reading and writing, dry-run mode sees through
it the same way real enforcement does (see `MISSING_INPUT` in
[Violation Types](/reference/violation-types/)): the inferred contract names the inputs read *before* the checkpoint, not an empty
list. The checkpointed Dataset has to have been created while the rule was installed — a
checkpoint made before the session had the extension can't be resolved, and its upstream
inputs won't appear in the draft.

## What it doesn't do

Dry-run mode only observes — it's the mirror image of
[`SparkAdapterListener`](/guides/installing-the-enforcement-rule/#reporting-on-a-write-not-just-gating-it),
not a replacement for real enforcement. Once you have a reviewed contract, switch back to
[`ContractEnforcementRule.forContract`](/guides/installing-the-enforcement-rule/) — that's
the mechanism that actually gates a write. Row-level DML (`MERGE`/`UPDATE`/`DELETE`) is
inferred only weakly: those operations have no single "new output" to build a dataset schema
from, so the draft describes the target's *current* schema and none of the operation's own
logic (see [Enforce Row-Level DML Rules](/guides/enforcing-dml-rules/) for how they're
verified once a contract exists). When [reporting to a sink](#report-dry-run-results-to-a-sink-to-roll-invaract-out-across-many-jobs),
such a draft is flagged `INFERRED_DEGRADED`.
