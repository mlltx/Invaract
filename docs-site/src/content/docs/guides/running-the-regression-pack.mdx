`ContractEnforcementRule` gates every Spark write against a contract before it executes: a
write that violates its contract is aborted, and no output is ever created. The
regression pack re-runs that guarantee as a script instead of a one-off manual check, with
real `spark-submit` invocations and real assertions — not mocks.

## Run it

<Tabs>
<TabItem label="Local Spark/sbt">

```bash
./dev/regression
```

Requires a working `./dev/test` environment (Codespaces already provides one).

</TabItem>
<TabItem label="Docker">

```bash
./dev/regression-docker
```

Builds a self-contained image and runs the same pack inside it — useful for verifying the
guarantee on a machine that hasn't set up JDK/sbt/Spark at all. Only Docker is required.

</TabItem>
</Tabs>

## What it checks

Six real cases, exiting non-zero if any behaves unexpectedly — schema-level
enforcement, then the same pass/fail proof for [static data-quality
verification](/guides/verifying-static-data-quality/) and for [input/output type
role-consistency](/guides/declaring-input-and-output-types/):

1. **Contract satisfied** (`demo/contracts/invaract_output.yaml`) — the job exits `0`,
   the report says `PASS`, and the output file exists.
2. **Contract violated** (`demo/contracts/invaract_output_broken_example.yaml`, which
   requires a `customer_name` column the demo transformation never produces) — the job
   exits non-zero, the report says `FAIL` with a `MISSING_OUTPUT_FIELD` violation, and —
   the core guarantee — **the output file is never created**.
3. **Data-quality constraint satisfied** (`demo/contracts/invaract_output_data_quality_pass.yaml`,
   declaring `value_tier` must be one of `[high, low]`) — the demo transformation's own
   `CASE WHEN value > 50 THEN 'high' ELSE 'low' END` provably satisfies that, so the job
   exits `0` and the published `ContractValidationEvent` carries a `Guaranteed` verdict
   for `value_tier`.
4. **Data-quality constraint violated** (`demo/contracts/invaract_output_data_quality_fail.yaml`,
   declaring `value_tier` must be `[high]` only) — the same transformation provably
   produces `'low'` on its `ELSE` branch, so the job exits non-zero, the report shows a
   `DATA_QUALITY_VIOLATION`, and the output file is never created.
5. **Declared type consistent with observed usage** (`demo/contracts/invaract_output_role_consistency_pass.yaml`,
   declaring the `orders` input `DATA_ASSET`) — `orders`' `value` column genuinely does
   derive `value_squared`/`value_tier` in the produced output, so the job exits `0` and
   the published `ContractValidationEvent` carries a `Conforms` verdict for `orders`.
6. **Declared type contradicted by observed usage** (`demo/contracts/invaract_output_role_consistency_fail.yaml`,
   declaring the same `orders` input `CONTROL`) — its data still reaches a produced
   output column, the exact high-confidence contradiction role-consistency checking
   exists to catch, so the job exits non-zero, the report shows a
   `ROLE_CONSISTENCY_VIOLATION`, and the output file is never created.

Cases 3/4 attach `spark.invaract.staticDataQuality=true` purely via `--conf`, the same
way a platform team would against a job whose source they don't own — see [Verify Static
Data Quality](/guides/verifying-static-data-quality/#enable-it). Cases 5/6 attach
`spark.invaract.roleConsistency=true` the identical way — see [Declaring Input and Output
Types](/guides/declaring-input-and-output-types/#enable-role-consistency-checking).

<Aside type="tip">
This same pack runs in CI on every push — directly, once per OS/Java combination in
`.github/workflows/test.yml`'s `test` job, and again inside a Docker image in the
`docker-regression` job — so the abort path is checked automatically on every change,
not just the happy path.
</Aside>

## Why this exists as a separate script

Unit tests can assert that `ContractEnforcementRule.verifyOrThrow` throws for a given
input, but that doesn't prove the *real* Spark write never happens end-to-end, via a real
`spark-submit` process, the way a production job would run. The regression pack closes
that gap: it's the same proof [Your First Contract](/getting-started/first-contract/)
walked through manually, automated and asserted on every run.
