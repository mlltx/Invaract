A CSV file says nothing about itself: a reader has to know that its values are separated by
semicolons, that its first line is data and not column names, that it is in Latin-1, that
`NA` means a missing value, and that `03/11/2026` is the 3rd of November. Get one of those
wrong and the job usually doesn't fail. It reads the wrong data: a file that is all one column,
a lost first row, mangled accents, `NA` as a word, dates that don't parse. A contract can
declare the layout, and every read and write of the dataset is then held to it.

<Aside type="note" title="Which engines check it">
Python jobs that read and write through the `invaract` package are checked, and the package
reads and writes with the declared options itself. Spark jobs are checked too: each CSV read
and write is held to the options it was given, with Spark's own default standing for any option
the job leaves unset (a streaming CSV sink is the exception; its options are not checked). Beam
Java and Beam Python jobs are checked where Beam's CSV transforms say what they use
([below](#what-beam-jobs-are-held-to)). See [What Each Engine Checks](/reference/what-each-engine-checks/).
</Aside>

## Declare the layout

Add a `csv:` block to the dataset. The option names, and what each one means, are Spark's own
CSV options, so one contract reads the same on every engine:

```yaml
inputs:
  - name: orders
    location: in/orders.csv
    format: csv
    csv: { delimiter: ";", header: false, encoding: ISO-8859-1, nullValue: NA, dateFormat: dd/MM/yyyy }
    schema:
      fields:
        - { name: id, type: long, required: true }
        - { name: city, type: string }
        - { name: day, type: date }
outputs:
  - name: report
    location: out/report
    format: csv
    csv: { delimiter: "|", header: true, dateFormat: dd/MM/yyyy, nullValue: "-" }
    schema:
      fields:
        - { name: id, type: long, required: true }
        - { name: city, type: string }
        - { name: day, type: date }
```

| Option | Meaning |
|---|---|
| `delimiter` | The character between values (`sep`, Spark's other name for it, is accepted too). `"\t"` is a tab. |
| `header` | Whether the first line names the columns (`true`) or is already data (`false`). Without a header, the columns are the contract's fields, in order. |
| `encoding` | The character set: `UTF-8`, `ISO-8859-1` (also `latin1`), `windows-1252`, ... |
| `quote` | The character values are quoted with. |
| `escape` | The character that escapes a quote inside a value. |
| `nullValue` | The text a missing value is written as, and read as: `NA`, `\N`, `-`. |
| `dateFormat`, `timestampFormat` | How dates and timestamps are written, as Java `DateTimeFormatter` patterns: `dd/MM/yyyy`, `yyyy-MM-dd'T'HH:mm:ss`. |

Only the options you declare are checked; one you leave out is the engine's own default. An
option the block doesn't know is a parse error, so a misspelt one fails loudly instead of
silently leaving the default in force. The validator also checks that a quote or escape is one
character, the encoding is a character set it knows, and each date pattern is valid.

## What Python jobs do with it

The `invaract` package reads and writes a CSV dataset with its declared options; the job does
nothing. Reading the input above (real output), `NA` is a missing value and the day is a date:

```python
>>> invaract.read("orders").to_dict("records")
[{'id': 1, 'city': 'Köln', 'day': datetime.date(2026, 11, 3)}, {'id': 2, 'city': nan, 'day': datetime.date(2026, 11, 4)}]
```

and writing it back as the report gives:

```
id|city|day
1|Köln|03/11/2026
2|-|04/11/2026
```

A job can give options itself with `csv=`, which a job with no contract yet uses to say how it
reads a file (see the dry-run section of [Use Invaract with Python](/guides/using-invaract-with-python/#start-from-a-job-with-no-contract);
the draft contract then declares them). Under a contract, options that disagree with the
declared ones are refused. Writing the report with commas instead of pipes:

```python
invaract.write(df, "report", csv={"delimiter": ","})
```

```
Why it violates the contract (1 violation):
  1. [OUTPUT_CSV_OPTIONS_MISMATCH] contract declares the output CSV options delimiter '|' but the write uses delimiter ','
```

The same goes for a read (`INPUT_CSV_OPTIONS_MISMATCH`), and nothing the run wrote is published.

Values are compared by meaning, not spelling: `"\t"` is a tab, `latin1` is `ISO-8859-1`, and
`TRUE` is `true`. A date or timestamp pattern can use years, months (also as names), days,
hours, minutes, seconds, AM/PM, weekday names and zone offsets, plus quoted text; fractions of a
second and week numbers can't be read or written by the Python package, which stops the run
(`CheckNotRun`) rather than misread them. A timestamp read without a zone in its pattern is taken
as UTC.

## What Spark jobs are held to

A Spark job sets its options itself, with `.option(...)` on the reader or writer or in a table's
`OPTIONS (...)`. Invaract compares them with the contract under the contract's names: Spark's
`sep` is `delimiter` and `charset` is `encoding`. An option the job leaves unset counts as Spark's
default, which is not always what you expect: Spark reads and writes **without** a header line
unless `header` is `true`. So this contract and job:

```yaml
outputs:
  - name: report
    location: out/report
    format: csv
    csv: { delimiter: ";", header: true }
```

```scala
df.write.mode("overwrite").option("sep", ";").csv("out/report")
```

are refused with `OUTPUT_CSV_OPTIONS_MISMATCH` before anything is written, because the job never
asked for a header line: *contract declares the output CSV options header true but the write uses
header false*.

Adding `.option("header", "true")` lets it through. A dry run's draft contract declares the options
the job set, and `header` always, since engines disagree on its default.

## What Beam jobs are held to

A Beam Java job writes CSV with `CsvIO.writeRows(...)` (or `CsvIO.write(...)`), and reads it with a
`TextIO.read()` whose lines go straight to `CsvIO.parseRows(...)` (or `CsvIO.parse(...)`). Both carry
a Commons CSV format, and Invaract holds what it says to the contract: the delimiter, the quote and
escape characters (none, if the format has none), the text a missing value is written as, and the
header. A write writes a header line unless its format skips the header record; a read has one when
its `TextIO.read()` skips a first line (`.withSkipHeaderLines(1)`). Text is UTF-8 both ways.

For an output declared `csv: { delimiter: ";", header: true }`, a job writing with
`CSVFormat.DEFAULT` (commas) is refused before the pipeline runs: *contract declares the output CSV
options delimiter ';' but the write uses delimiter ','*.

A Beam Python job reads and writes CSV with pandas, `beam.io.ReadFromCsv(...)` and
`beam.io.WriteToCsv(...)`, and Invaract holds pandas' options to the contract: `sep` (or `delimiter`),
the header (a read has one unless the job passes `names=` or `header=None`; a write writes one unless
`header=False`), `encoding`, `quotechar` (none with `quoting=csv.QUOTE_NONE`), `escapechar`, a write's
`na_rep`, and a read's missing-value text only when the job sets `keep_default_na=False` and one
`na_values`. pandas' default stands for each option the job leaves unset. Beam doesn't record these in
the pipeline it hands to its runner, so the `invaract_beam` runner reads them off the job's transforms
before the check. A `sep` pandas would guess (`sep=None`) or a regular expression is no delimiter, and
pandas' `date_format` is not the contract's pattern, so neither is held to the contract.

A plain `TextIO` read or write of CSV lines (`ReadFromText`, `WriteToText` in Python) is the job's own
code, and a CSV format has no date or timestamp pattern. So a read or write of a dataset that declares an option nothing in the pipeline
states (a `TextIO.write()` of lines the job joined itself, or a `dateFormat`) is refused as
unverifiable rather than let through unchecked; the refusal names the options.
