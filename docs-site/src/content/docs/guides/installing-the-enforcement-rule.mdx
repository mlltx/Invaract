This guide wires Invaract into a Spark job of your own. `ContractEnforcementRule` is a
`SparkSessionExtensions` check rule: it runs on the analyzed logical plan of every query
your session executes, and throws before Spark runs a query that violates the active
contract.

<Aside type="caution" title="Install it at session construction">
`SparkSessionExtensions` are configured when a `SparkSession` is built and can't be
changed afterward. Load your contract *before* building the session.
</Aside>

## Two ways to install it, depending on who's in control

### 1. Attached externally, via `spark-submit --conf` — no job code changes

`InvaractSparkSessionExtension` installs Invaract with **no code at all** in the job it's
attached to — the same way Delta Lake's own
`io.delta.sql.DeltaSparkSessionExtension` is attached, purely via `spark.sql.extensions`:

```bash
spark-submit \
  --class com.example.MyRealJob \
  --master yarn \
  --jars invaract-spark-adapter-0.3.0.jar \
  --conf spark.sql.extensions=com.invaract.sparkadapter.InvaractSparkSessionExtension \
  --conf spark.invaract.contract=/path/to/contract.yaml \
  my-real-job.jar
```

`MyRealJob`'s source never imports anything from `com.invaract.contract`/
`com.invaract.sparkadapter` — a platform team, an orchestration framework, or a CI
pipeline can attach contract enforcement to a job whose source they don't own at all.
This is what closes CLAUDE.md's "External Attachability Requirement" for the one
capability every other one sits on top of: installing Invaract itself.

Every other `spark.invaract.*` conf key documented elsewhere in these docs — the location
resolver, `computeFingerprint`/`rejectUndeclaredInputs`/`rejectUndeclaredFields`, a
notification sink — composes with this for free, since `InvaractSparkSessionExtension`
just calls the same `forContract` those are built into.

<Steps>

1. ### Dry-run mode, without a contract at all

   Set `spark.invaract.dryRun=true` instead of `spark.invaract.contract` to run
   [dry-run mode](/guides/dry-run-mode/) — no contract needed, nothing ever blocked. With
   no job code to hand an inferred contract to, it's logged at `WARN` instead:

   ```bash
   spark-submit \
     --conf spark.sql.extensions=com.invaract.sparkadapter.InvaractSparkSessionExtension \
     --conf spark.invaract.dryRun=true \
     ...
   ```

2. ### Publishing notification events too

   Add `spark.invaract.notifyConfig=<path>` — see
   [Configure a Notification Sink](/guides/notification-sinks/#1-attached-externally-via-spark-submit-conf--no-job-code-changes)
   for the full mechanism.

</Steps>

### 2. Called explicitly in code

Call `ContractEnforcementRule.forContract` yourself when you need something the
conf-driven path can't express — a contract loaded from somewhere `spark.invaract.contract`
can't name, a custom `LocationResolver`, or any other programmatic control:

<Steps>

1. ### Parse your contract

   ```scala
   import com.invaract.contract.ContractParser

   val contract = ContractParser.parseFile("contracts/my_contract.yaml")
   ```

2. ### Install the check rule when you build the session

   ```scala
   import com.invaract.sparkadapter.ContractEnforcementRule
   import org.apache.spark.sql.SparkSession

   val spark = SparkSession
     .builder()
     .appName("MyJob")
     .master("local[*]")
     .withExtensions(_.injectCheckRule(ContractEnforcementRule.forContract(contract)))
     .getOrCreate()
   ```

   From this point on, every write your job attempts is checked against `contract` before
   it executes. A violation throws `ContractViolationException` — before any output is
   created — with a human-readable explanation of what the contract expected, what the
   plan contained, and how to fix it (see
   [Your First Contract](/getting-started/first-contract/) for a real example of
   that message).

3. ### Run your job as usual

   Nothing else about how you write your transformation changes. If your job's actual
   write matches the contract, it proceeds exactly as it would without Invaract
   installed.

</Steps>

`runner/DemoJobHarness` — the example job this repository's own `./dev/test` runs — uses
this explicit-code path, since it exists to demonstrate `ContractEnforcementRule` and
`SparkAdapterListener` directly; see CLAUDE.md's "What's the product, and what's the test
harness."

## Handling a rejection

`ContractEnforcementRule.forContract` throws `ContractViolationException` from inside
Spark's query analysis, so it surfaces as an ordinary Scala exception around whatever
triggered the write (`.write.save(...)`, `.write.parquet(...)`, and so on):

```scala
import com.invaract.sparkadapter.ContractViolationException
import scala.util.{Failure, Success, Try}

Try {
  outputDf.write.mode("overwrite").parquet(outputPath)
} match {
  case Success(_) => // write succeeded and was verified
  case Failure(e: ContractViolationException) =>
    // e.getMessage is the full four-part explanation: what the contract
    // expects, what the plan contains, why it violates the contract, and
    // how to correct it.
    logger.error(e.getMessage)
    sys.exit(1)
  case Failure(other) => throw other
}
```

## Reporting on a write, not just gating it

`ContractEnforcementRule` only decides pass/fail — it doesn't hand you a structured
summary of the write it just verified. If you also want the translated plan and its
column-level lineage (for a report, a dashboard, or logging), register
`SparkAdapterListener` alongside it — it observes the same writes *after* they succeed:

```scala
import com.invaract.sparkadapter.SparkAdapterListener

val irListener = new SparkAdapterListener
spark.listenerManager.register(irListener)

// ... your write happens here, gated by ContractEnforcementRule ...

// QueryExecutionListener callbacks run asynchronously on Spark's own
// listener thread, so poll briefly if you need the result immediately
// after write() returns.
val result = irListener.lastWrite // Option[TranslationResult]
```

See [Verification vs. Enforcement](/concepts/verification-vs-enforcement/) for
why these are two separate mechanisms rather than one.

## Version compatibility warnings

Every time you build a `SparkSession` with `ContractEnforcementRule` installed (`forContract`
or [dry-run mode](/reference/dev-commands/)), it also checks the running Spark version — and,
if either is on the classpath, the running Delta Lake/Iceberg version — against this
project's own [verified-version list](/reference/spark-version-support/). Running an
unverified version doesn't block your job: verification proceeds normally, but a line like

```
WARN VersionCompatibilityGuard: Invaract is running against Spark 3.5.1, which is not in
this project's verified-version list (verified: 3.5.6, 3.5.7, 3.5.9). This is advisory
only - verification will continue normally - but Spark 3.5.1's compatibility with
Invaract has not been checked by this project's own CI. See
https://mlltx.github.io/Invaract/reference/spark-version-support/ for the current
verified-version list.
```

is logged so you have a concrete signal (not a raw stack trace, if something does go
wrong) that you're outside what's been tested. See
[Troubleshooting](/troubleshooting/common-problems/) for the two known failure modes this
warning would predict.

## What gets checked

Only a plan that translates to a recognized write is verified — everything else (reads,
`.count()`, intermediate transformations) is a silent no-op. See
[Connector Support](/reference/connector-support/) for which write shapes are
recognized today, and
[Fail-Closed by Default](/concepts/fail-closed/) for what happens when your job
writes via a shape Invaract doesn't recognize at all.
