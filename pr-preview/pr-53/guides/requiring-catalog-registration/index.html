Require Catalog Registration

A contract’s schema/format/saveMode all describe what a dataset looks like. None of them say anything about where downstream tools can find it — a job can write perfectly well-formed Parquet to a bare path that no catalog knows about at all, and nothing in the contract format could require otherwise. catalog: closes that gap: a dataset can declare that it must be registered in a real catalog — optionally pinning down exactly which one.

Declare it in your contract

Section titled “Declare it in your contract”

catalog: is entirely opt-in, per dataset — a dataset that omits it (like every contract before this feature existed) is checked exactly as it always was. required: true is the only mandatory key within a present catalog: block; every other sub-field is independently optional and only checked when you declare it:

KeyRequiredMeaning
requiredyesWhether this dataset must be registered in a catalog at all.
technologynoThe catalog implementation, e.g. hive, delta, iceberg. Open vocabulary, not a closed enum.
catalogNamenoThe Spark-level catalog plugin/session-catalog name, e.g. spark_catalog — a local alias, not necessarily unique across an organization.
locationnoThe catalog service’s own address — e.g. a Hive metastore’s thrift://host:port URI. See “What location can and can’t check” below.
namespacenoThe database/schema path within the catalog, as an ordered list, e.g. [default].
tablenoThe table name within that namespace.

Applies identically to inputs and outputs — the same Dataset type both share. An org that requires every job’s output to have a catalog entry, and separately requires every input it reads to already be catalog-registered too, declares both independently.

Only the sub-fields you declare are checked

Declaring technology: hive alone doesn’t require a specific table or catalogName — each sub-field is compared independently, the same way format/saveMode are only checked when a contract declares them. Pin down as much or as little as matters to you:

What happens on a mismatch

Section titled “What happens on a mismatch”

Two ways a required registration can fail: missing (no catalog entry exists at all) and mismatch (a real entry exists, but disagrees with a declared sub-field). A real example — a contract requiring Hive registration under one metastore, checked against a table actually registered under a different one:

The write is aborted before anything is committed — see Fail-Closed by Default. Input-side mirrors (MISSING_INPUT_CATALOG_REGISTRATION/INPUT_CATALOG_MISMATCH) behave identically against inputs. See Reference → Violation Types for the full list.

required: false is informational, not a check

catalog: { required: false, technology: hive } records an expected shape without gating anything — useful for documenting intent (ContractValidator warns on this combination, since a fully-specified but non-required block is easy to write by mistake). Nothing about a plan’s actual catalog registration is compared unless required: true.

What location can and can’t check

Section titled “What location can and can’t check”

location is the one sub-field worth understanding carefully, because what it can verify depends on the catalog technology — this isn’t a hypothetical caveat, it’s exactly what closing the org-wide “every job needs a real catalog entry” policy required confirming for real, against a real Spark session, rather than assuming.

Hive: a real, durable check. For a Hive-backed write or read, location is the metastore’s own network address — hive.metastore.uris (a real thrift://host:port), or an embedded:<jdbc-url> fallback for a local/embedded metastore — read from the active session’s own Hadoop configuration, not a value this module invents. This answers the concrete question a platform team would actually ask: can a job silently write through a different Hive metastore than the one the contract declares? No — a job connected to the wrong metastore reports that metastore’s real address, which disagrees with the contract’s declared one and is rejected, exactly like the example above.

Delta / Iceberg / JDBC: not checked, honestly. No DSv2 catalog implementation exposes its own network endpoint through a public API this module can read without taking on a compile-time dependency on that connector — so location is always absent for these today. Declaring catalog.location against a Delta/Iceberg/JDBC output is accepted as a no-op (not an error, and never a permanent, unsatisfiable rejection) — only technology/catalogName/namespace/table are actually verified for those. If you need to pin down which Delta/Iceberg catalog instance a job talks to, that’s not something this check can do yet.

Section titled “Trying it yourself”

The three scenarios below are the real, unedited output of that script (only Spark’s own log noise and the JVM startup banner are trimmed). Each one names, explicitly, what Invaract validated and what it published — and, just as importantly, what it didn’t.

Scenario 1: pass — a correctly Hive-registered write

Section titled “Scenario 1: pass — a correctly Hive-registered write”

The contract requires catalog: { required: true, technology: hive, table: sales_tbl }. A real CREATE EXTERNAL TABLE ... LOCATION registers the output under exactly that table name before the write, the same way a platform team would set a table up once and let many jobs write to it:

What this shows: two different events publish for one successful write — a pre-write ContractValidationEvent (from the check rule, before anything is committed) and a post-write WriteEvent (from SparkAdapterListener, once Spark reports the write actually completed). Only the WriteEvent carries the real, resolved catalog field — this is the first place a downstream consumer can see the actual metastore address a write resolved to, not just what it was compared against.

Scenario 2: missing-registration — a bare-path write, rejected

Section titled “Scenario 2: missing-registration — a bare-path write, rejected”

Same contract, but the job writes with a plain .write.parquet(path) — no CREATE TABLE, no catalog entry of any kind. Before this feature, this passed cleanly:

What this shows: the write is aborted before it commits — no WriteEvent publishes at all, since Spark never reports a successful write. Only the ContractValidationEvent fires, FAILED, with a remediation string telling the job’s author exactly what to fix.

Scenario 3: wrong-metastore — registered, but under the wrong metastore

Section titled “Scenario 3: wrong-metastore — registered, but under the wrong metastore”

The contract now pins catalog.location: thrift://not-the-real-metastore.example.com:9083. The job registers the table exactly as in scenario 1 — a real Hive registration exists — just not against the metastore the contract names:

What this shows: registration existing isn’t enough on its own — this is the concrete answer to “can a job silently write through a different Hive metastore than the one the contract declares?” It reports both the expected and actual catalog descriptors, and names exactly which sub-field disagreed (location), so nothing about the mismatch is left for the reader to reconstruct by hand.

Summary: what’s validated, what’s published, and what isn’t

passmissing-registrationwrong-metastore
Write committed?YesNo — aborted pre-writeNo — aborted pre-write
ContractValidationEvent published?Yes, PASSEDYes, FAILEDYes, FAILED

And, independent of scenario — the honest limitation from “What location can and can’t check” above still applies: technology/catalogName/namespace/table are checked for Delta, Iceberg, and JDBC outputs too, but catalog.location is accepted as a no-op for all three — there is no equivalent “wrong metastore” proof for a non-Hive catalog today, because no DSv2 catalog exposes its own network endpoint through an API this module can read.
