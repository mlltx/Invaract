Use Invaract with Python Jobs

This guide makes a plain Python job (one that reads and writes files with pandas, Polars, DuckDB or pyarrow, with no Spark or Beam underneath) keep to a data contract. The job reads and writes through the invaract package by the names its contract gives; every read and write is checked as it happens, and the job’s outputs are published together, only if the whole run passed. The contract is the same YAML you write for Spark.

What this does and does not check

Invaract checks what a Python job reads and writes: which datasets, where, in which format and save mode, and with which columns and types (including that a required column holds no empty value). It cannot read what your own Python code does between a read and a write, so the transformation-shape rules (required_filter_columns, required_join_columns, required_group_by, forbid_cross_join), custom rules, static data-quality proofs and role consistency are refused with UNSUPPORTED_CONTRACT_FEATURE rather than checked. It reads and writes Parquet and CSV files on local and mounted file systems. Object storage (S3, GCS, Azure) and Delta Lake and Iceberg tables come next. The full list, in plain words, is in What Each Engine Checks.

How it works

Section titled “How it works”

Unlike Spark and Beam, where Invaract is attached from the command line, a Python job adopts Invaract once, in its code: each read and write that named a path names the dataset instead, and the contract says where it is. The change is the same for every job, and small:

When the job starts, the package starts Invaract’s checker, the same verification code the other engines use, and describes each read and write to it: the dataset’s name, its columns, their types and how many empty values each holds. It never sends the data itself. Each write is checked before it is written, and written to a staging folder beside its location. When the job returns, every staged output is published (moved into place); if anything was refused, nothing is. So a run that breaks its contract leaves the outputs exactly as they were before it started.

After that one change, a platform configures the job from outside it, with INVARACT_* environment variables: which contract, where events go, which policy applies (see The settings).

Install the package

Section titled “Install the package”

It needs Python 3.10 or later and pyarrow 15 or later (installed with it); for pandas, 2.2 or later, and for Polars, 1.0 or later.

The checker comes with the package. On Linux (x86_64 and aarch64) with glibc 2.34 or later (Ubuntu 22.04, Debian 12, RHEL 9 and later) and on macOS 11 or later (Apple silicon and Intel), pip installs a wheel that carries the checker as a native program: nothing else is needed. On any other platform it installs a wheel that carries the checker as a Java program, so Java 11 or later must be installed there (JAVA_HOME, or java on the PATH). Set INVARACT_CHECKER to run a checker of your own instead (see Python-only settings).

  3. Replace each read and write with the dataset’s name. invaract.read(name) returns a pandas DataFrame; pass as_="polars", "polars-lazy" or "arrow" for another kind.     Nothing else in the job changes: the transformations between the reads and the writes stay as they are.

A job that breaks its contract

Section titled “A job that breaks its contract”

If the report’s total is no longer what the contract declares (here the contract was changed to say string), the write of the report is refused, the job stops with exit status 1, and neither output is published, the audit included. After Python’s traceback, the reason:

“The job’s own Python code” stands for everything between the reads and the write, which Invaract does not look into. The exception is invaract.ContractViolation, and the exit status 1 lets a scheduler tell a refused run from a crash. If the check could not be made at all (no checker for the platform, a contract that cannot be read, a format the package cannot write), the exception is invaract.CheckNotRun, the exit status is 2, and nothing is published either.

Start from a job with no contract

Section titled “Start from a job with no contract”

Dry-run mode writes the contract for you. Replace each read and write, keeping its path as location=, and run the job with INVARACT_DRY_RUN=true: it reads and writes exactly where it did before, nothing is refused, and a draft contract is inferred from what it actually read and wrote.

With a notification sink configured, each write’s draft is published as a CONTRACT_INFERENCE event, and when the job returns one DRY_RUN_SUMMARY event merges them into one contract. For the job above, its mergedContractYaml begins (real output; the columns of each dataset follow in the same form):

Review the draft before you commit it. Its id is the job’s entry point; give it a real one. Each output’s derivedFrom lists every input read before that output was written (here the audit is listed as derived from the customers too, because they were read first): keep only the inputs it really comes from. Then commit the contract, name it in @invaract.job (or with INVARACT_CONTRACT), and remove the location= arguments. With a contract in force, a location= that disagrees with it is refused. See Dry-run mode for more on turning a draft into a contract.

It flags reads (IVR001) and writes (IVR002) through pandas, Polars, pyarrow and DuckDB, database and storage connections (IVR003), and SQL that reads or writes files (IVR004), matching each call by the name it resolves to through the file’s imports, so an alias is no way around it. A call kept on purpose is marked on its line, ideally with the reason:

invaract-lint --format github jobs/ prints each finding as an annotation on the pull request’s diff.

The settings

Section titled “The settings”

Every Invaract setting is an environment variable of the job, spelled INVARACT_<SETTING> (a switch is INVARACT_DRY_RUN=true), so a platform can set them for a job it does not own:

VariableWhat it does
INVARACT_CONTRACTThe contract to enforce: a file path, or registry://<id>@<version> (Use a Contract Registry). Overrides the one @invaract.job names.
INVARACT_DRY_RUN=trueInfer a contract from the job’s writes instead of enforcing one (above).
INVARACT_NOTIFY_CONFIGWhere validation events go (Notification Sinks).
INVARACT_LOCATION_MAPHow ref:// locations resolve (Resolve Dataset Locations).
INVARACT_ORG_POLICY, INVARACT_ORG_POLICY_OVERLAYSOrganizational policy layered on the contract (Enforce Organizational Policy).
INVARACT_REJECT_UNDECLARED_FIELDS=trueRefuse an output column the contract does not declare.
INVARACT_REGISTRY_URL, INVARACT_REGISTRY_CLIENT_CLASSThe contract registry.
INVARACT_CHECKERThe command that runs the checker, instead of the one the package carries.

A read of an input the contract does not declare is always refused, since every read names the input it reads. Every setting, with its spelling on the other engines, is in Configuration Settings.

Formats, save modes and locations

Section titled “Formats, save modes and locations”
  • Formats: Parquet and CSV, for reading and writing. A write uses the format the contract declares for the output, or Parquet.
  • Save modes: overwrite replaces what is at the location, append adds the run’s files beside what is there, error refuses the write if the location already holds data, and ignore publishes nothing if it does. A write uses the save mode the contract declares, or overwrite.
  • Locations are files or folders on a local or mounted file system. A run stages each output in a hidden folder beside its location and moves it into place when the job returns.
  • Required columns: a column the contract marks required: true must hold no empty value; the file written then states the column as not null.
