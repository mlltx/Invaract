Publish Lineage to OpenLineage

This guide turns on OpenLineage publishing, so each run of a job appears in your lineage backend: the datasets it read and wrote, the columns of each, where each output column came from, and the contract’s verdict on every write. Like the rest of Invaract it is set through the job’s own configuration, so a platform team can turn it on for a job whose code it does not own. With none of the settings below, nothing here runs.

OpenLineage is an open standard for lineage events. Any backend that accepts it works: Marquez, DataHub, Atlan, OpenMetadata, or the cloud catalogs that read it.

Turn it on

Section titled “Turn it on”

Point the job at your backend’s URL. Events go to <url>/api/v1/lineage, the endpoint OpenLineage backends serve.

  • Spark
  • Beam Java
  • Beam Python
  • Python

A job that installs Invaract in its own code (ContractEnforcementRule.forContract) publishes too: the settings are read from the session, as spark.invaract.locationMap is.

Two more settings, spelled the same way per engine (see Configuration):

  • openLineageNamespace: the namespace the job is published under. Default: the configuration file’s namespace, else the OPENLINEAGE_NAMESPACE environment variable, else default.
  • openLineageConfig: a .properties file for everything else: the configuration file.

Either openLineageUrl or openLineageConfig turns publishing on. Settings Invaract cannot use (a URL that is not http or https, an unknown key in the file, a file that is not there) stop an enforced job when it starts, naming the setting, as a broken notifyConfig does. In dry-run mode they cost one warning and the job runs without them.

What a run looks like

Section titled “What a run looks like”

Each run of a job is one OpenLineage run: a START event, a RUNNING event for each write Invaract checks (and, on Spark attached through configuration, each write once it completes), and a terminal event, COMPLETE, or FAIL when Invaract refused a write.

User names and passwords in a location are never published.

When a run ends

Section titled “When a run ends”
EngineThe run ends
Sparkwhen the application stops (spark.stop(), or the driver exiting)
Beam Javawhen the pipeline is refused, or once it is checked and handed to its runner (for a runner that blocks, when the pipeline finishes)
Beam Pythonwhen the checker has checked the pipeline: refused, or let through to be submitted
Pythonwhen the job’s Invaract run finishes

A process that ends before saying so (it was killed, or never stopped its session) has its open runs ended as it exits, within shutdownTimeoutMs. A process killed outright (kill -9) cannot: the backend shows that run as still running.

What it costs a job

Section titled “What it costs a job”

Publishing happens on a thread of its own. The job’s thread only hands each event to it, so a slow or unreachable backend never slows the job down or fails it. The figures below are from the OpenLineagePerformanceSpec and SparkOpenLineageSpec tests:

  • A check of a 200-column job costs tens of microseconds more with OpenLineage on (within the noise of the measurement).
  • Publishing an event costs the job about a microsecond, whether the backend answers in a millisecond or not at all: a thousand events against a backend that takes a second each cost the job under 20 ms.
  • A Spark job of 20 writes took 2,960 ms with OpenLineage off and 2,939 ms with it on, against a backend answering in 20 ms.
  • Memory is bounded by queue.capacity. A queued event holds what describes its write, so a thousand events of a 200-column job are on the order of 100 MB at the very worst (a backend that hangs while the job writes a thousand times); an ordinary job holds a few MB.
  • At the end of the job, at most shutdownTimeoutMs is spent sending what is left, and only when something is left.

To publish less: emission=endOfRun sends two events per run, failuresOnly=true sends only failed runs, facets.disabled=columnLineage,schema drops the largest facets, and compression=gzip shrinks what is sent.

Delivery is best effort

An event that still cannot be delivered after its retries, or that is dropped because the queue is full, is lost (or written to deadLetter.path): lineage never holds up a job. One warning a minute says how many were lost, and why.

How complete the column lineage is

Section titled “How complete the column lineage is”

Invaract’s Spark column lineage is held up against openlineage-spark and Spline on a corpus of real Spark jobs, on every build of Invaract. Spark Column Lineage Coverage lists each construct (projections, conditions, joins, aggregates, windows, rollups, nested data, SQL subqueries and CTEs, UDFs, catalog tables, Delta Lake MERGE, Iceberg, Hive, JDBC, RDDs, streaming), whether the three agree, and why not where they differ. For each job it shows the code and the lineage Invaract publishes for it, so you can check it, and the steps to run the comparison yourself. It also lists what Invaract captures that the other tools miss, and its known limits.

Alongside openlineage-spark

Section titled “Alongside openlineage-spark”

The openlineage-spark integration publishes one run per Spark SQL query, with the plan’s lineage as Spark sees it. Invaract publishes one run per application, with what it checked. Both can be on: they are different jobs in the graph, and the datasets are the same nodes, measured on every job of the coverage corpus. A table a write creates (CREATE TABLE AS SELECT, writeTo(...).create()) is named by where it will be stored, as openlineage-spark names it, when Spark’s configuration says where that is: a LOCATION, the session catalog, or an Iceberg Hadoop or JDBC catalog. In a catalog that chooses the location itself when it creates the table, such as an Iceberg Hive, REST or Glue catalog, Invaract names the table by its catalog identifier. Set openLineageNamespace or jobName to keep them apart, or the same parent run to group them under one orchestrator run.
