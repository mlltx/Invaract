Spark Column Lineage Coverage

Invaract publishes column lineage for Spark jobs in its OpenLineage events, traced from the job’s analyzed plan. This page shows how complete and correct that lineage is. Each of the 55 Spark jobs below runs once, with three tools capturing lineage from the same run: Invaract, openlineage-spark (OpenLineage’s own Spark integration) and the Spline agent. Versions measured: openlineage-spark 1.55.0, Spline agent 2.4.0, Spark 3.5.9. For each job’s write, the comparison covers:

  • datasets: the input and output datasets, named by the OpenLineage naming conventions;
  • direct lineage: which input columns each output column’s value comes from, and how (IDENTITY, TRANSFORMATION, AGGREGATION, masking);
  • indirect lineage: which input columns decide the output’s rows or their order (FILTER, JOIN, GROUP_BY, SORT), or which value an output column takes (CONDITIONAL, WINDOW).

Spline does not classify edges, so against Spline every column an output column depends on is compared, by value or not.

Invaract agrees with openlineage-spark on 35 of 55 jobs, and with Spline on 41 of 55. A job agrees only when every dataset and every edge, with its type, is the same; each difference is listed below with its reason. Most come from one of two things: openlineage-spark reads Spark’s optimized plan, so it also reports columns the optimizer added (such as an isnotnull filter on a join key); or another tool misses part of the plan Invaract follows (what Invaract captures that the others miss). The rest are conventions, and Invaract’s known gaps.

Check it yourself

Section titled “Check it yourself”

Everything on this page comes from one run of the lineage-crosscheck module, and the code shown for each job is the code that ran. To run it, from a checkout of Invaract with Java 11 or later and sbt:

The run fails when any job’s lineage, Invaract’s or a reference’s, differs from what is recorded here (lineage-crosscheck/src/test/resources/crosscheck-baseline.txt). CI runs it on every pull request and every push, so lineage verified here cannot change without the change being reviewed. After an intended change, explain it in Corpus.scala and run CROSSCHECK_UPDATE=true sbt test to rewrite the baseline and this page.

In the code, s is the job’s SparkSession and f the shared inputs: f.orders(s) and f.customers(s) read Parquet, f.events(s) JSON. A job that is a DataFrame expression is written as Parquet to out.

InputFormatColumns

In the lineage, <in> is the inputs’ directory and <out> the job’s own. field <- dataset.column is direct lineage, field <~ dataset.column indirect (*: on every row of the output), each with its OpenLineage type.

Known gaps

Section titled “Known gaps”

None of the jobs on this page shows a gap in Invaract’s lineage.

Limits of Invaract’s Spark lineage that no job on this page measures:

  • A table its own write creates, in a catalog that chooses where to store it. Invaract names a table a write creates by where it will be stored when Spark’s configuration says (a LOCATION, the session catalog, an Iceberg Hadoop or JDBC catalog). In a catalog that chooses the location when it creates the table (an Iceberg Hive, REST or Glue catalog, for example), Invaract names the table by its catalog identifier.
  • Streaming queries. Invaract checks a streaming query once, when it starts, and publishes that lineage. It publishes nothing for each micro-batch.
  • User-defined functions. A column a UDF computes has the UDF’s input columns as its sources, typed TRANSFORMATION and described as opaque: what the function does with them is not known.
  • RDDs. A DataFrame made from an RDD has the files the RDD read as its inputs, with no column lineage through the RDD.
  • Operators Invaract does not translate. An operator Invaract does not translate is a boundary: a column computed through it has no sources.
  • A MERGE’s DELETE clauses, and the rows it leaves. The rows a DELETE clause removes are not written, so its condition is not reported. Rows no clause touches are not counted, as openlineage-spark counts them.

SQL: a filter by IN (subquery) over another input.

Invaract publishes:

Against openlineage-spark (the other tool’s limit): openlineage-spark reads the optimized plan, where Spark has rewritten the IN subquery into a semi join, so it calls these columns JOIN. Invaract reads the plan the job wrote: a filter.

Against Spline (the other tool’s limit): Spline does not follow a subquery inside a filter: it misses the subquery’s input and the columns it filters on.

delta-merge

Section titled “delta-merge”

Delta Lake: MERGE INTO a Delta table from another input.

Invaract publishes:

Against openlineage-spark (a convention): A MERGE’s ON condition decides which rows each of its clauses writes: Invaract reports its columns as INDIRECT/JOIN, as for any join. openlineage-spark reports no indirect lineage for a MERGE.

Against Spline (a convention): Spline also counts the rows a MERGE leaves as they are (no clause touches them), so the table’s own amount is a source of amount; Invaract, like openlineage-spark, counts the rows the MERGE’s clauses write. Spline records no indirect lineage, so not the ON condition either.

Against Spline (the other tool’s limit): Spline records no indirect lineage for a MERGE: neither its ON condition nor the clause conditions that decide which rows are written.
