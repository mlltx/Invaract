Partition Outputs

A partitioned dataset is laid out in one folder (or table partition) per value of its partition keys, Hive-style: day=2026-11-04/region=north/part-....parquet. Readers rely on that layout, both to read only the days they need and to find a day where they expect it. A contract can declare the layout, and Invaract then refuses a write that would break it:

  • a write by other keys, or by the same keys in another order;
  • a write with no partitions at all;
  • an overwrite that would replace more, or less, than the contract says.

Which engines check it

Python jobs that write through the invaract package are checked, and the package writes the layout itself. Spark and Beam Java jobs are checked too, for the writes where the engine says how they are partitioned (Spark, Beam); any other write to a partitioned output is refused as unverifiable. Beam Python doesn’t check partitioning yet, so it refuses a contract that declares partition keys (UNSUPPORTED_CONTRACT_FEATURE) rather than let a write break the layout unseen. See What Each Engine Checks.

Declare the partition keys

Section titled “Declare the partition keys”

Mark each key field partitioned: true, the Open Data Contract Standard’s own key. When there is more than one key, partitionKeyPosition orders them, 1 first:

A key must be a top-level field of a scalar type, since its values name folders. Keys without a position come after those with one, in the order they are declared.

Choose what an overwrite replaces

Section titled “Choose what an overwrite replaces”

partitionOverwriteMode says what a write with save mode overwrite replaces. It takes Spark’s two names:

ModeAn overwrite replacesUse it when
static (the default)every partition the output holdseach run writes the whole dataset
dynamiconly the partitions the write puts data in; the rest stay as they areeach run writes one day, or one region, and re-running it must not touch the others

An append adds the run’s files to their partitions whatever the mode.

Where the output lives

Section titled “Where the output lives”
  • Files on a local or mounted disk, or HDFS. A dynamic overwrite renames each partition folder the run wrote into place. Each folder is replaced at once, but the output as a whole is replaced folder by folder, not at once. A failure part way puts back the folders already replaced.
  • Object storage (S3, GCS, Azure). The run’s files are copied in, then the old files of the replaced partitions are deleted (all of them for static), and _SUCCESS is written last.
  • Delta tables. A new table is created partitioned by the keys. A dynamic overwrite adds the new files and removes the replaced partitions’ old ones in one commit. It needs a deltalake release that has deltalake.transaction.RemoveAction; with an older one the write is not checked and nothing is written.
  • Iceberg tables. A new table gets an identity partition on each key. A dynamic overwrite is pyiceberg’s dynamic_partition_overwrite, in one commit.

A Delta or Iceberg table that already exists keeps its partitioning. A write laid out otherwise is not checked and nothing is written; partitioning by a column the table lacks is the same.

A PostgreSQL table is not written partitioned: a write with partition columns is not checked and nothing is written. Partitioning a PostgreSQL table is part of the table’s own definition, which the run does not create.

Write it from Spark

Section titled “Write it from Spark”

A Spark job lays out its output itself, with .partitionBy(...) or its table’s PARTITIONED BY, and Invaract holds that to the contract. For the contract above (keys day, then region), this write is let through:

while .partitionBy("region") is refused before anything is written, with a message like contract declares the output partitioned by day, region but the write partitions by region.

What an overwrite replaces is decided as Spark decides it: the write’s own partitionOverwriteMode option, else the session’s spark.sql.sources.partitionOverwriteMode (static unless you set it). An INSERT OVERWRITE ... PARTITION (day = '2026-11-04', region = 'north') that names every key is a static overwrite of that one partition. An insert into a Hive table that Spark converts to its own Parquet or ORC writer is always dynamic, as Hive tables are, whatever the setting.

Spark says how a write is partitioned for these writes:

.writeStream into files, a Delta table or a table partitioned by plain columnsthe stream’s .partitionBy(...), else the Delta table’s owna stream appends, so none

Any other write to an output that declares partition keys is refused with UNVERIFIABLE_WRITE rather than let through unchecked: a Kafka stream, an insert into a Hive table Spark doesn’t convert (a TEXTFILE table, say), another source’s .save(...) with no .partitionBy(...) (a JDBC write, for one), and a table partitioned by a derived value such as days(ts) or bucket(4, id), which a contract’s keys (columns) cannot name. A console or memory stream reports no partitioning, so it is checked as unpartitioned.

A foreachBatch stream is not itself a write: the writes its function makes to each batch are checked, each as the batch write it is, partitioning included.

Write it from Beam

Section titled “Write it from Beam”

Beam has no file writer that lays out folders by column values: a team writes one with FileIO.writeDynamic(), whose destination is a function of its own that Invaract cannot see into. So the Beam adapter ships one it can read, HivePartitions, which lays out folders as Spark does:

writes data/out/revenue/day=4/region=north/part-00000-of-00001.parquet, each key a folder in order, its value escaped as Spark escapes it, and a missing one __HIVE_DEFAULT_PARTITION__. Unlike Spark’s, the files keep the key columns too. The elements are Beam rows or Avro records.

What else Beam says about a write’s layout:

WritePartition keys
FileIO.writeDynamic() by HivePartitionsits keys
A write to one folder: FileIO.write(), TextIO, AvroIO, TFRecordIO, CsvIOnone
BigQueryIO.write() with .withTimePartitioning(...) on a columnthat column

Any other dynamic destination, and a BigQuery write that states no partitioning (its table may have one already) or one by ingestion time, is refused with UNVERIFIABLE_WRITE when the output declares partition keys. A Beam file write states no save mode, so nothing says what an overwrite of it replaces: a partitionOverwriteMode declared on an output written that way is refused too. Beam Python doesn’t check partitioning yet, and refuses a contract that declares it (UNSUPPORTED_CONTRACT_FEATURE).
