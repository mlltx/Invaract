Infer a Starting Contract with Dry-Run Mode

Write a Contract walks through authoring one by hand, field by field. If you don’t have a contract yet and just want to see what your transformation actually reads and writes, dry-run mode does that for you: run your job with no contract at all, and Invaract prints one back — built from the job’s real inputs and outputs — that you can copy into a file, review, and use with the enforcement rule from then on.

A starting point, not a finished contract

Dry-run mode infers structure — locations, formats, save mode, field names/types/ nullability — never business rules. It has no way to know your MERGE must always match on customer_id, or that a DELETE should never run unconditionally; add those by hand once you have a contract to add them to. Every inferred field is also marked required: true, since it genuinely was present in this run — review that against what you actually intend before treating it as a finished document.

Logging a draft is enough for one job you’re looking at. To onboard a fleet — collect every job’s inferred contract in one place, and learn how safe it is to turn enforcement on for each — point dry-run mode at a notification sink by adding spark.invaract.notifyConfig, exactly as for enforcement. Nothing in the job changes:

With a sink configured, dry-run mode stops logging the draft and instead publishes two kinds of event:

  • CONTRACT_INFERENCE, one per write dry-run mode met — including the writes it couldn’t infer a contract from, which plain logging never mentioned.
  • DRY_RUN_SUMMARY, once, when the application ends — how many writes landed in each status, plus every draft from the run merged into one contract.

The statuses

Section titled “The statuses”
statusMeaningWhat to do with it
INFERREDA contract was inferred and nothing about it is in doubt.Candidate for your contract repository.
INFERRED_DEGRADEDA contract was inferred, but from a plan Invaract could only partly see: an unresolved .checkpoint()/cache boundary (inputs behind it are missing), a resolution that had to guess, or row-level DML (MERGE/UPDATE/DELETE, where the draft describes the target’s current schema and the operation’s own logic isn’t inferred). diagnostics says which.Review before trusting.
SKIPPED_UNSUPPORTEDA state-changing procedure CALL. Dry-run mode infers a contract from a write’s output schema, and a procedure call has none.Nothing to infer; enforcement would verify the resulting table state.
SKIPPED_UNRECOGNIZEDA command that may write data but that Invaract has no translation for. With a contract active, enforcement would reject it as an UNVERIFIABLE_WRITE.A blocker for turning enforcement on for this job.
INFERENCE_ERRORInference itself threw. The job was unaffected.Report it.

A job that ran but wrote nothing Invaract recognizes reports NO_WRITES_OBSERVED in the summary — the only place that outcome is visible, since there’s no write to attach an event to. Treat it as “not enough information”, not as “safe”.

The self-check

Section titled “The self-check”

Every inferred draft is verified against the very write it came from, under the options enforcement would use (so your spark.invaract.rejectUndeclaredFields and friends count). The event’s selfCheck is PASSED when turning enforcement on with that contract would not have blocked this write, and FAILED (with selfCheckViolations), INVALID or ERROR otherwise. That is a better readiness signal than the count of successes: a draft that doesn’t pass its own write isn’t something to promote.

Tag the draft, and link events back to the run

Section titled “Tag the draft, and link events back to the run”

Two kinds of metadata, kept apart on purpose:

Conf prefixDescribesWhere it lands
spark.invaract.contract.metadata.<key>=<value>The contract: owner, team, source system, a ticket.The draft’s extensions: block, and every event’s metadata.
spark.invaract.job.metadata.<key>=<value>One run of the job: an orchestrator run id, a DAG, a trigger.job.attributes on every event, and nowhere else.

The run-level facts stay out of the contract because a contract outlives the run: a run id in a promoted contract would be stale the next night. The contract-level ones ride in the draft, so it arrives already tagged with what it is and who owns it.

They also link the dry run to what comes after it. When you promote a draft and enforce it, Invaract copies a contract’s extensions into its own events, so the same keys appear in metadata on every CONTRACT_VALIDATION and WRITE event of the real runs. Whatever you use to find the dry run’s events, a key like owner or a ticket id, finds those too. Both prefixes can be set with spark-submit --conf, with no change to the job:

That is what produced the examples above: look at metadata and job.attributes in each, and at the extensions: block in contractYaml. Values are strings.

The DRY_RUN_SUMMARY’s mergedContractYaml is the job’s drafts merged exactly as MergeDraftsCli does, named for the job. If two writes disagree about a location’s schema, mergeStatus is CONFLICT and mergeConflicts lists them; no contract is guessed at.

The end-of-run summary always reaches every target, so each destination still learns that the job ended.

Dry-run never gets in the job's way

Inference, the self-check and publishing are each failure-isolated: a sink that is down or a plan shape Invaract hasn’t seen costs a log line, never a query. That includes setting the sink up: a notifyConfig that can’t be read, or names a class that doesn’t exist, logs one WARN and falls back to logging the inferred contract, instead of failing the job (enforcement mode, by contrast, still fails loudly on a bad notifyConfig). Delivery to an HTTP endpoint is asynchronous, and at application end the sink is given up to ten seconds to finish what it already accepted, so a short job doesn’t lose its last events. Each SparkSession a job creates reports on its own; a job that spawns child sessions sends one summary per session.

Migrating a job: from dry-run to enforcement

Section titled “Migrating a job: from dry-run to enforcement”

Dry-run exists to answer one question per job: is it safe to turn enforcement on? Work through the answer like this.

  1. Run the job once with dry-run reporting, down every code path that writes (a job that writes differently by date or by parameter needs a run for each).
  2. Read its DRY_RUN_SUMMARY. statusCounts says how many writes landed in each status.
  3. A job is ready when every write is INFERRED with selfCheck: PASSED, nothing is SKIPPED_UNRECOGNIZED, and mergeStatus is MERGED.
  4. If it isn’t, the status says what to do:
    • SKIPPED_UNRECOGNIZED: the write is a shape Invaract can’t verify, so enforcement would reject it. Check Connector Support; change the write to a supported shape if you can (an example).
    • INFERRED_DEGRADED: read diagnostics. An unresolved .checkpoint() means a draft’s inputs are incomplete; row-level DML means the draft describes only the target’s current schema.
    • selfCheck of FAILED, INVALID or ERROR: the draft doesn’t pass its own write, so don’t promote it. selfCheckViolations and diagnostics say why.
    • NO_WRITES_OBSERVED: Invaract saw no write it recognizes. Either that run never wrote, or the write shape isn’t recognized; don’t read it as “safe”.
    • CONFLICT: two writes disagree about one location’s schema. mergeConflicts names it.
  5. Review the merged draft (mergedContractYaml): replace the placeholder id, version and status (its extensions already carry the contract metadata you set), make locations portable, and add the rules dry-run can’t infer, as in Write a Contract.
  6. Switch to enforcement: replace spark.invaract.dryRun=true with spark.invaract.contract=<your reviewed contract>. The strict toggles (rejectUndeclaredInputs, rejectUndeclaredFields) are off by default; turn them on later, once the job has run clean.

Need a custom callback?

Section titled “Need a custom callback?”

Call ContractEnforcementRule.dryRun yourself when you want to do something with the inferred contract besides logging it — write it to a specific file, publish it somewhere, merge it with an existing draft. See Install and Configure Invaract Explicitly in Code.

ContractEnforcementRule.dryRun never throws and never blocks a write, under either mechanism — there’s no contract to violate. It only calls its callback (or, in the conf-driven path, logs) when the analyzed plan is a write Invaract recognizes (see Connector Support); a .count(), a plain read, or an unrecognized write shape produces nothing — unless a sink is configured, which also reports the writes it couldn’t infer from (see above). If your job performs more than one write, the callback fires once per recognized write — capture the one you want by overwriting a mutable cell, the same way the explicit-code example does.

Merging drafts from a job with several writes

Section titled “Merging drafts from a job with several writes”

What the merge does, and what it refuses to guess:

  • Inputs are one per location. The same location read by several writes becomes one input, named after its location (data/orders.csv → orders; a catalog table main.sales.orders → orders; a clash gets _2, _3, …). Each output’s derivedFrom is rewritten to those names.
  • Conflicting schemas are an error, not a pick. If two drafts saw the same location with different schemas (say, one was inferred before the source changed), the command prints every conflict, exits 1, and writes nothing. Re-run the stale write and merge again.
  • Outputs stay distinct by location. Two writes to one location merge only if they agree on its schema.
  • A write that read nothing keeps derivedFrom: [].
  • The merged contract is checked with the same validation as any contract file, and parses back with the normal parser. --output merged.yaml writes it to a file instead of standard output; --id defaults to merged_contract, --version to 0.1.0.

From code, ContractDraftMerger.merge(drafts, id, version) does the same on parsed Contracts and returns either the merged contract or the list of conflicts.

Checkpoints

Section titled “Checkpoints”

If your job calls .checkpoint() between reading and writing, dry-run mode sees through it the same way real enforcement does (see MISSING_INPUT in Violation Types): the inferred contract names the inputs read before the checkpoint, not an empty list. The checkpointed Dataset has to have been created while the rule was installed — a checkpoint made before the session had the extension can’t be resolved, and its upstream inputs won’t appear in the draft.

What it doesn’t do

Section titled “What it doesn’t do”

Dry-run mode only observes — it’s the mirror image of SparkAdapterListener, not a replacement for real enforcement. Once you have a reviewed contract, switch back to ContractEnforcementRule.forContract — that’s the mechanism that actually gates a write. Row-level DML (MERGE/UPDATE/DELETE) is inferred only weakly: those operations have no single “new output” to build a dataset schema from, so the draft describes the target’s current schema and none of the operation’s own logic (see Enforce Row-Level DML Rules for how they’re verified once a contract exists). When reporting to a sink, such a draft is flagged INFERRED_DEGRADED.
