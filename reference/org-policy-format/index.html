Organizational Policy Format

The full shape OrgPolicyParser/OrgPolicyValidator accept. See Enforce an Organizational Policy for a guided introduction.

Document shape

Section titled “Document shape”

Top-level fields

Section titled “Top-level fields”
KeyRequiredMeaning
versionyesFree-form revision identifier for this document — your own tracking, not compared against a contract’s ContractVersion.
policiesnoThe policy rules themselves — see below.
injectnoRules/options this policy contributes to every governed contract — see Rule/option injection.
exemptionsnoPlatform-controlled exceptions — see Exemptions.
customPolicyTypesnoMaps a type: name outside the built-in set to a CustomPolicyEvaluator class — see Custom policy types.
typeGuaranteesnoConfigures cross-contract type guarantee checks (data_asset_schema_consistency/data_asset_downstream_consumption, and any registered custom check) — see Type guarantees. Unlike every other field here, only CrossContractLintCli --org-policy consults this one; OrgPolicyEvaluator/ContractEnforcementRule never do, since it governs a check across many contracts, not one contract at a time.
controlTablesnoThe org-owned catalogue of known CONTROL-declared datasets, checked by require_control_registration — see Keep a CONTROL table honest.

Policy rule fields (policies[])

Section titled “Policy rule fields (policies[])”
KeyRequiredMeaning
idyesStable identifier, referenced by exemptions and shown in violation messages. Must be unique within the document.
typeyesPolicy kind — see Policy types below.
descriptionnoHuman-readable explanation, appended to violation messages for self-service remediation.
scopenoinputs, outputs, or all (default). Which of a contract’s datasets this rule applies to.
whenno{ sensitivityTag: <tag> } — narrows scope further to only datasets with at least one field (recursively) carrying that sensitivity tag.
modenoenforce (default) blocks a write before any plan is analyzed. warn only publishes a notification event and never blocks — the safe-rollout mechanism for a newly-introduced rule.

Every other key on a policy rule is type-specific and captured verbatim, the same way a contract’s own rules: entries work.

Policy types

Section titled “Policy types”
TypePropertiesChecks
require_catalogtechnology (optional)The dataset declares catalog.required: true, optionally matching a specific technology.
require_fieldname (required), fieldType (optional)The dataset’s schema declares a top-level field named name — not recursive into nested structs — optionally of fieldType (checked case-insensitively).
field_naming_conventionpattern (required)Every field name in the dataset’s schema — recursing into nested struct properties — fully matches the regular expression pattern. A partial match doesn’t satisfy it.
require_extensionkey (required), value (optional)The contract itself declares key in its top-level extensions map (e.g. extensions: { owner: data-platform-team }), optionally pinning key to an exact value (case-sensitive). A key present but mapped to YAML null counts as absent.
require_formatformats (required)The dataset declares format as one of formats — a single string (formats: delta) or a list (formats: [delta, iceberg]) — matched case-insensitively. A dataset with no format at all does not satisfy this.
require_dataset_description(none)The dataset declares a non-blank description.
require_dataset_typetypes (optional)The dataset declares a type (DATA_ASSET/SOURCE/CONTROL) at all; if types is also set (a single string or a list), the declared type must additionally be one of them.
forbid_control_sensitivity_tagstags (optional, defaults to [pii, financial])A dataset already declared type: CONTROL must not carry any schema field (recursing into nested structs) tagged with one of tags. A dataset with no declared type, or declared DATA_ASSET/SOURCE, is never in scope — see Keep a CONTROL table honest below.
require_control_registrationrequireRegistration (optional, defaults to true)A dataset already declared type: CONTROL must match a location entry in the top-level controlTables catalogue, and once matched, its schema must carry every field that entry’s requiredFields names. requireRegistration: false skips the “must be registered at all” half but still enforces conformance against any entry that does match. See Keep a CONTROL table honest below.
require_extension_ififKey (required), ifValue (optional), thenKey (required), thenValue (optional)A conditional require_extension: only once the contract itself already satisfies ifKey (optionally =ifValue) must it also satisfy thenKey (optionally =thenValue). A contract not satisfying the if condition at all produces no violation.

A policy type matching neither this set nor a customPolicyTypes entry is recorded but never checked — the same permissive behavior an unrecognized contract rules[].type already has, though OrgPolicyValidator now reports it as a Warning (not an Error) since customPolicyTypes makes this shape more likely to be a typo than intentional. A known type with malformed or missing properties for its shape (e.g. require_field with no name) is an OrgPolicyValidator Error, not silently ignored.

require_field's type pin is fieldType, not type

A policy rule’s own kind (require_field) is itself spelled type: at the same mapping level. SnakeYAML doesn’t reject a document with two type: keys — it silently keeps only the last one, which would overwrite the rule’s own kind rather than raise anything. The type pin therefore uses the distinct key fieldType.

require_extension and require_extension_if check the whole contract, not a dataset

require_catalog, require_field, field_naming_convention, require_format, require_dataset_description, require_dataset_type, forbid_control_sensitivity_tags, and require_control_registration each check one dataset at a time, honoring scope/when. require_extension and require_extension_if are different: they check the contract document as a whole, exactly once, so scope/when have no effect on either — setting either produces an OrgPolicyValidator Warning (not an Error; the rule still evaluates correctly), since it’s likely not what the author intended.

require_extension_if answers 'only if' requirements

require_extension can require a key to exist, but can’t make that requirement depend on another key’s value. require_extension_if fills that gap — e.g. only a contract whose extensions.status is deprecated needs to also declare extensions.sunsetDate; a contract that isn’t deprecated is entirely unaffected by the rule, not merely exempted from it.

Keep a CONTROL table honest

Section titled “Keep a CONTROL table honest”

forbid_control_sensitivity_tags exists because type: CONTROL is self-declared by whoever writes the contract — nothing stops a real business dataset from being labeled CONTROL to dodge DATA_ASSET-scoped obligations like require_catalog or role-consistency checking. A genuine control/watermark/processing-calendar/reconciliation signal has no legitimate reason to carry sensitive business data, so a CONTROL-declared dataset whose schema does is a mechanical, single-contract red flag:

With no tags property, this forbids the default pii/financial set on every CONTROL-declared dataset in the contract. Pin your own vocabulary instead:

Design your other rules so CONTROL isn't a free pass

If a universal rule like require_catalog or require_dataset_description is scoped or conditioned so it only applies to DATA_ASSET datasets, relabeling something CONTROL becomes the easiest way to dodge it. Keep governance rules that should bind everyone scoped all/outputs with no type-based narrowing, and reserve a type-conditioned rule like forbid_control_sensitivity_tags for checks that are specifically about whether the type claim itself holds up.

Require CONTROL tables to be registered

Section titled “Require CONTROL tables to be registered”

forbid_control_sensitivity_tags catches one honest signal that a CONTROL claim is wrong — but it proves nothing about an unsuspicious declaration nobody ever actually approved. controlTables is the org-owned catalogue that closes that gap: it lives in the policy document, not the contract, so only whoever owns the policy can add an entry — exactly the same trust boundary exemptions already gives you.

controlTables is purely documentary until require_control_registration is attached — you can build the catalogue up first, then turn on enforcement once it’s populated. OrgPolicyValidator warns if you have entries but no such rule, since that’s almost always a forgotten step rather than intentional.

The rule has one knob for how far to take it — requireRegistration, default true:

  • true (strict) — “CONTROL is the only thing allowed, and only once registered.” A CONTROL-declared dataset with no matching controlTables entry is itself a violation.
  • false (loose) — registration is optional; an unregistered CONTROL dataset is never flagged for that alone. But a dataset that is registered still has to conform: if the matching entry names requiredFields, your schema must carry them, or it’s a violation regardless of requireRegistration. This is the shape a platform rolling the catalogue out gradually wants — register real control tables as you find them, without retroactively blocking everything nobody’s gotten to yet.

A registration can lapse, too: give it a reviewBy date (identical semantics to an exemption’s own) and a stale entry stops counting as registered — the dataset falls back to unregistered, forcing periodic re-approval rather than a one-time rubber stamp.

A catalogue, not just a gate

Because controlTables is a plain top-level list, it doubles as a browsable inventory of every control table your organization has approved — owner, purpose, and expected shape all in one place — independent of whether you’ve turned on enforcement yet.

Custom policy types

Section titled “Custom policy types”

customPolicyTypes maps a type: name your document uses to the fully-qualified class name of a com.invaract.contract.CustomPolicyEvaluator implementation — the escape hatch for a policy type outside the built-in set above, with no Invaract source change needed. See Write your own policy type for a full worked example.

KeyMeaning
customPolicyTypes.<type>Fully-qualified class name of a CustomPolicyEvaluator (public no-arg constructor required), resolved reflectively and cached — one instance per class name, reused across every rule/contract that names it.

OrgPolicyEvaluator only consults customPolicyTypes for a type: outside the ten built-in ones — a customPolicyTypes key matching a built-in type is dead (the built-in always wins; OrgPolicyValidator warns on this). PolicyExemption coverage and mode: enforce/warn splitting still apply automatically to a custom type’s violations, exactly like a built-in one.

Composes with spark.invaract.orgPolicy for free

A customPolicyTypes entry is just more content in the same YAML document spark.invaract.orgPolicy=<path> already names — the evaluator class itself is supplied via --jars, the same as any other Invaract extension jar. No new spark-submit flag, no job source change.

OrgPolicyValidator outcomeWhen
ErrorcustomPolicyTypes.<type> has an empty class name, or names a class that doesn’t resolve (missing, no public no-arg constructor, doesn’t implement CustomPolicyEvaluator).
WarningcustomPolicyTypes.<type> collides with a built-in type (dead — the built-in always wins).
WarningA policy rule’s type matches neither a built-in type nor a customPolicyTypes entry (it will never be evaluated).

Type guarantees

Section titled “Type guarantees”

typeGuarantees configures com.invaract.contract.TypeGuaranteeValidator’s cross-contract “stronger semantic and guarantee validation” checks — see Declare Input and Output Types for a guided introduction. Only CrossContractLintCli --org-policy reads this block; OrgPolicyEvaluator does not.

KeyMeaning
typeGuarantees.enabledWhich checks to run, by name. Two are built in: data_asset_schema_consistency, data_asset_downstream_consumption (see the guide linked above for what each one checks). Empty or omitted means no type guarantee check runs at all.
typeGuarantees.modeenforce (default) — a real Contradicts result from any enabled check fails the lint run. warn — every enabled check still runs and is reported, but nothing blocks.
typeGuarantees.customTypeGuaranteeTypes.<name>Fully-qualified class name of a com.invaract.contract.TypeGuaranteeCheck implementation (public no-arg constructor required) — the escape hatch for a check outside the two built in, resolved reflectively by TypeGuaranteeCheckFactory, exactly the same shape customPolicyTypes already uses for CustomPolicyEvaluator.
OrgPolicyValidator outcomeWhen
ErrortypeGuarantees.enabled has an empty entry.
ErrortypeGuarantees.customTypeGuaranteeTypes.<name> has an empty class name, or names a class that doesn’t resolve (missing, no public no-arg constructor, doesn’t implement TypeGuaranteeCheck).
WarningtypeGuarantees.customTypeGuaranteeTypes.<name> collides with a built-in check name (dead — the built-in always wins).
WarningA typeGuarantees.enabled entry matches neither a built-in check nor a customTypeGuaranteeTypes entry (it will never be evaluated).

inject.rules/inject.minVerificationOptions

Section titled “inject.rules/inject.minVerificationOptions”
KeyMeaning
inject.rulesA list of ordinary DML rule entries ({type, ...properties}, the same shape a contract’s own rules: uses) merged into every governed contract’s rules before verification runs. A rule the contract already declares isn’t duplicated.
inject.minVerificationOptionsA map of VerificationOptions flag name (rejectUndeclaredInputs, rejectUndeclaredFields, computeFingerprint) to true — ORed onto a job’s own options. A flag a job left false can be forced true by policy; the reverse never happens. An unrecognized key (e.g. a typo) is rejected — ContractEnforcementRule fails loudly rather than silently ignoring it.

Exemptions

Section titled “Exemptions”
KeyRequiredMeaning
contractIdyesThe Contract.id this exemption covers.
policyIdsyesWhich policy rule ids (at least one) this exemption suppresses, for this contractId only.
reasonyesWhy the exemption exists — required, for auditability.
reviewBynoAn ISO-8601 date (YYYY-MM-DD). Once passed, the exemption stops applying and the violation it was suppressing re-surfaces. Omitted means it never expires.

Exemptions live in the policy file, not the contract

A contract’s own author can’t grant themselves an exemption — that would defeat the purpose of an organization-wide rule. Only whoever owns the policy document can.

Policy layering

Section titled “Policy layering”

A stricter business-unit (or team) policy can compose with a looser org-wide baseline, without the business unit’s document duplicating or replacing anything the org-wide one already declares. An overlay is not a different document shape — it’s an ordinary OrgPolicy YAML document, in every respect identical to the base, layered on top of it.

KeyMeaning
spark.invaract.orgPolicyThe org-wide base layer — unchanged from the single-document case above.
spark.invaract.orgPolicyOverlaysOptional, comma-separated, ordered list of additional OrgPolicy documents layered on top of the base. Requires spark.invaract.orgPolicy to also be set — an overlay with no base is rejected rather than silently treated as one.

Each layer is evaluated independently and the violations are unioned, so a stack of layers is always at least as strict as any one layer alone:

  • A layer can only add, never loosen. There is no mechanism for an overlay to override, replace, or loosen a rule an earlier layer declares. A business unit wanting a stricter version of a check the org-wide layer already has (e.g. tightening warn to enforce) adds its own additional rule of that type — both rules are then evaluated and unioned, the same as any other pair of rules.
  • A layer’s exemptions cover only that layer’s own policies. An overlay’s exemptions can grant an exception to a rule that same overlay declares, but it is structurally incapable of exempting a rule the org-wide layer (or any other layer) declares — OrgPolicyValidator rejects an exemption naming a policy id its own document doesn’t declare, and each layer’s exemptions are only ever checked against that layer’s own policies. Only the document that owns a rule can grant an exemption for it.
  • Custom policy types stay per-layer. Each layer resolves its own customPolicyTypes against only its own map, so two layers can independently use the same type: name for unrelated CustomPolicyEvaluator classes without colliding.

A policy id repeated across layers is a Warning, not a problem

Each layer evaluates independently, so a repeated id across layers doesn’t cause shadowing or misattributed exemptions. It’s still worth avoiding, though — a human reading two violations both attributed to catalog-required can’t tell which layer produced which. Prefix a layer’s own rule ids (e.g. bu-finance-catalog-required) rather than relying on id alone to distinguish them.

Linting a layered stack

Section titled “Linting a layered stack”

The same base-first, comma-separated convention as the conf key — useful for a business unit’s own CI to lint its contracts against org-wide + its own overlay, with the same argument shape spark-submit would take. Every policy document (base and overlays alike) is excluded from the contract sweep, the same as the single-document case.
