Python I/O Adapter

The design write-up for pythonio-adapter, generated by dev/new-adapter and filled in as the adapter is built, following docs/ADDING_AN_ENGINE_ADAPTER.md. It is the adapter’s counterpart of docs/SPARK_ADAPTER.md. The decision to build it, and the reasoning behind each choice, is docs/PYTHON_IO_ADAPTER_DESIGN.md (with the two surveys before it, docs/PYTHON_ADAPTER_SURVEY.md and docs/SINK_RECORDS_SURVEY.md). This document records what was built and what the build found.

While modules.json says this adapter is in-progress, TODO and ❓ are expected. Setting it to complete makes .github/scripts/check_modules.py fail until neither remains, so “done” means this document has no open item.

Status: milestones 0 to 4 done. The checker, PythonIoCheck, speaks the whole protocol (open, read, write, written, finish, and dry-run mode) over Arrow’s own type names, and builds as a native program that gives the same replies as the JVM. The invaract Python package (python/invaract) drives it: reads and writes by name, staging and publishing, the save modes, the settings, and the dry-run migration path. Every conformance scenario runs as a real Python job through the package and comes out as the declaration promises, and the declaration’s enforcement point is staged-publish. invaract-lint (lint/) flags the reads and writes a job makes around the package. Nothing is released yet (the platform wheels carrying the native checker are milestone 5), so the user pages list the engine as “in development”.

What it is

Section titled “What it is”

A Python job reads and writes through the invaract package by the names its contract gives (invaract.read("orders"), invaract.write(df, "report")). The package does no checking. It starts the checker once per run and describes to it each read and each write: the dataset’s name, the format and save mode, each column’s Arrow type, and the empty values each column holds. The checker answers each request with a verdict, and the package publishes the staged outputs only when the run finished and every answer was yes.

FileDoes

The protocol

Section titled “The protocol”

One request per line from the package, one reply per line from the checker, as the recorded cases (src/test/resources/protocol) hold them. A column is {"name", "type", "nullable", "nulls"}: type is pyarrow’s own name for it (str(field.type): int64, large_string, list<item: struct<sku: string, qty: int32>>, dictionary<values=string, indices=int8, ordered=0>), nullable is Arrow’s flag, and nulls how many empty values the data holds, where the data has been seen.

RequestThe checkerReply
{"op": "open", "settings": {...}, "job": {...}}reads the settings (the neutral names, from INVARACT_*), resolves the contract, location map and organisational policy, and refuses a contract it cannot check{"ok": true, "mode": "enforce", "contract": {inputs and outputs, each with its location, format, save mode and fields}}, or "mode": "dry-run"
{"op": "read", "name": "orders", "schema": [...]}refuses a name the contract does not declare (UNDECLARED_INPUT: the package has no location for it), and a location the job gives that is not the input’s (UNDECLARED_INPUT); checks the columns against the input’s, and records the read for every later write{"ok": true}
{"op": "write", "name": "report", "format": "parquet", "saveMode": "overwrite", "schema": [...]}the pre-check, before anything is staged: location (the contract’s, or the location the job gives, which must be the output’s), format, save mode, the inputs read, the columns and their types; publishes an event only when it refuses{"ok": true}
{"op": "write", "name": "report", "unverifiable": "why"}a table the package could not describe (no Arrow stream): UNVERIFIABLE_WRITErefused
{"op": "written", "name": "report", "nulls": {"total": 0}}the final check of a staged write, with the empty values each column turned out to hold: a required column that holds one is refused (decision 3); publishes the write’s event{"ok": true}
{"op": "finish", "completed": true}refuses a completed run that never wrote a declared output; in a dry run, publishes the job’s merged draft{"ok": true, "publish": true}

A refusal is {"ok": false, "status": "refused", "violations": [...], "explanation": ...}. A request the checker cannot check (a missing contract file, an unknown setting, a malformed request, a written with no write before it) gets {"ok": false, "status": "not-checked", "reason": ...}, which the package treats as a refusal, so nothing is published unchecked.

Why two requests per write. The columns and their types are known before any data is written, so a write that cannot pass is refused before the job spends time staging it. Whether a required column holds an empty value is known only once the data has been written, batch by batch: pandas marks every column nullable (the native Python survey, probe 8), so Arrow’s flag cannot answer it. The pre-check judges every column as if it held no empty values, and publishes only a refusal; the written check is the verdict on the whole write.

location with a contract in force. A job migrated from a dry run may still say where it reads and writes (location=). The checker then checks that location like any other, so an argument left behind cannot point a read or a write somewhere the contract does not declare (location-given-agrees, read-location-disagrees-refused, write-location-disagrees-refused).

Dry-run mode (INVARACT_DRY_RUN=true). There is no contract, so read and write carry the job’s own location and format. Every write is let through, each staged one gets a draft contract (CONTRACT_INFERENCE, with its self-check), and finish merges them into one draft for the job, named after it (DRY_RUN_SUMMARY), as Spark’s and Beam’s dry runs do.

Milestone 0: the checker as a native program

Section titled “Milestone 0: the checker as a native program”

The design’s gating question: can the existing Scala checker run where Python jobs run, with no Java there? The pass criteria and the result (2026-11-01, GraalVM CE 21.0.2, Linux x86_64):

CriterionResult
The same verdicts as the JVM, over recorded casesAll 27 recorded cases give identical replies natively and on the JVM (PythonIoProtocolCasesSpec in the JVM, native/cases.py against the program). One more case is JVM-only (below).
Contract parsing, organisational policy, the built-in sinksAll exercised by the cases: a bad contract, a missing contract file, a policy refused and kept, ref:// locations resolved and unresolved, and the file, HTTP, logging and fan-out sinks
Start-up well under a secondA whole run, start-up included, takes 6 to 15 ms natively, against about 0.45 s on the JVM. CI fails a case over 1 s
A size that suits a wheel41 MB, 14 MB compressed. CI fails above 50 MB compressed

The build needed very little configuration. GraalVM’s tracing agent, run over the cases on the jar, recorded the file sink’s constructor, two java.sql classes SnakeYAML looks up, and the capability declaration as a resource. The committed configuration lists those, the other built-in sinks, and the slf4j provider. The build takes about 75 s and 3 GB of memory.

CI’s pythonio-native-checker job repeats all of it on every run: sbt test assembly, native-image, the cases against the program with the 1 s limit, and the size check. It uploads the program.

What the native program cannot do (design section 4): load a class named in configuration that was not built into it. That covers a team’s own notification sink, custom rule verifiers, custom policy evaluators, and a registry client named by INVARACT_REGISTRY_CLIENT_CLASS. The registry case is therefore JVM-only: its stub client lives in the tests. A team that needs its own plug-ins needs a build that includes them, or the Java route.

With milestone 1 (2026-11-02) the protocol grew to 40 recorded cases: reads, the two-step write, Arrow’s type names, empty values in required columns, unverifiable writes and dry runs. The native program still gives the JVM’s replies on all 39 that it can run, with no change to its configuration (the dry run’s YAML writing and its events needed none), at 44 MB and at most 31 ms a run.

Milestone 1: the protocol

Section titled “Milestone 1: the protocol”

Milestone 1 (design section 12) is the checker’s whole side of the protocol, tested with recorded descriptions and no Python:

  • read checks each read as it is made, and the checker keeps the run’s reads, so a write no longer carries them.
  • The two-step write (write, then written) gives the early refusal and the data-based check of required columns that design section 5 and decision 3 call for.
  • Arrow’s own type names. The mapping (ArrowSchemas) moved from beam-adapter into verification-core, where both adapters share it, and gained dataType for one type name.
  • unverifiable writes are refused (UNVERIFIABLE_WRITE), which made failClosed.unverifiableWrites partial: the kit’s scenario for it now conforms (42 scenarios in all).
  • Dry-run mode reuses the core’s ContractInference, DryRunSelfCheck and DryRunSummary, so reporting.dryRunInference is supported.

Milestone 2: the package

Section titled “Milestone 2: the package”

Milestone 2 (design section 12) is the invaract package, in python/invaract, and its tests against the real checker:

  • The API is the design’s: @invaract.job() (or with invaract.run():), invaract.read(name, as_=...), invaract.write(frame, name), and the decorators @invaract.reads and @invaract.writes.
  • Writing. Any object with __arrow_c_stream__ is accepted. A pandas frame goes through pa.Table.from_pandas without its row index, and a Polars LazyFrame runs batch by batch. Polars and DuckDB releases from before the Arrow stream use their own conversion. Each write is described to the checker before anything is staged. It is then written batch by batch to a staging folder beside its location, with not null on each required column. A required column’s first empty value ends the write, and the checker refuses it.
  • Publishing. When the job returns and finish says to publish, each staged output is moved into place by a rename, per its save mode, with the previous version moved aside until every output is in place. A job that fails, or that catches a refusal and carries on, publishes nothing.
  • Reading. Parquet or CSV, a file or a folder. Only the columns the contract lists are read, and CSV columns are read as the contract’s types.
  • Settings are the INVARACT_* variables named in invaract/_settings.py, forwarded by their neutral names. PythonIoSettingsSpec holds that list to the checker’s. INVARACT_CHECKER names the checker program; it is the package’s own variable, not a setting.
  • Exit status. An uncaught ContractViolation ends the job with 1 (Python’s own status for an uncaught exception). An uncaught CheckNotRun ends it with 2, set from sys.excepthook once the traceback is printed.
  • Tests. 91 pytest tests: every refusal, the save modes, dry runs, the events, every frame library, the exit statuses, and the example job with each of probe 14’s bugs. They pass against the jar and against the native program, on Python 3.10 to 3.13, with the oldest supported libraries (pyarrow 15, pandas 2.2, Polars 1.0, DuckDB 1.0) and the newest (pyarrow 26, pandas 3.1, Polars 2.1, DuckDB 2.0). CI’s pythonio-python job runs them against the native program on Python 3.10 with the oldest libraries, and on 3.13 with the newest.

Milestone 3: conformance through real Python jobs

Section titled “Milestone 3: conformance through real Python jobs”

Milestone 3 (design section 12) runs the kit’s scenarios as real Python jobs, and gives staging its own enforcement point:

  • PythonIoPackageConformanceAdapter writes each scenario’s job as JSON. python/tests/conformance_job.py runs it as a team’s job would run: the contract, the options and the notification sink as INVARACT_* variables, and the checker as PythonIoCheck from the test run’s own classpath. The job reads through invaract.read, joins, filters, groups and projects with pyarrow, and writes through invaract.write with the format and save mode it uses itself. The verdict is read back from its exit status (0, or 10 for a refusal) and the validation events its file sink wrote.
  • Inputs hold empty values. The kit describes inputs only by their schemas, and other adapters make them empty. This adapter judges a required column by the empty values the data holds (decision 3), so each input gets one row with every column set and, for each column it lets be empty, one row where only that column is empty. Values are positive and equal row by row across inputs, so filters keep rows and joins match.
  • All 42 scenarios conform as real jobs, the same as in-process. That held on pyarrow 25 and 26, and on pandas 2.3 and 3.1. A sabotaged job (one that never writes) fails 20 scenarios, so the run tests the package and does not just pass. Without Python (INVARACT_TEST_PYTHON without pyarrow) the scenarios are canceled; under INVARACT_CONFORMANCE_STRICT=true, as CI’s pythonio-native-checker job runs them, they fail.
  • staged-publish (EnforcementPoint.StagedPublish): each write is checked before it is staged, and the outputs are published together only if the whole run passed. The user pages now say that for this engine, not in-engine-blocking’s “writes the job made before it have already happened”.

Milestone 4: the lint

Section titled “Milestone 4: the lint”

Milestone 4 (design section 7) is invaract-lint, the main guard against reads and writes made outside the package (decision 5):

  • What it flags. It flags a call by the name it resolves to through the file’s imports, so an alias (import pandas as pd, from pyarrow import parquet as pq) is no way around it. There are four codes:
    • reads (IVR001);
    • writes (IVR002): pyarrow’s writers, a frame’s to_* and write_* given a destination (df.to_csv() alone returns text), sink_*, open in a mode that writes or one not spelled out, Path.write_text;
    • connections (IVR003): database drivers, sqlalchemy, cloud storage clients;
    • SQL that reads or writes files (IVR004): COPY, ATTACH, read_parquet(...), a quoted path after FROM.
  • What it does not do. It checks only that such calls are present, as the design asks. It does not follow names reached dynamically (getattr, __import__).
  • Exceptions. A call is kept with # invaract: allow on any of its lines, which shows in review. The conformance job uses this for the two lines that make its inputs.
  • Running it. invaract-lint [paths] exits 0, 1 (findings) or 2 (a file it cannot parse). --format github prints each finding as a pull-request annotation, and the README shows a pre-commit hook. It has no dependencies.
  • Tests.
    • 71 pytest tests, on Python 3.10 to 3.13. They include the example job before it adopted the package (4 findings, the survey’s probe 14) and after (none).
    • Mutation testing with mutmut (design section 10): 283 of 323 mutants killed (87.6%). The 40 that survive are argparse help and description texts, and equivalent mutants. For example, a broken-file count of -1 still exits 2, "UTF-8" is the same as "utf-8", and the mode set "XXwax+XX" still catches every write mode.
    • CI’s pythonio-lint job runs the tests and lints the example and conformance jobs. It also runs mutmut with an 80% floor.

Friction log

Section titled “Friction log”
  • dev/new-adapter takes an engine name without a hyphen, so the design’s python-io-adapter and engine python-io became pythonio-adapter and pythonio; the design now says so.
  • The generated declaration marks every capability unsupported, which makes the checker refuse every contract with an output schema (UNSUPPORTED_CONTRACT_FEATURE). The declaration had to be written before the checker could be tried on a real contract.
  • The kit’s scenario an-undeclared-second-write-is-blocked expected a MISSING_INPUT that only per-write read attribution shows, which this adapter cannot have (D4 of the native Python survey). It was settled with a kit change, as D4 recommends: Scenarios.partialExcuses names, per scenario, the violations an adapter declaring a capability partial is excused from (here MISSING_INPUT, for check.inputExistence).
  • The user pages’ sentence for in-engine-blocking says a job’s earlier writes have already happened; with staging they have not. Milestone 3 added the staged-publish enforcement point to verification-core (EnforcementPoint.StagedPublish, with its own wording in the kit’s CapabilityGuide), and the declaration uses it. The engine stays labelled “in development” until the first release.
  • Stryker4s leaves instrumented classes in target/; running the checker from that classpath afterwards fails with NoClassDefFoundError: stryker4s/package$. sbt clean first.
  • A /simplify pass (2026-11-02) moved what the adapter had copied or worked around into verification-core: one way to refuse (VerificationPipeline.reject), a write’s verdict without publishing it (evaluateWrite, so the pre-check no longer runs the pipeline twice), dry-run reporting shared with Beam (DryRunReporting, which also guards the final flush), loading a capability declaration (AdapterCapabilities.load, used by every adapter and the scaffold) and the settings’ snake-case spelling (ConfigSource.snakeCase, shared with the Beam Python adapter).
  • Milestone 0’s protocol carried each write’s reads and judged a required column by the frame’s nullable flag. Both had to change once the conformance adapter played the package faithfully: the package learns the reads one at a time, and pandas sets the flag on every column. Milestone 1’s read and written requests are the result; the recorded cases were regenerated for them.
  • Milestone 2’s package needed two things from the checker that milestone 1 had not given it: the inputs’ declared columns in open’s reply (to read only those, and CSV with the contract’s types), and a check of location= with a contract in force (the design’s guard against an argument left behind after a migration). Both are checker changes with recorded cases.
  • pandas’ __arrow_c_stream__ carries the row index as a column (__index_level_0__) once a filter has made it anything but 0, 1, 2, …; the example job’s audit was written with it. The package converts a pandas frame without its index.
  • pyarrow 14 has no RecordBatchReader.from_stream, so the package needs pyarrow 15. Polars 1.0 and DuckDB 1.0 have no Arrow stream; the package falls back to their own to_arrow() and arrow().
  • A contract has no CSV delimiter field, so CSV is read and written with a comma (design section 5 said “the contract’s delimiter”).
  • The design named Python 3.9 as the oldest supported release. CI’s runners no longer offer it (it reached its end of life in October 2025), so the package requires 3.10, the oldest CI can test.
  • The design placed the lint at python/invaract_lint/, beside the package. A second package needs its own pyproject.toml and root, so it is lint/ instead.
  • Run over the package’s own code, the lint finds exactly the package’s three pyarrow reads and writes (_frames.read_table, _run._writer). That is a check that it catches real I/O; the package is not a job, so it is not marked.
  • Both conformance specs record their results as target/conformance/<adapter>.json, and both are the adapter pythonio, so the second overwrote the first. The package spec now writes to target/conformance/package/.
  • Re-recording every case with cases.py --record overwrote the JVM-only registry case with a failure (its stub registry client is on the test classpath only). --record now skips JVM-only cases, whose replies are written by hand.
  • The registry client’s “not found” message says to add a jar “via spark-submit —jars”, which is Spark’s wording, in verification-core; a Python job sees it too. Left for a wording pass across adapters.

Unverified items

Section titled “Unverified items”

  • The HTTPS path of the HTTP sink natively: the cases use plain HTTP to a local receiver (--enable-url-protocols=http,https is set for it).
