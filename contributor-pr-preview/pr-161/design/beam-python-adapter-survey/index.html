Beam Python adapter survey

Status: survey, followed by the adapter (docs/BEAM_PYTHON_ADAPTER.md). The forecasts below are as written before the adapter existed; the scenario tables’ Actual column and the Retrospective at the end compare them with what the conformance run showed. This document helps decide whether and how to let Invaract check Apache Beam pipelines written in Python. It builds on the Java Beam adapter (docs/BEAM_ADAPTER.md), which exists, and on its survey (docs/BEAM_ADAPTER_SURVEY.md). Engine surface surveyed: the Beam Python SDK 2.77.0 on Python 3.11, its portable pipeline description, Beam YAML, and Java steps used from Python (“cross-language”), checked on Beam’s in-process runner. Written: 2026-10-18. Evidence checked: 2026-10-18. Source of each claim: section 10, “Evidence log”.

The short version

Section titled “The short version”

What it would be. Before a Python Beam job starts, Invaract would take the job’s description in Beam’s language-neutral form (the portable pipeline, defined in section 2). It would hand that to the checking code that already exists in Java, compare it with the data contract, and refuse to start the job if it breaks the contract. As on the Java adapter, it checks the shape of a job: what it reads, where it writes, and which columns and types come out. It does not check what the team’s own Python functions do to individual values.

How much of the suite it is expected to pass. Of the suite’s 53 scenarios: 24 by doing the check, 5 partly, 13 by refusing safely, and 11 skipped because they do not apply. “Partly” means BigQuery in CI and streaming runs, neither proven yet. Details in section 7.

Can it be switched on without changing the job’s code? Partly, in the same way as on Java. A platform team adds --runner=invaract_beam.InvaractRunner and the Invaract settings to the job’s launch command, and installs one Python package where the job is submitted. The job’s code stays as it is, provided it passes its command line to Beam and does not choose its own runner. Tested on a real Python pipeline (probe 4). Section 5.

The biggest risks.

  1. The checking code runs in Java, so the machine that submits the job needs Java. A Python job is often launched from a Python-only environment, such as a scheduler worker or a Dataflow Flex Template launcher. Whether those have Java is not yet checked (UNVERIFIED). The fallback is to ship the checker as a ready-to-run program that needs no Java (D3).
  2. Much of what a Python job states about itself is “display data”: labels each step publishes for people (File Pattern, Table), not a promised interface. A Beam release could rename them. The Java adapter has the same exposure through class names, and the answer is the same: a version matrix in CI, and refusing what can’t be read.
  3. Python steps carry their logic as pickled Python (Python’s own way of saving an object, readable only by Python). Java cannot read it, so whatever is known only inside a Python object (a grouping’s keys, a Parquet read’s columns when the job did not ask for rows) is invisible unless a small Python-side helper copies it out (D2).

Decisions I need from you. (Each is explained in section 4; a one-line answer is enough.)

  1. Build it, as a Python package plus the existing Java checker reading the portable pipeline? Recommend yes.
  2. Translate in Java from the portable pipeline (one translator for Python, YAML and any other SDK), with a small Python helper that adds the facts only Python can read? Recommend yes.
  3. Call the Java checker as a separate program per job submission at first, needing Java on the submitting machine, and move to a no-Java build only if that proves a problem? Recommend yes.
  4. Declare the transformation-shape rules unsupported at first (refused safely), and add group-by from the helper later? Recommend yes.
  5. For the BigQuery scenarios in CI, check the pipeline without running it, since Python Beam has no in-memory BigQuery? Recommend yes, if the kit can be given a “check only” mode; otherwise declare those partial with a note.
  6. Publish the Python package to PyPI with its own release step, versioned with the Java adapter? Recommend yes.

How to read this document

Section titled “How to read this document”
  • What “conforming” means here. Invaract has a conformance suite: 53 small, engine-neutral jobs (scenarios) every adapter is run against. An adapter is the part of Invaract that knows one engine. It declares what it can and cannot do (its declaration), and each scenario must come out the way that declaration promises. Refusing safely is conforming. If an adapter says “I cannot check this”, the suite expects it to refuse any contract that depends on it, rather than let the job through unchecked. So a ❌ below is a limit to understand, not a failing grade.
  • Forecast marks.
    • ✅ expected to do the check and produce what the suite expects.
    • ⚠️ only partly, or with a workaround, or depends on something not yet verified.
    • ❌ cannot do the check, so the suite expects a safe refusal.
    • ➖ does not apply.
  • Confidence. High: shown by a probe I ran. Medium: each part was probed, or the source says so, but the whole has not been assembled. Low: inferred. Nothing here has been run as an adapter.
  • “Probe”. A throwaway program I wrote and ran against real Python Beam 2.77.0 to see what it reveals. The programs are not committed; what they printed is quoted below.

1. What Invaract asks of an engine

Section titled “1. What Invaract asks of an engine”

The contract, and the check

Section titled “The contract, and the check”

A data contract is a small YAML file saying what a job may read, where it must write, and what the written data must look like:

Invaract checks a job against it before the job writes anything. If the job reads something undeclared, writes somewhere else, or produces the wrong columns, the write is refused with a message saying what was checked, what failed and how to fix it. On Spark the check runs inside Spark just before each write. On Beam (Java today, Python here) it runs once, just before the whole pipeline is handed to the engine.

The engine-neutral model (the “IR”)

Section titled “The engine-neutral model (the “IR”)”

Every engine describes a job in its own way. Invaract translates that description into one small engine-independent description of reads, filters, joins, groupings and writes, called the IR (intermediate representation). All the checking code works on the IR, so it is written once for every engine:

The Spark adapter builds the IR from Spark’s query plan. The Java Beam adapter builds it from the Java pipeline in memory. A Python adapter would build it from the portable pipeline, the description every Beam SDK can produce (section 3).

2. The engine in plain words

Section titled “2. The engine in plain words”

Apache Beam is a way of writing data-processing jobs (“pipelines”) once and running them on several engines, called runners: Google Dataflow, Flink, Spark, or Beam’s own in-process runner (in Python 2.77 that is “Prism”, a small runner written in Go). A pipeline is a chain of steps (transforms: a read, a filter, a grouping, a write) with collections of data flowing between them.

Beam has an SDK (a library for writing pipelines) per language: Java, Python, Go, and a YAML format that the Python SDK runs. Python is the most used of these on Dataflow. A Python job looks like this:

When the with block ends, Beam asks the chosen runner to run the pipeline. Before a runner submits a Python pipeline, Beam turns it into the portable pipeline: a language-neutral description of every step and collection, written in Protocol Buffers (a compact, typed data format that any language can read; “proto” for short). That moment, after the pipeline is built and before anything runs, is where Invaract can stop a job.

Why the Java adapter does not cover this. The Java adapter is a Java runner that reads Java objects. A Python job never reaches it: Python picks a Python runner, and the Python objects are not Java objects.

3. How the adapter would get hold of a job

Section titled “3. How the adapter would get hold of a job”

The portable pipeline (the proto)

Section titled “The portable pipeline (the proto)”

  • What it is. The pipeline written out as data: every step with its name, the kind of step it is, its inputs and outputs, a few labels it publishes about itself, and every collection with the encoding its items travel in. It is like a shipping manifest for the job: it lists what goes where, but not what is inside each parcel.

  • How we get hold of it. pipeline.to_runner_api() in Python returns it. A wrapper runner gets the pipeline in run_pipeline(pipeline, options), after the job has built it and before any step has run (probe 4), so a job can still be refused. The proto can be written to bytes and read in Java with Beam’s own Java classes (RunnerApi.Pipeline.parseFrom, probe 7).

  • What it contains.

    • Every step’s unique name.
    • Its kind (a urn: beam:transform:read:v1, beam:transform:pardo:v1, …).
    • The Python class it was built from, in an annotation (python_type=apache_beam.io.parquetio.ReadFromParquet).
    • Its inputs and outputs.
    • Its display data: labels such as File Pattern=..., Table=proj:ds.report, schema=id: int64 ....
    • For each collection, whether it is finite or a stream, and its coder (how items are encoded). When items are Beam rows, the coder carries the row schema: the column names and types.

  • What it leaves out.

    • Anything inside a step’s own Python code. Functions are stored pickled (Python’s own way of saving an object, readable only by Python).
    • The columns of plain Python dictionaries, which travel pickled too.
    • A grouping’s keys (beam.GroupBy("id") states no key in the proto).
    • The columns of a Parquet read that did not ask for rows.

    The cost: those checks are either done from what the write states, done by a small Python helper (D2), or refused.

  • A real example. Captured by probe 1 and probe 2 (pipeline.to_runner_api(), Beam 2.77.0), trimmed to the steps the job wrote:

Reading it line by line:

  • ReadOrders is a Parquet read (its python_type) of the folder data/in/orders (its File Pattern). Its output has the columns id and amount, both 64-bit integers that may be empty (the row schema).
  • Positive is the team’s own function (<lambda>). Invaract sees that a step is there, not what it does, as with Java.
  • WriteReport writes Parquet files under data/out/report, with exactly the columns id and amount, both 64-bit integers (the schema label).

Those are the facts the contract above needs.

The same pipeline, read in Java

Section titled “The same pipeline, read in Java”
  • What it is. The bytes of the proto above, parsed by Beam’s Java classes inside the existing beam-adapter test setup.
  • How we get hold of it. The Python side writes the bytes; the Java side reads them (RunnerApi.Pipeline.parseFrom). Display data decodes with RunnerApi.LabelledPayload.parseFrom, and row schemas with SchemaTranslation.schemaFromProto (probe 7).
  • What it contains. Everything above. Probe 7 printed, from Java: ReadOrders urn=beam:transform:generic_composite:v1 dd=[File Pattern=.../data/in/orders/*.parquet, Compression Type=auto] ann=[python_type=apache_beam.io.parquetio.ReadFromParquet] out=[{ id: <INT64> amount: <INT64> }].
  • What it leaves out. One surprise: a beam.Select with a computed field has fields with no type, and Beam’s Java decoder rejects such a schema (Failed to decode Schema). The translator must read the field names itself and treat their types as unknown.
  • A real example. Above. The annotation Invaract’s helper added in Python (invaract:group_keys=id) also arrived intact (probe 5, read back in probe 7).

4. Key design decisions

Section titled “4. Key design decisions”

D1. Where does the check run?

Section titled “D1. Where does the check run?”
  • Options.
    • (a) A Python wrapper runner named by --runner, which checks and then hands the pipeline to the real runner.
    • (b) A proxy in front of a “job service” (the server portable runners such as Flink and Spark accept jobs through).
    • (c) Inside each runner.
  • Recommendation. (a).
  • Why. It is the same design as the Java adapter. It sees every pipeline whatever the runner, Dataflow included (Python’s Dataflow runner does not go through a job service, so (b) would miss it). And probe 4 showed it works: the wrapper got the whole pipeline before anything ran, refused it with exit status 1, and nothing was written.
  • What it costs. A job that picks its runner in code bypasses it, exactly as on Java.
  • What would change my mind. A large share of jobs choosing their runner in code. Then (b) for the portable runners, plus a one-line call for the rest.

D2. Where is the pipeline translated into the IR?

Section titled “D2. Where is the pipeline translated into the IR?”
  • Options.
    • (a) In Java, from the proto alone.
    • (b) In Python, from the live Python objects, sending the IR to Java.
    • (c) In Java from the proto, with a small Python helper that first copies into the proto, as annotations, the few facts only Python can read.
  • Recommendation. (c), starting with an empty helper (pure (a)) and adding facts one at a time.
  • Why. One translator in Java serves Python, Beam YAML and any later SDK (Go), and reuses the Java adapter’s rules: how locations become contract locations, what fails closed, which steps only report (D14). The helper is the escape hatch for facts that live only in Python objects. Probe 5 read a GroupBy’s keys from the live object (_key_fields) and added them to the proto as invaract:group_keys=id, and Java read them back (probe 7).
  • What it costs. A second “IO catalogue”, from Python step types and display labels to reads and writes, next to the Java one. The translation walk (the graph, unknown steps, D14, failing closed) should be shared, which means a small refactor of BeamTranslator to work on steps from either source.
  • What would change my mind. If most checks needed Python-only facts, (b) would be simpler. Probes 1 to 3 say they don’t: locations, write schemas, BigQuery tables and dispositions are all in the proto.

D3. How does Python reach the Java checker?

Section titled “D3. How does Python reach the Java checker?”
  • Options.
    • (a) Run java -jar invaract-beam-checker.jar once per submission, passing the proto as a file and reading the verdict.
    • (b) A long-running local service.
    • (c) The checker compiled ahead of time into a program that needs no Java (GraalVM “native image”), shipped inside the Python package.
  • Recommendation. (a) first; (c) if Java on the submitting machine turns out to be a real obstacle.
  • Why. (a) is the least new machinery. Submission happens once per job, so a JVM start-up of a second or two (UNVERIFIED, to be measured) does not matter. Jobs that use Java steps from Python (SQL, Kafka) already need Java on the submitting machine for Beam’s own expansion service (probe 6 started one).
  • What it costs. Java 11+ wherever jobs are submitted, and two artefacts to install (the Python package and the jar). The package can download the jar the way Beam downloads its expansion service.
  • What would change my mind. Dataflow Flex Template launchers or common schedulers lacking Java (UNVERIFIED).

D4. How do Python’s names become contract locations?

Section titled “D4. How do Python’s names become contract locations?”
  • Recommendation. Reuse the Java adapter’s rules:
    • A read pattern is its folder (data/in/orders/*.parquet is data/in/orders).
    • A write is its prefix’s folder, ignoring the shard template (part-%(shard_num)05d-...).
    • A BigQuery proj:ds.table is proj/ds/table in the bigquery catalog.
    • A Pub/Sub topic is its path.
  • Why. One contract then describes the same dataset whichever SDK a job uses.
  • What it costs. Parsing the Python write’s file-pattern template, which Java writes do not have.

D5. How do Python’s types map to the contract’s?

Section titled “D5. How do Python’s types map to the contract’s?”
  • Recommendation.
    • Row schemas use Beam’s own type names, mapped exactly as on Java (BeamSchemas).
    • Write schemas arrive as pyarrow text (id: int64, tags: list<item: string>); the helper should send them as structured data instead of the text being parsed.
    • A field with no type (beam.Select with a computed field) is a column whose type is unknown, so a contract that declares its type has the write refused, never passed.
  • Why. Parsing pyarrow’s printed form is fragile (it is meant for people), while the helper can read the pyarrow schema object directly.
  • What it costs. A small part of the helper, and a test per pyarrow type.

D6. Transformation-shape rules (required filter, join or group-by columns; no cross join)

Section titled “D6. Transformation-shape rules (required filter, join or group-by columns; no cross join)”
  • Options.
    • (a) Unsupported, refused safely.
    • (b) Group-by from the helper (GroupBy keys); filters and joins stay opaque.
    • (c) Also read Beam YAML’s filter expressions.
  • Recommendation. (a) at first, then (b) and (c).
  • Why. Python has no column-naming filter or join: beam.Filter takes a function, and joins are CoGroupByKey. The suite judges a capability as a whole, so declaring it “partial” with only group-by would make the filter and join scenarios fail, instead of refusing safely as they do when it is declared unsupported. (b) needs the capability split, or a per-rule declaration in the kit.
  • What it costs. Teams that rely on these rules get a clear refusal, not a check, at first.

D7. What cannot be seen, and the policy

Section titled “D7. What cannot be seen, and the policy”
  • Recommendation. As on Java:
    • A step that ends the pipeline without being a recognised write is refused, unless it only reads what writes report or the platform trusts it (D14, --invaract_trusted_steps).
    • A read Invaract cannot locate makes a declared input “unverifiable”, not “missing”.
    • A write whose columns cannot be told is refused when its output declares columns.
    • A function that writes in the middle of a pipeline cannot be seen by any check made before the run.
  • Why. Failing closed (refusing what cannot be checked) is Invaract’s rule everywhere.

D8. How results are reported

Section titled “D8. How results are reported”
  • Recommendation. The Java checker publishes the same validation events as every adapter, through the same sinks. The engine is named beam-python, and the Python SDK version and the delegate runner are passed by the helper. The Python side prints the verdict and raises, so the job’s submit command fails with Invaract’s message.

D9. How CI proves it without secrets

Section titled “D9. How CI proves it without secrets”
  • Recommendation.
    • Python jobs generated from each scenario and run on Beam’s in-process runner (Prism), the way the Java adapter’s BeamScenarioJobs builds Java jobs.
    • Recorded protos as fast unit-test fixtures for the Java translator.
    • A Python version matrix like the Java one.
  • The open part. Python Beam ships no in-memory BigQuery (Java’s FakeBigQueryServices has no Python counterpart in the 2.77.0 package). The BigQuery scenarios, save mode and catalog, need either a “check only, do not run” mode in the kit or a stand-in. Streaming scenarios need a Python stream that ends by itself on Prism (UNVERIFIED).

D10. Language, packaging and release

Section titled “D10. Language, packaging and release”
  • Recommendation.
    • A Python package (invaract-beam on PyPI: the runner, the options and the helper) with its own tests (pytest), lint, and a release step.
    • The Java checker as a runnable jar (the existing beam-adapter, plus a small command-line entry point), published with the other modules.
    • Versions kept in step.
  • What it costs. A new toolchain in the repository’s guardrails: Python tests, coverage and a release job. The repository’s mutation testing is Scala-only, so the Python helper would need its own (mutmut) or be kept small enough not to.

5. Switching it on without touching the job: external attachability

Section titled “5. Switching it on without touching the job: external attachability”

Verdict: Partly, exactly as on Java Beam.

The mechanism. Python Beam accepts a runner by dotted module path (--runner=module.Class; apache_beam/runners/runner.py, create_runner). The wrapper’s options are an ordinary PipelineOptions subclass, parsed from the same command line. Probe 4 ran a job that knows nothing about Invaract like this:

The probe’s version printed INVARACT: contract=contracts/report.yaml delegate=DirectRunner ... nothing has run yet, ran the job, and wrote its output. With a refusing contract it exited with status 1 and wrote nothing. Without the package installed, Beam stopped with ModuleNotFoundError: No module named 'invaract_probe', exit status 1, nothing written. A missing install fails closed.

A Beam YAML pipeline is launched by Beam’s own Python entry point (python -m apache_beam.yaml.main --yaml_pipeline_file=...), so the same flags apply (PREDICTED; the proto it produces was probed, the launch was not).

The settings. Python options are spelled in snake case:

How a job can get around it, and what is not possible.

  • A job that sets its runner in code (PipelineOptions(runner="DataflowRunner"), or options.view_as(StandardOptions).runner = ...) or ignores its command line is not checked. This is the same as Java, and stated in the declaration.
  • A job submitted from a machine without the package fails to start. That fails closed, but means an install step for the platform.
  • A job submitted from a machine without Java cannot be checked (D3).

A blocked run (PREDICTED). If the team changed the write to data/out/report_v2/part, the submit command would fail before anything ran, with the message every adapter prints:

Glossary

Section titled “Glossary”
  • Adapter: the part of Invaract that knows one engine and translates its jobs into the IR.
  • Annotation: a key/value note attached to a step in the portable pipeline (python_type=...).
  • Attach: switch Invaract on for a job, ideally without changing the job’s code.
  • Capability / declaration: one thing an adapter can or cannot do; the declaration is its full list, with a status for each.
  • Coder: how a collection’s items are encoded; a row coder carries the column names and types.
  • Composite step: a step made of smaller steps (a Parquet read is a read plus a conversion).
  • Conformance / scenario: the suite of small engine-neutral jobs; an adapter conforms when each comes out as its declaration says.
  • Cross-language: a Java step used inside a Python pipeline, run by Beam in a Java environment.
  • Display data: labels a step publishes about itself, meant for people (File Pattern, Table).
  • Dry run: run the job unchanged and infer a draft contract from its writes, instead of enforcing one.
  • Enforcement point: where the check runs; here pre-submit-gate, before the job is handed to the engine.
  • Expansion service: the Java server Beam starts so a Python pipeline can include Java steps.
  • Fail closed: refuse what cannot be checked, rather than let it through.
  • Graph / pipeline: the job as a chain of steps and the collections between them.
  • IR: Invaract’s engine-neutral description of a job’s reads, filters, joins, groupings and writes.
  • Lineage: which input columns each output column comes from.
  • Pickled: saved with Python’s own object format, readable only by Python.
  • Portable pipeline / proto: the language-neutral description of a pipeline, in Protocol Buffers.
  • Prism: Beam’s in-process runner in Python 2.77, a small Go program.
  • Runner: the engine a Beam pipeline is handed to (Dataflow, Flink, Spark, Prism).
  • Schema: the column names and types of a dataset.
  • Sink / source: where a write lands / where a read comes from.
  • Transform: one step of a pipeline.
  • Wrapper runner: a runner that checks the pipeline and then hands it to the real one.
  • OUTPUT_LOCATION_MISMATCH: a write lands somewhere other than the contract’s output.
  • MISSING_OUTPUT_FIELD / OUTPUT_FIELD_TYPE_MISMATCH / OUTPUT_FIELD_NULLABILITY_MISMATCH: a declared output column is missing, has the wrong type, or the wrong nullability.
  • UNDECLARED_OUTPUT_COLUMN: with rejectUndeclaredFields, the output has a column the contract does not declare.
  • MISSING_INPUT / UNDECLARED_INPUT: a declared input is not read / an undeclared one is.
  • MISSING_OUTPUT: a declared output is never written.
  • OUTPUT_FORMAT_MISMATCH / OUTPUT_SAVE_MODE_MISMATCH: the write’s format or save mode differs from the contract’s.
  • MISSING_OUTPUT_CATALOG_REGISTRATION: the contract requires a registered table and the write is to a bare path.
  • UNVERIFIABLE_WRITE: a step changes data in a way Invaract cannot check, so it is refused.
  • UNSUPPORTED_CONTRACT_FEATURE: the contract relies on something this adapter declares it cannot check, so it is refused.
  • INVALID_CONTRACT: the contract itself is malformed.

Retrospective

Section titled “Retrospective”

The adapter was built the same day (docs/BEAM_PYTHON_ADAPTER.md) and its conformance run, real Python pipelines through the real package and checker, gave: 42 of 53 scenarios conform (29 by doing the check, 13 by refusing safely), 11 skipped, against a forecast of 24 checked, 5 partly, 13 refused, 11 skipped. Every ⚠️ became a ✅, and no ✅ or ❌ changed.

What the forecast got wrong, and why:

  • BigQuery (rows 11, 26, 27) did not need a stand-in. The check happens before the pipeline is handed to a runner, so the conformance job hands a checked BigQuery pipeline to a runner that runs nothing. The survey assumed the kit had to run the write; it only has to reach the hand-over.
  • Streaming (rows 50, 51) works, but not the way forecast. A file stream (fileio.MatchContinuously) keeps its pattern in pickled code, so the stream’s read is not located: the declared input is reported unverifiable rather than read. That is why read.streaming is declared partial, a limit the survey did not foresee. Pub/Sub reads are located.
  • No Python-side helper was needed (D2). Every fact the checks use is in the portable form; the helper the survey kept as an escape hatch was never written, which leaves the Python package with no logic to maintain.
  • A refusal could hide the reason that mattered. With shape rules unsupported, a pipeline combining collections with CoGroupByKey was refused as unverifiable before the core said the rule was unsupported. Both Beam adapters now refuse an unsupported contract first (VerificationPipeline.requireSupported).
  • Unknown coders do not fail; their order is not fixed. Java rehydrates a pickled Python coder as UnknownCoderWrapper, and a proto map has no order, so a step’s inputs are sorted by tag. Neither was foreseen; both were found by the first tests.
  • Resolved unverified items. The JVM checker answers in about 0.9 s. Python’s in-process runner (Prism) runs the conformance jobs to completion. A required pyarrow column prints not null.
