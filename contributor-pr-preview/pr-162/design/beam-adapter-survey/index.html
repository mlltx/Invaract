Apache Beam adapter survey

Status: survey, and the adapter has since been built (docs/BEAM_ADAPTER.md; see the Retrospective at the end). This document is what the go-ahead was given on; it is kept as written, with the retrospective saying where reality differed. Engine surface surveyed: the Beam Java SDK, version 2.77.0, run on Beam’s in-process test runner (the DirectRunner). Written: 2026-10-13. Evidence checked: 2026-10-13. Source of each claim: section 10, “Evidence log”.

The short version

Section titled “The short version”

What it would be. Before a Beam job starts, Invaract would read the job’s description (Beam calls it the pipeline: the list of steps the job will run and how data flows between them), compare it with the data contract, and refuse to start the job if it breaks the contract. It cannot stop a job that is already running, and it cannot look inside the code a team writes for its own steps, so it checks the shape of a job (what it reads, where it writes, what columns and types come out) and not what the team’s own code does to individual values.

How much of the suite it is expected to pass. Of the suite’s 51 scenarios: 21 by doing the check, 2 partly (streaming, not yet proven possible), 17 by refusing safely, and 11 skipped because they do not apply or are declared out of reach. Details in section 7.

Can it be switched on without changing the job’s code? Partly. A platform team adds one flag (--runner=...) and one jar to the job’s launch command; the job’s source stays as it is, provided the job passes its command line to Beam the usual way and does not pick its own runner in code. Both halves were tested on a real Beam pipeline. Section 5.

The biggest risks.

  1. A job that chooses its runner in its own code, or ignores its command line, slips past the check. Measured, not guessed: a probe job that did this ran unchecked.
  2. A Beam job’s own functions are opaque. The adapter will see that a job filters, joins or groups, but not on which column, so the “plan-shape” rules (required filter, required join keys, required group-by) cannot be checked and would be refused as unsupported. If those rules matter to the first users, the adapter’s value drops.

Decisions I need from you. (Each is explained in section 4; a one-line answer is enough.)

  1. Build it at all, scoped to the Java SDK, file formats (Parquet, Avro, text) and the in-process runner first? Recommend yes.
  2. Accept “check before submit” (cannot block mid-run, cannot see inside functions)? Recommend yes.
  3. Accept “partly” attachable, and also offer an explicit one-line call a job author can add? Recommend both.
  4. A text file write cannot say whether it is CSV or JSON: let a text write satisfy a declared csv/json/text? Recommend yes, disclosed as a limit.
  5. A collection with no visible schema (plain Java objects): refuse the write rather than pass it? Recommend refuse.
  6. A pipeline step that writes by itself and is not a known writer: refuse as unverifiable, accepting some false alarms? Recommend refuse.
  7. Scala for the adapter, with one small Java file only if Beam cannot load the Scala runner class? Recommend yes.

How to read this document

Section titled “How to read this document”
  • What “conforming” means here. Invaract has a conformance suite: 51 small, engine-neutral jobs (“scenarios”) every adapter is run against. An adapter declares what it can and cannot do (its declaration), and each scenario must come out the way that declaration promises. Refusing safely is conforming: if an adapter says “I cannot check this”, the suite expects it to refuse any contract that depends on it, rather than let the job through unchecked. So a ❌ below is a limit to understand, not a failing grade.
  • Forecast marks. ✅ expected to do the check and produce what the suite expects. ⚠️ only partly, or with a workaround, or depends on something not yet verified. ❌ cannot do the check, so the suite expects a safe refusal or a skip. ➖ does not apply to this engine.
  • Confidence. High: shown by a probe I ran. Medium: stated by the engine’s own source or documentation, or each part was probed but the whole has not been assembled. Low: inferred. A forecast is a forecast: nothing here has been run as an adapter.
  • Words. Each technical term is explained where it first appears and again in the glossary at the end.
  • “Probe”. A throwaway program I wrote and ran against real Beam to see what it reveals. The programs are not committed; what they printed is quoted below.

1. What Invaract asks of an engine

Section titled “1. What Invaract asks of an engine”

The contract, and the check

Section titled “The contract, and the check”

A data contract is a small YAML file that says what a dataset must look like and what a job may do with it: where it may read, where it must write, which columns come out and of what types, and a few rules. For example:

Invaract’s job is to look at a data job before it writes anything, and compare what the job is about to do with the contract. If they disagree (it writes to the wrong place, a column has the wrong type, a declared input is never read) Invaract stops the write and prints why. Each kind of disagreement has a name, called a violation type (OUTPUT_LOCATION_MISMATCH, MISSING_INPUT, and so on; the glossary lists those used below).

The engine-neutral model (the “IR”)

Section titled “The engine-neutral model (the “IR”)”

Every engine describes a job in its own vocabulary. To avoid writing every check once per engine, Invaract translates each engine’s description into one small engine-independent description of reads, filters, joins, groupings and writes. This is the IR (“intermediate representation”). All the checking code works on the IR, and never sees the engine. A three-step job as the IR holds it:

For Spark, the translation takes Spark’s own query plan (a tree Spark builds describing what a query will do, available before it runs) and converts each node. An adapter is the piece of code that does this translation for one engine and installs the check at the right moment. The Beam adapter’s central job is therefore: get a description of the Beam job, and turn it into this IR.

Capabilities, declarations and scenarios

Section titled “Capabilities, declarations and scenarios”

Invaract names 30 capabilities: things an adapter might be able to do (“recognise a batch read”, “check column types”, “check required-filter rules”). Each adapter publishes a declaration: for every capability, supported, partial, unsupported or not-applicable, with a note. The conformance suite then runs 51 scenarios and checks that the adapter behaves as its own declaration says. Section 7 forecasts both.

2. The engine in plain words

Section titled “2. The engine in plain words”

Apache Beam is a toolkit for writing data jobs once and running them on different engines (Google Dataflow, Flink, Spark, or Beam’s own in-process runner for testing). A job is written in Java (also Python and Go; only Java is surveyed here) as a pipeline:

  • A PCollection is a named bundle of data flowing between steps (a “parallel collection”: think of it as a table that may be spread over many machines). It is either bounded (finite, a batch) or unbounded (a stream). Each has a coder (how its items are turned into bytes), and sometimes a schema (column names and types).
  • A transform is a step that takes collections and produces collections: read a file, filter, join, group, write. Transforms nest: a composite transform (for example “Parquet read”) is made of smaller ones, down to primitive ones the engine actually executes.
  • A source reads from outside (a file, a table) and a sink writes to outside.
  • A runner is the piece that actually executes a pipeline on an engine. The job picks it with --runner=.... The DirectRunner runs the pipeline inside the same Java process, which is what makes it usable in tests.
  • The team’s own logic lives in functions (Beam calls them DoFns, or lambdas passed to MapElements and Filter). To Beam these are opaque compiled Java code.

The job is constructed first (each .apply(...) call adds a step to an in-memory graph, nothing runs), then pipeline.run() hands that finished graph to the runner, which executes it. The moment between “constructed” and “running” is where Invaract can look and stop things.

3. How the adapter would get hold of a job

Section titled “3. How the adapter would get hold of a job”

Everything below was observed with Beam 2.77.0 on the DirectRunner, with Java 21, on 2026-10-13. The “real example” in each block is verbatim program output, shortened only where marked ....

The pipeline graph

Section titled “The pipeline graph”
  • What it is. The list of steps the job will run, and which collection each step reads and writes: like a recipe that exists before anyone starts cooking.
  • How we get hold of it. Pipeline.traverseTopologically(visitor), a public Beam call that walks every step in an order where inputs come before the steps that use them. It can be called as soon as the job is constructed, before anything runs, from the code of a wrapper runner (see “The hook” below).
  • What it contains. For every step: its full name, its Java class (for example AutoValue_ParquetIO_Read), the collections it consumes and produces, and each collection’s boundedness and schema when it has one. Composite steps contain their children, so each file read is one step with a handful of internals beneath it.
  • What it leaves out. What a team’s function does. A Filter appears as a filter, but its test is a compiled predicate (display predicate = Filter.predicate in the probe below is all it says). Join keys and group-by fields are held in non-public state (Beam’s own source; not shown by any public call I found).
  • A real example. A Parquet read followed by a Parquet write, captured by my graph probe (IoProbe), top level only:

Reading it: the first block is the step named ReadParquet. filePattern is where the data comes from (in/orders/*.parquet, which the contract spells as the folder in/orders). schema is the Avro schema the job told the reader to expect: id is a required long, amount a nullable long (["null","long"] is Avro’s way of saying “may be null”). The second block is the write. Notice it states no location and no schema in its own display data; the next two blocks show where those come from.

A step’s display data

Section titled “A step’s display data”
  • What it is. A short label sheet each Beam step can fill in about itself, meant for monitoring screens.
  • How we get hold of it. DisplayData.from(node.getTransform()), public, available at construction time.
  • What it contains. Whatever the step’s author chose to publish. TextIO publishes its file prefix and pattern, ParquetIO.read its file pattern and Avro schema, BigQueryIO its table, write disposition and schema.
  • What it leaves out. Anything the author did not publish. FileIO.write (which the Parquet sink runs on) publishes nothing but the name of its sink class.
  • A real example. Captured by the opaque-filter probe, the text write at the end of a job:

Reading it: filePrefix is where the text file will be written. Beam already turned the relative path I gave (out/opaque) into an absolute one, so the adapter must compare locations after making both sides absolute. A read by contrast states its pattern as given. This asymmetry is why the location rule is in decision D3.

The write’s sink

Section titled “The write’s sink”
  • What it is. The object inside a file write that knows how to write the files (and where).
  • How we get hold of it. ((WriteFiles) node.getTransform()).getSink().getTempDirectoryProvider().get(), all public calls, at construction time. For a FileIO write the temporary folder defaults to the output folder.
  • What it contains. The destination folder.
  • What it leaves out. If the job sets a separate temporary folder (withTempDirectory), that folder is what this call returns, and it is not the destination. The adapter cannot tell the two apart from this call alone (UNVERIFIED how to detect it; cheapest check in section 10).
  • A real example. Captured by SinkProbe:

Reading it: the Parquet write’s destination is out/report/. The text write’s temporary folder is out/, the parent of its prefix out/text, so for text writes the adapter reads the prefix from display data instead.

A collection’s coder and schema

Section titled “A collection’s coder and schema”
  • What it is. The description of one collection’s items: how to encode them, and for structured data, the columns. It is how the types of a Parquet write’s output are known even though the write step states none.
  • How we get hold of it. PCollection.getCoder() and PCollection.getSchema(), public, at construction time. A collection of Avro records carries its Avro schema in its coder; a collection of Beam rows carries a Beam schema.
  • What it contains. Column names, types and nullability.
  • What it leaves out. A collection of plain Java objects (SerializableCoder) has no schema at all. A collection produced by a lambda must be given an explicit coder or schema by the job, or Beam refuses to build the pipeline, so that case is at least a clear signal.
  • A real example. Captured by CoderProbe, on the output of the Parquet read above:

Reading it: the collection’s coder carries the full Avro schema, and Beam’s own library converts it to id: INT64 NOT NULL, amount: INT64 (nullable), which map directly to the contract’s long, required and not. Note this is the schema the job states it expects, not the schema of the files on disk. Beam never opens the files before the job runs, so a mismatch between a job’s declared read schema and the real files is not something this check can see (it would surface at run time as a read error).

Bounded and unbounded sources

Section titled “Bounded and unbounded sources”
  • What it is. Whether a collection is finite (a batch) or never-ending (a stream).
  • How we get hold of it. PCollection.isBounded(), public, at construction time.
  • What it contains. BOUNDED or UNBOUNDED.
  • What it leaves out. Nothing relevant, but see section 7.2: whether the in-process runner can run a stream to completion for a test is unverified.
  • A real example. Captured by the probe that reads text files and a counting generator:

Joins and groupings

Section titled “Joins and groupings”
  • What it is. How Beam spells “combine two collections by a key” and “aggregate by a key”.
  • How we get hold of it. The same graph walk. A join appears as one composite step with two inputs; a grouping as one composite step with a key/value output.
  • What it contains. That a join or grouping happened, and the output columns (lhs, rhs; key, value).
  • What it leaves out. The key fields. They are held in non-public state, so a rule such as “must group by customer_id” cannot be checked from public calls. Supporting it would need reflection into Beam’s internals, which can break on any Beam upgrade, so the draft declares these rules unsupported (section 7).

A step Beam cannot see into

Section titled “A step Beam cannot see into”
  • What it is. A function that does something Beam does not model, such as calling a web service or inserting into a database.
  • How we get hold of it. It shows up in the same graph walk, as a step with no declared destination.
  • What it contains. The step’s name and the Java class of the function.
  • What it leaves out. Everything it does.
  • A real example. A function reading a BigQuery table and pushing each row somewhere unknown:

Reading it: the step consumes the table and produces a collection nobody uses. The only hint is the class name of the function. The adapter would treat “a last step that is not a recognised writer” as an unverifiable write and refuse it (decision D6). A function that writes in the middle of a pipeline and passes data on is invisible; that is a limit of every pre-run check on Beam (section 9).

BigQueryIO steps

Section titled “BigQueryIO steps”
  • What it is. Beam’s built-in BigQuery reader and writer.
  • How we get hold of it. The same graph walk. The pipeline can be constructed without contacting Google (my probe built one with no network access to Google), so a check can run with no credentials.
  • What it contains. The table, the schema given to the writer, the write disposition (append, truncate, fail if not empty) and create disposition.
  • What it leaves out. Whether the table exists and what its real schema is.
  • A real example.

This is why check.saveMode and check.catalogRegistration are marked could be supported later for BigQueryIO only (they have no meaning for file writes). The first version does not include BigQueryIO.

The hook: a wrapper runner

Section titled “The hook: a wrapper runner”
  • What it is. A runner that does not execute anything itself: it receives the finished pipeline, looks at it, and then either refuses or hands it to the real runner.
  • How we get hold of it. The job’s command line names it: --runner=<our class>. Beam finds the class and calls its static fromOptions(options) method; later pipeline.run() calls the class’s run(pipeline) method, still before any data moves. Beam options such as --invaractContract=... are declared in an interface and registered through Java’s ServiceLoader (a standard “find all plugins on the classpath” mechanism), so the job needs no code to know about them.
  • What it contains. The full pipeline and the options (which include the job name).
  • What it leaves out. A running pipeline: once run hands over, Invaract cannot intervene.

4. Key design decisions

Section titled “4. Key design decisions”

D1. Where does the check sit?

Section titled “D1. Where does the check sit?”
  • Options. (A) Wrapper runner: gate before submit. (B) Walk the pipeline from a hook in the job’s own code. (C) Wrap each runner separately. (D) Watch execution and report only.
  • Recommendation. A, and offer B as an explicit one-line call (InvaractBeam.verify(pipeline)).
  • Why. A is the only place where nothing has started, so the check can truly block, and it can be attached from the command line. B covers jobs that choose their runner in code. C repeats work per runner; D cannot block.
  • What it costs. Declared enforcement point is pre-submit-gate, not in-engine-blocking: Invaract can refuse to start a job but not stop one mid-run.
  • What would change my mind. Evidence that real jobs mostly choose their runner in code (then B becomes the main route and A the convenience).

D2. How does the adapter get hold of the job and turn it into the IR?

Section titled “D2. How does the adapter get hold of the job and turn it into the IR?”
  • Options. (A) Public graph walk plus display data, coder and sink calls (section 3). (B) Also read Beam’s private fields by reflection. (C) Convert the pipeline to Beam’s portable (language-neutral) protobuf form and read that.
  • Recommendation. A for the first version; revisit C later.
  • Why. A uses only public calls that survive upgrades. B would make join keys and group-by fields readable but breaks on any Beam upgrade. C (PipelineTranslation.toProto) is public and standard, but I have not probed what it exposes (UNVERIFIED), so it is a candidate for closing the plan-shape gap rather than a reason to delay.
  • What it costs. No plan-shape rules, no column lineage, no value analyses in version 1 (section 7).
  • What would change my mind. A probe showing the portable form carries join and group fields.

D3. How do Beam names become the locations a contract uses?

Section titled “D3. How do Beam names become the locations a contract uses?”
  • Options. (A) Compare absolute paths after normalising both sides. (B) Compare exactly as written.
  • Recommendation. A, plus the rule that a read pattern such as in/orders/*.parquet matches the contract folder in/orders when the pattern’s folder is the contract’s location.
  • Why. The graph probe showed reads state the pattern as given while writes state absolute paths. Invaract’s location matching is pluggable per adapter (LocationMatching), so this is adapter-side code, not a core change.
  • What it costs. A read of in/orders/2024-*.parquet would match a contract for in/orders; precise enough to catch a wrong folder, not a wrong file. A contract naming a single file location also matches only that file.
  • What would change my mind. Real users writing contracts per file rather than per folder.

D4. How do Beam and Avro types map to the contract’s types?

Section titled “D4. How do Beam and Avro types map to the contract’s types?”
  • Options. (A) Map from the collection’s coder (Avro) or Beam row schema. (B) Require the job to publish types some other way.
  • Recommendation. A, using Beam’s own AvroUtils.toBeamSchema and a table from docs/ENGINE_RESEARCH_BIGQUERY_BEAM.md.
  • Why. Shown to work (section 3): INT64 NOT NULL and INT64 come out correctly. Arrays and maps are in the same library conversion.
  • What it costs. Beam has narrower integers (INT16, INT32) than BigQuery; the research doc covers the table. Types Avro cannot express (interval, json, geography, time) are reported as a type mismatch, which is what scenario 5 wants.
  • What would change my mind. A real job using Beam row schemas with logical types the library does not convert.

D5. How are writes described, and what are the defaults?

Section titled “D5. How are writes described, and what are the defaults?”
  • Options. (A) The format is the writing transform (ParquetIO is parquet, AvroIO is avro, TextIO is text). (B) Also infer from the file suffix.
  • Recommendation. A. For text, a write satisfies a declared csv, json or text (see the decisions list).
  • Why. The transform is the only reliable signal. File-based Beam writes have no append/overwrite choice at all, so check.saveMode is declared unsupported for them: a contract that declares a save mode is refused safely.
  • What it costs. A text write against a csv contract is passed even if the lines are not CSV.
  • What would change my mind. A text write transform that publishes its delimiter or format.

D6. What cannot be seen, and what happens then?

Section titled “D6. What cannot be seen, and what happens then?”
  • Options. (A) Refuse a last step that is not a recognised writer (UNVERIFIABLE_WRITE). (B) Allow it with a warning. (C) Let the contract list steps to allow.
  • Recommendation. A for version 1.
  • Why. Invaract’s rule is to fail closed: if it cannot tell, the answer is no. My probe showed such a step is recognisable as a final step that no recognised writer owns.
  • What it costs. A pipeline that ends in a metrics-only or logging step is refused until an allow-list exists.
  • What would change my mind. Real jobs with legitimate terminal steps, in numbers.

D7. How are results reported?

Section titled “D7. How are results reported?”
  • Options. Same as Spark: a validation event per check and a write event per write, to the configured sinks.
  • Recommendation. Reuse verification-core’s sinks and events; name the engine beam and the job from options.getJobName() (the probe printed job-root-1013065800-1d5e447d).
  • Why. The events already carry engine and job. No new format.
  • What it costs. On Beam, the “write” event is published at the gate, before the write happens, so a row count is not available (Spark’s is). A field left empty, not a wrong value.
  • What would change my mind. A consumer that needs row counts: they would have to come from Beam metrics after run.

D8. Language and packaging

Section titled “D8. Language and packaging”
  • Options. (A) Scala, in a new module beam-adapter, package com.invaract.beamadapter. (B) Java.
  • Recommendation. A; add one small Java file only if Beam cannot load the Scala runner class.
  • Why. Same language as the rest of the engine and the SPI. Beam requires a static fromOptions on the runner class; a Scala companion object normally generates one (UNVERIFIED for Beam’s reflective lookup; cheapest check: a ten-line class and the wrapper probe).
  • What it costs. A Hadoop and Parquet dependency set the probe needed (hadoop-client and beam-sdks-java-io-parquet), which is heavy; keep them optional so a text-only user is not forced to take them.
  • What would change my mind. The static-forwarder check failing in an awkward way.

D9. How does CI prove it without secrets?

Section titled “D9. How does CI prove it without secrets?”
  • Options. (A) The DirectRunner with local files and the kit’s scenarios. (B) A BigQuery emulator. (C) A real project on a schedule.
  • Recommendation. A for the file formats; BigQueryIO graphs are constructible without credentials (probed), so the check is testable the same way, while “the write really worked” would need B or C and is out of scope.
  • Why. Real engine in process, the same level of evidence Spark has with local[*].
  • What it costs. Nothing about real Dataflow or Flink is proven.
  • What would change my mind. A user whose only runner is Dataflow.

5. Switching it on without touching the job: external attachability

Section titled “5. Switching it on without touching the job: external attachability”

Verdict: Partly. A platform team can turn it on, tested end to end on a probe job, if the job passes its command line to Beam and does not set its own runner. Otherwise they cannot.

The mechanism. A runner class named on the command line (--runner) wraps the real runner. The Invaract settings are Beam options, declared in an interface and registered through Java’s ServiceLoader, so Beam accepts them as if they were its own. The jar is added to the job’s classpath. The job’s source is untouched. Example (the shape the probe used; class and flag names are PREDICTED for the real adapter):

The settings. Beam option names are the setting name with invaract in front and the first letter capitalised (getInvaractContract becomes --invaractContract; verified by the probe reading contract=pass).

rejectUndeclaredInputs / rejectUndeclaredFieldsstricter checking--invaractRejectUndeclaredInputs=true and ...Fields=trueYes
computeFingerprint / staticDataQuality / roleConsistencyoptional analysesan option exists, but turning one on gets a safe refusalNo: declared unsupported

How a job can get around it, and what is not possible.

  • A job that calls options.setRunner(...) in its own code overrides --runner. Measured: the wrapper never ran.
  • A job that builds its options without reading its command line (PipelineOptionsFactory.create()) never sees the flags at all. (My graph probes did exactly this.)
  • A job that launches another pipeline from inside a function is invisible to the outer one.
  • Not possible: attaching to a job whose source we do not control and that does either of the first two. The only route there is the explicit call (D1, option B), which is a code change.
  • UNVERIFIED: whether a wrapper can hand over to production runners (Dataflow, Flink) with their own required options. The mechanism is the same; the delegate’s setup was only run for the DirectRunner.

Glossary

Section titled “Glossary”
  • Adapter. Code that connects Invaract to one engine: gets the engine’s description of a job, translates it to the IR, and installs the check.
  • Pipeline. A Beam job: a graph of steps that read, transform and write data. Built first, run later.
  • Graph. The steps and the data flowing between them, as boxes and arrows.
  • PCollection. The data flowing between two steps; bounded (finite) or unbounded (a stream).
  • Transform. One step in a pipeline. Composite transforms contain smaller ones; primitive ones are executed.
  • Source / sink. A step that reads from, or writes to, the outside world.
  • Runner. The piece that executes a pipeline on an engine. --runner= names it on the command line.
  • DirectRunner. Beam’s in-process runner, used for tests; no cluster needed.
  • Wrapper runner. A runner that checks a pipeline and hands it to the real runner, or refuses.
  • Coder. How a collection’s items are turned into bytes; for Avro records it also carries their schema.
  • Schema. The columns of a collection with their types and nullability.
  • Display data. Labels a step can publish about itself for monitoring; includes file paths.
  • Function / DoFn. The team’s own code inside a step. Opaque to Beam.
  • ServiceLoader. Java’s standard way of finding plugins listed in a jar, so no code in the job is needed.
  • Fail closed. When Invaract cannot tell whether something is safe, it refuses, rather than allowing it.
  • IR. Invaract’s engine-neutral description of a transformation.
  • Capability / declaration / scenario. A thing an adapter might do; the adapter’s statement of what it can do; one small job in the conformance suite.
  • Enforcement point. Where the adapter can stop a job: inside the engine, before submission, or not at all.
  • OUTPUT_LOCATION_MISMATCH. The job writes somewhere other than the contract’s declared output.
  • MISSING_INPUT / UNDECLARED_INPUT. A declared input is never read / a dataset the contract does not declare is read (strict option).
  • MISSING_OUTPUT_FIELD. A declared output column is not produced.
  • OUTPUT_FIELD_TYPE_MISMATCH / OUTPUT_FIELD_NULLABILITY_MISMATCH. An output column has a different type / can be null where the contract says required.
  • UNDECLARED_OUTPUT_COLUMN. An output column the contract does not declare (strict option).
  • OUTPUT_FORMAT_MISMATCH / OUTPUT_SAVE_MODE_MISMATCH. Written in another format / with another save mode.
  • MISSING_OUTPUT_CATALOG_REGISTRATION. The contract requires a catalog table; the write is to a bare path.
  • RULE_*_VIOLATION. A transformation-shape rule (required filter, join columns, group-by, no cross join) is broken.
  • DATA_QUALITY_VIOLATION / ROLE_CONSISTENCY_VIOLATION. A provable value constraint is broken / a dataset is used contrary to its declared role.
  • UNVERIFIABLE_WRITE. A step changes data but cannot be translated, so it is blocked.
  • UNSUPPORTED_CONTRACT_FEATURE. The contract needs something the adapter declared unsupported, so it is refused.
  • INVALID_CONTRACT. The contract itself is unsound.

Section titled “Retrospective”

Added after the adapter was built (2026-10-13), as .claude/skills/survey-engine-adapter asks, so the next survey is better.

The forecast against the run. Of the 51 scenarios, the adapter’s own conformance run gave: 21 conform by doing the check, 17 by refusing safely, 13 skipped. That is the forecast’s 21 and 17 exactly. The 13 are the forecast’s 11 plus the two streaming scenarios (48, 49), which the survey marked ⚠️ and which became skipped: the adapter declares streaming unsupported until a streaming job is run under the kit, because a read shape (FileIO.match().continuously) it does not yet recognise is needed. Every ✅, every ❌ and every ➖ held.

What the survey got wrong or missed.

  1. A Parquet write is not a transform of its own. The survey described a write step that states its destination and format, by analogy with ParquetIO.read. In fact a Parquet write is FileIO.write().via(ParquetIO.sink(...)), which publishes neither. The destination and the sink are read from non-public members of FileIO.Write by reflection (confined to one method, tested, failing closed). The survey’s “public calls only” claim (D2) holds for reads, the graph, coders and schemas, not for this.
  2. D3’s location rule needed a second case. A prefix write (TextIO.write().to("out/text")) has no folder; the adapter reports the prefix.
  3. D5’s text rule was implemented as a rewrite of the reported format (a text write is reported as the text-family format the contract declares), because the format check compares names exactly.
  4. The kit had a latent bug the survey could not have seen: an adapter that declares an analysis unsupported was still judged on that analysis’s results (PR #147).
  5. Unverified items settled: the Scala fromOptions is found by Beam; empty Parquet inputs read fine; reflection can tell a separate temporary directory from the destination; reads beneath an opaque step stay reachable. Still open: streaming, production runners, the portable form, a short runner name, other Beam versions.

A second pass (2026-10-15) closed the rest. Streaming (the two ⚠️ scenarios now conform, run to completion in-process), BigQueryIO (save mode and catalog checked, the scenarios run on Beam’s in-memory BigQuery, so check.saveMode and check.catalogRegistration became partial: 40 of 51 conform), KafkaIO, JdbcIO, Pub/Sub, a hand-over to Flink, --runner=Invaract, Beam 2.60 to 2.77 in CI. The portable form was probed and does not help (docs/BEAM_ADAPTER.md, friction log 19). Probing common pipeline shapes found what the survey had not foreseen: the FileIO.match() read idiom hid its read, a partitioned glob pattern and a projected read were mislocated or mis-schema’d, and an Impulse-driven source was invisible (all fixed); and two shapes that are refused but should perhaps not be, left as a decision (D14). For the next survey: forecast every IO the engine’s users actually use, not only file IO, and probe what the engine’s own built-in transforms expand to.
