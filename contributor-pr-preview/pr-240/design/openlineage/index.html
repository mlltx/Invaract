OpenLineage: Design

Invaract publishes what it verified as OpenLineage run events, so the lineage tools a data platform already runs (Marquez, DataHub, Atlan, Collibra, OpenMetadata, …) show, for every run of every job, which datasets it read and wrote, their columns, how each output column was derived, and whether the write passed its contract. MISSION.md §5: OpenLineage stays the ecosystem’s interoperability layer for lineage; Invaract adds the verification that gives those relationships confidence. This document is the design and the record of how it was built.

1. Goals and non-goals

Section titled “1. Goals and non-goals”

Goals:

  1. One implementation, every engine. The mapping, the delivery and the settings live in verification-core; an adapter gets OpenLineage by doing what it already does (calling VerificationPipeline and AttachSetup). Spark, Beam (Java and Python) and plain Python jobs publish it from the first commit, and an adapter added later gets it by default.
  2. Attached by configuration alone (CLAUDE.md’s External Attachability Requirement): neutral settings in InvaractConf, spelled by each engine its own way (spark.invaract.openLineageUrl, --invaractOpenLineageUrl, --invaract_open_lineage_url, INVARACT_OPEN_LINEAGE_URL).
  3. Checked by the conformance kit on every adapter: a new capability, reporting.openLineage, which every adapter declares, and scenarios that hold each adapter’s events to the OpenLineage specification and to what the adapter declares (column lineage only from an adapter that declares it).
  4. Cheap and safe to turn on. Nothing on the job’s own thread but handing a reference to a bounded queue; mapping, serialization and delivery happen on one background thread. A slow, failing or unreachable endpoint never fails, blocks or slows the job, and memory stays bounded however long the endpoint is down.
  5. Correct to the specification, held to it by tests: every event the tests produce is validated against the official OpenLineage JSON Schema (pinned, vendored), dataset names follow the OpenLineage naming conventions, and Invaract’s own facets have published schemas.
  6. Honest. A fact Invaract does not know is left out, never guessed: no column lineage from a plan Invaract cannot see into (a Python job’s own code, a Beam step’s function), no completion where the adapter saw none.

Non-goals (this version):

  • Replacing an engine’s own OpenLineage integration (openlineage-spark). The two can run side by side; section 9 says how they relate.
  • A Kafka transport. HTTP covers Marquez and every hosted backend; a file transport covers a log-shipping pipeline. Kafka can follow as an opt-in module the way notification-kafka did.
  • Consuming OpenLineage (reading other tools’ lineage to verify against).

2. What is published

Section titled “2. What is published”

2.1 Runs

Section titled “2.1 Runs”

One OpenLineage run per Invaract run: a Spark application, a Beam pipeline submission, a Python job’s run. The specification requires each run to have one START and one terminal event (COMPLETE, FAIL or ABORT):

WhenOpenLineage eventCarries
The run’s first Invaract eventSTARTjob and run facets
Each contract check of a writeRUNNINGthat write’s inputs and output, with their facets; on a refused write, the errorMessage run facet
Each completed write (Spark, Python)RUNNINGthe output, with outputStatistics, datasetVersion, lifecycleStateChange
The run endsCOMPLETE, or FAIL when a write was refusedthe run’s totals (invaract_run facet)

RUNNING events let a backend show a long Spark application’s lineage while it runs, and a RUNNING event is never needed for correctness: OpenLineage backends merge the inputs and outputs of every event of a run. For fewer requests, emission=endOfRun sends only START and the terminal event, the terminal one carrying every dataset seen.

The run ends when the adapter says so - NotificationSink.endRun(job), a neutral signal every wrapping sink passes on and every other sink ignores (a JobSummaryEvent or DryRunSummaryEvent ends it too) - or, failing that, when the process ends (a JVM shutdown hook, bounded by shutdownTimeoutMs). A run that saw a refused write ends FAIL; otherwise COMPLETE. Where each adapter ends it:

AdapterEnds the run
Sparkat application end: DeclaredOutputs, already the end-of-application hook for check.outputsWritten, calls endRun after any MISSING_OUTPUT it reports (and for a job discarded unjudged)
Beam JavaInvaractRunner.run, in a finally: the pipeline was refused, or checked and handed to its runner (for a blocking runner, finished)
Beam PythonPortableCheck.run, in a finally: the checker’s verdict is the end of Invaract’s part of the run
Python I/Othe run’s end (finish/published, or the checker’s close at end of input), after the JobSummaryEvent

The kit holds every adapter to it (section 7): a run with no terminal event within 30 seconds of the job returning is a divergence. A process killed outright (SIGKILL, os._exit) runs no hook: its run has no terminal event, which OpenLineage backends show as still running - the honest picture of a run nobody saw end.

Run identity. OpenLineage requires a UUID. The run’s id is a name-based UUID (version 5) of the engine and Invaract’s own run id (JobInfo.runId: Spark’s application id, Beam’s job id, the Python run’s id), so every event of a run, from every process that publishes for it, carries the same id, and the same run published twice is the same run. Once a run has ended, a completed write reported for it afterwards (Spark reports one from a listener thread, which can trail the end) is dropped rather than reopening the run, which OpenLineage’s one-terminal-event rule forbids. A new check under the same Invaract run id - a process whose engine gives its runs no id of their own runs one after another under the same key - is a new run: its id is the UUID of the key and its generation (<runId>#1, #2, …), still deterministic.

Job identity. namespace (setting openLineageNamespace, else the configuration file’s namespace, else the OPENLINEAGE_NAMESPACE environment variable, else default, OpenLineage’s own default) and name: the job’s stable id (jobId), else the engine’s name for the job, else the contract’s id. A configured jobName wins over all three.

Parent run. When the job runs inside an orchestrator that publishes OpenLineage itself (Airflow, Dagster), the parent run facet links the two: from the configuration file (parent.runId, parent.job.namespace, parent.job.name) or from the OPENLINEAGE_PARENT_ID environment variable (<namespace>/<name>/<runId>, the form Airflow’s integration sets).

2.3 Facets

Section titled “2.3 Facets”

Standard facets (OpenLineage 2-0-2, the versions pinned in verification-core/src/test/resources/openlineage/):

Invaract’s own facets, each with a JSON Schema published by the docs site (docs-site/public/schemas/openlineage/1-0-0/):

  • invaract_contract (output dataset): the contract (id@version), the dataset’s name in it, the verdict (PASSED, FAILED), every violation (type, message, column, expected, actual, remediation), the inputs it could not verify, and the transformation fingerprint when one was computed.
  • invaract_run (run): the adapter, how it attached (enforce, dryRun), and on the terminal event the run’s totals (checks passed and failed, violations, writes).

2.4 Scope settings

Section titled “2.4 Scope settings”

What is published is configurable, for cost and for privacy: facets.disabled (a comma-separated list of facet names, for instance columnLineage,schema), schema.maxFields and columnLineage.maxFields (larger schemas and lineage are cut to that many fields), failuresOnly=true (only runs with a refused write publish at all - for a team that wants lineage tools to show problems only), emission=perCheck|endOfRun.

A setting that cannot be used (an unknown transport, a number that is not one, an apiKeyEnv naming a variable that is not set when one was asked for explicitly) fails the job at start-up under enforcement, as a broken notification sink does, and is said once and ignored in dry-run mode, whose promise is never to fail a job.

OpenLineage publishing composes with notifyConfig: both can be on, and they never share a failure.

4. Architecture

Section titled “4. Architecture”
  • WriteLineage (verification-core): the write’s plan, its output and inputs (location, format, schema, catalog), as references the pipeline already holds. Carried on ContractValidationEvent.lineage, not serialized into Invaract’s own event JSON (whose schema is unchanged). Column lineage is computed from it lazily, on the worker thread.
  • OpenLineageSink (com.invaract.verification.openlineage): a NotificationSink. AttachSetup builds it from the settings and combines it with the notifyConfig sink, if any, so every adapter that already uses AttachSetup publishes OpenLineage with no change of its own.
  • OpenLineageMapper: pure functions from Invaract’s events to OpenLineage events, with the per-run state (started, totals, held events) kept in a bounded map. Only the worker thread touches it.
  • OpenLineageNaming: section 2.2.
  • JsonText (verification-core’s notification package): an RFC 8259 writer, written by hand (no JSON library at runtime); NotificationJson now escapes through it too, which fixed control characters and non-finite numbers in Invaract’s own events.
  • Column lineage follows the adapter’s declaration: an event carries the plan for columnLineage only when the adapter declares lineage.columnLevel supported or partial (VerificationPipeline.tracesColumns), so an adapter whose plans are opaque never claims column lineage it does not trace.
  • A write refused before it is checked in full (Python I/O judges a write before it is staged) is refused through VerificationPipeline.rejectWrite, whose event carries the write’s lineage as verifyWrite’s does.
  • An adapter installed in code with a sink of its own (Spark’s forContract, Beam’s InvaractBeam.enforce) still gets OpenLineage from configuration alone: AttachSetup.withOpenLineage joins the OpenLineage sink the settings ask for, unless the sink already carries it.
  • Dry run publishes each inferred write as an output; ContractInferenceEvent carries no plan, so a dry run’s events have no inputs and no column lineage.
  • Transport: HttpTransport (java.net.http, optional gzip), FileTransport (appends one line per event, under a lock, so concurrent processes interleave whole lines), ConsoleTransport (SLF4J).

5. Performance

Section titled “5. Performance”

What turning it on costs the job:

  • On the job’s thread: building WriteLineage from references the pipeline already holds, and one offer to a bounded queue. No mapping, no JSON, no I/O. Measured in section 8.
  • Off the job’s thread: column lineage (Lineage.trace, already trampolined for deep plans), JSON, delivery. One daemon thread per sink.
  • Memory: at most queue.capacity events, each one a reference to data the job already built.
  • At the job’s end: at most shutdownTimeoutMs (default five seconds) waiting for delivery - only when there is still something to deliver.

6. Hardening

Section titled “6. Hardening”
  • Never throws into the job: the sink is wrapped (SafeNotificationSink), and the worker catches everything.
  • A slow endpoint is bounded by timeoutMs; a down one by the circuit breaker; a flood by the queue’s capacity. Every drop is counted, and said at WARN once per minute at most, never once per event.
  • Secrets: a bearer token only from an environment variable; credentials removed from every dataset name and from every URL a log line shows.
  • Text: every string the job controls (column names, messages, locations) is escaped; property tests hold the JSON well-formed for any string, control characters and unpaired surrogates included.
  • Size: maxEventBytes, then shedding, then dropping with a WARN.
  • Concurrency: one worker; state per run in a bounded map (oldest runs closed first when it is full).

7. The conformance kit

Section titled “7. The conformance kit”

A capability every adapter declares, reporting.openLineage (“publishes OpenLineage run events through configuration alone”), and scenarios that attach a real job through configuration (ConformanceAdapter.attached) with openLineageUrl set to an endpoint the kit serves, then hold what arrives to:

  • every event’s required fields (eventType, eventTime, producer, schemaURL, a UUID run id, the job) - the events themselves are built by the core, whose tests hold every one to the official OpenLineage JSON Schema;
  • one START and one terminal event per run, in that order, all with the run’s id;
  • the namespace openLineageNamespace sets;
  • the inputs and the output named for the locations the job read and wrote (section 2.2), the output’s schema facet equal to the columns written;
  • the contract’s verdict on dataQualityAssertions and invaract_contract: PASSED for an allowed write; for a refused one, FAILED, the violation, and a FAIL terminal event with errorMessage;
  • columnLineage exactly when the adapter declares lineage.columnLevel supported or partial, and its edges naming real input columns;
  • a job that is refused still publishes; an unreachable endpoint does not fail the job.

Three scenarios (openlineage-run, openlineage-refused, openlineage-unreachable), attached through Attachment.OpenLineage; OpenLineageConformance judges them. BrokenAdapterSpec gains the broken adapters they exist to catch: one that never sets the endpoint on its engine, one that loses the namespace, and one that never ends its run.

8. Test plan and results

Section titled “8. Test plan and results”

Core (verification-core, com.invaract.verification.openlineage, about 100 tests). JsonTextSpec (property tests: any string, control characters and lone surrogates included, renders as JSON a strict parser reads back unchanged); OpenLineageNamingSpec; OpenLineageSettingsSpec (every key, every refusal); OpenLineageMapperSpec (every event and facet, validated against the official OpenLineage 2-0-2 JSON Schema and each facet against its own versioned schema, the spec vendored at release 1.55.0; Invaract’s facets against the schemas the docs site publishes); OpenLineageSchemaSpec (the validator itself catches what it should); OpenLineageDeliverySpec (ordering, retries and backoff, the circuit breaker, dead letter, shedding, a full queue, bounded close, interrupts, many threads); OpenLineageTransportSpec (a real HTTP server: statuses, no redirects, gzip, headers, timeouts, credentials never in a message; concurrent file writers interleave whole lines); OpenLineageAttachSpec (through AttachSetup as every adapter attaches it; a real JVM whose shutdown hook ends its run).

Kit. OpenLineageConformanceTest breaks each rule of the judge one at a time; BrokenAdapterSpec holds the three scenarios to the mistakes above. The reference adapter conforms.

Adapters, through the kit’s scenarios on real jobs. Spark (SparkConformanceSpec), Beam Java (BeamConformanceSpec), Beam Python (BeamPythonConformanceSpec, a real Python pipeline and the checker), Python I/O (PythonIoConformanceSpec, and PythonIoPackageConformanceSpec with real Python jobs and the package): all three OpenLineage scenarios conform, and are on each adapter’s baseline. Plus SparkOpenLineageSpec (a real application attached by spark.sql.extensions, ended by spark.stop(); one installed in code with forContract) and a Beam test of a check built in code.

Mutation testing (Stryker4s, scoped to the new files): verification-core’s OpenLineage files and JsonText/ WriteLineage scored 83% (of covered code 85%) before the targeted tests were added for the real survivors (run eviction, the held-event cap, statistics, dataset-level lineage, credentials holding @, a daemon worker, interrupted callers), which also found and fixed an empty user part (hdfs://@nn) left in a namespace. What survives is in the rate-limited WARN summary’s arithmetic and log text, and two equivalent mutants (a boundary the map’s own invariant never reaches; a shortcut whose fallback computes the same answer).

Performance (OpenLineagePerformanceSpec, SparkOpenLineageSpec; a laptop-class container):

MeasureResult
A check of a 200-column job (two inputs joined, filtered), OpenLineage off vs on41-112 us vs 68-169 us across runs; the difference is within run-to-run noise (-50 to +57 us)
Publishing one event, on the job’s threadabout 1 us (an offer), whatever the endpoint does
1,000 events against an endpoint answering in 1 s0-14 ms on the job’s thread
50,000 events against a stalled endpoint, queue.capacity=10001,001 kept, 48,999 dropped and counted; 0.1-1.4 us each

The worst case for memory is a wide job writing many times while the endpoint hangs: each queued event holds what describes its write, which is why queue.capacity defaults to 1,000, not 10,000.

9. Alongside openlineage-spark

Section titled “9. Alongside openlineage-spark”

openlineage-spark publishes one run per Spark SQL execution, with the plan’s lineage as Spark sees it; Invaract publishes one run per application with what it verified. Both can be on: they are different jobs in the graph (set openLineageNamespace and jobName to keep them apart, or the same parent to group them under one orchestrator run), and the datasets are the same nodes, since both follow the naming conventions. That is measured, not assumed (section 11): on every job of the cross-check corpus the two name every dataset alike, except a table a write creates in a catalog (CREATE TABLE AS SELECT), which Invaract names by its catalog identifier, as its location does not exist yet.

11. Cross-checking Spark lineage

Section titled “11. Cross-checking Spark lineage”

Unit tests can only hold lineage to what their author expected. lineage-crosscheck/ holds it to two independent tools instead, on real Spark jobs: each job of its corpus (Corpus.scala, 55 jobs: projections, conditions, filters, sorts, joins of every kind, aggregates, windows, rollups, pivots, unions, nested data, SQL with views, CTEs and subqueries, UDFs, the Dataset API, caching and checkpoints, partitioned and appending writes, catalog tables, Delta Lake MERGE, Iceberg, Hive, JDBC, RDDs and streaming) runs once in a session with all three capturing it:

ToolWhat it is held to
Invaractthe job’s contract declares its output; Invaract publishes OpenLineage to a file
openlineage-spark 1.55.0the reference for dataset naming and for the transformation types of the column lineage facet
Spline agent 2.4.0an independent model of the analyzed plan: every written attribute traced back to the read attributes it comes from

Each tool’s report of the write is reduced to one model (Captured: inputs, output, direct edges with their subtypes, indirect edges per field or for the whole output) and compared (Comparison). Every difference is either fixed or explained in Corpus.scala, as Gap (Invaract’s), Reference (the other tool misses or adds something) or Choice (a convention); the spec fails on a difference with no explanation and on an explanation for a job that now agrees. The baseline (crosscheck-baseline.txt) records Invaract’s complete lineage of every job as well as each difference, so any change in Invaract’s lineage - even of a job every tool agrees on - or in a reference’s, on an upgrade, is seen. docs-site’s “Spark Column Lineage Coverage” page is generated from the run (Report): each job’s code, read from Corpus.scala so it is the code that ran, what Invaract publishes for it, each difference with its reason, what Invaract captures that the other tools miss, and Invaract’s known gaps and limits. CROSSCHECK_UPDATE=true sbt test rewrites the baseline and the page. CI runs it (lineage-crosscheck) on every pull request and push.

What the first runs found, and what was done:

What stays a difference is on the generated page, each with its reason. Most are openlineage-spark reading Spark’s optimized plan (an inferred isnotnull filter on every join key; IN/EXISTS rewritten into semi joins), or a reference missing what Invaract follows (subqueries, CTEs, localCheckpoint, rollup keys, a MERGE’s clauses). No corpus job shows a gap of Invaract’s; the page lists the limits no job measures (a catalog that chooses a new table’s location itself, streaming micro-batches, UDF internals, lineage through an RDD, operators Invaract does not translate).

12. Production-readiness review

Section titled “12. Production-readiness review”

A review of the whole feature as something a platform team would run on every job, against the questions that decide that: is the lineage correct, is it complete enough and are its gaps known, can a team move to it from what they run today, can it hurt a job, and can it be operated. Each finding, and what was done:
