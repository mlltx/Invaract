JDBC support

← Back to Spark Adapter

Spark’s generic JDBC data source (spark.read.jdbc(...), df.write.jdbc(...), format("jdbc")) is part of spark-sql itself, so it needs no extra dependency. Its tests (JdbcConnectorSpec) run against an embedded, in-memory Apache Derby database, which is on the test classpath through Spark’s Hive dependencies; no database server is started.

One location string for a table, read or written. A JDBC table is located as jdbc: + the connection URL + / + the table name: jdbc:jdbc:derby:memory:orders_db;create=true/ORDERS. The URL’s own jdbc: makes the prefix appear twice; that is expected. A read has always been located this way (SparkPlanAdapter.jdbcLocationOf, reading the relation’s JDBCOptions); a write used to be located by its whole options map rendered as text, which no contract could match and which could put a password into an error message. Both now go through SparkPlanAdapter.jdbcLocation, so they cannot drift apart. A save with neither a path nor a JDBC url and dbtable is located as <source class>(no path), with a diagnostic, and the options map is never shown.

The format is jdbc on both sides (the provider’s DataSourceRegister.shortName() for a write; SparkPlanAdapter.readFormatOf for a read).

This pass covered what a contract needs to name a JDBC table and to check a job that reads or overwrites one. It did not survey vendor-specific behaviour (type mapping per database, truncate/cascadeTruncate, isolation levels, partitioned reads); those rows are marked ❓ below rather than assumed.
