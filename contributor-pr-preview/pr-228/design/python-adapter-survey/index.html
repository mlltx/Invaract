Native Python adapter survey

Status: survey. No adapter code exists. This document helps decide whether and how to let Invaract check plain Python data jobs: scripts that read and write files themselves, with no data-processing engine underneath. It is not about Beam’s Python SDK (Beam’s library for writing pipelines in Python), which has its own adapter (docs/BEAM_PYTHON_ADAPTER.md). Engine surface surveyed: CPython 3.11.17 (the standard Python interpreter) running scripts that do their file work through the standard library (open, csv, json, pathlib, shutil, os, sqlite3) and through the two libraries almost every Python data script uses for columnar files, pyarrow 25.0.1 and pandas 2.3.3. Linux kernel 6.18. Written: 2026-10-26. Evidence checked: 2026-10-26. Source of each claim: section 10, “Evidence log”.

The short version

Section titled “The short version”

What it would be. A plain Python job has no plan to inspect beforehand. It is a script, and its reads and writes happen as each line runs. So Invaract would sit inside the Python interpreter (the program that runs the script). When the interpreter starts, Invaract would install a hook (a function Python calls whenever the script is about to do something, such as open a file). It would also wrap the handful of library functions that write data files. Each time the job is about to write, Invaract would compare that write with the data contract and refuse it, before a byte lands, if it breaks the contract. This is the way Spark is checked, one write at a time, rather than the way Beam is checked, the whole job before it starts. As everywhere, it checks the shape of a job: what it reads, where it writes, and which columns and types come out. It never checks what the team’s own code does to individual values.

How much of the suite it is expected to pass. Of the suite’s 55 scenarios:

  • 25 by doing the check;
  • 2 only partly: one passes only because of how the kit’s job is laid out, and one is expected to diverge;
  • 15 by refusing safely;
  • 13 skipped because they do not apply.

Details in section 7.

Can it be switched on without changing the job’s code? Partly. A platform team installs one Python package in the environment the job runs in, and sets INVARACT_CONTRACT=<contract> (plus any other Invaract settings) as environment variables. The job’s code and its command stay exactly as they are. Probe 5 showed this on an unmodified job. Section 5 has the details, and the ways a job can escape it.

Classifying outputs: a data asset or a readiness signal. A contract can already label each output type: DATA_ASSET (the data product itself) or type: CONTROL, which the contract model defines to include “a readiness/reconciliation signal”. Nothing checks an output’s label today, on any engine. D13 proposes the check, and it suits plain Python well:

  • the adapter confirms the job wrote to each declared place;
  • it confirms that what landed there matches the label: a table with columns for a data asset, a marker or small status file for a readiness signal;
  • it refuses a readiness signal for a data asset that was not written, and checked, earlier in the same job.

It is an engine-neutral change, so it needs a decision of its own (decision 9).

The biggest risks.

  1. The checking code runs in Java, so every machine that runs a governed Python job needs Java. For Beam that was only the machine that submits jobs. Here it is every worker, and slim Python container images usually have no Java (UNVERIFIED). The alternative is a checker compiled to a program that needs no Java (D9).
  2. Some writes are invisible to Python. pyarrow writes files from compiled C++ code. Python’s hook never sees those writes, so a pyarrow write function Invaract has not wrapped goes through unchecked (probe 6: three of them did). On Linux the operating system can be told to refuse writes outside the contract’s places, and probe 7 showed it stopping exactly those writes. It does not check columns, though, and other systems have nothing like it (D8).
  3. Python does not record which data went into which write. The adapter knows what the job read before a write, not what that write was built from. So in a job with several outputs, a missing input can go unnoticed, and one scenario is expected to diverge from the suite (D4).
  4. Switched on through the environment, it fails open (lets the job run unchecked) when the package is missing. If a job runs in a Python environment the platform did not prepare, nothing is checked and nothing says so. A small launcher command closes this for platforms that want it (section 5).

Decisions I need from you. (Each is explained in section 4; a one-line answer is enough.)

  1. Build it, as a hook inside the interpreter that checks each write as it is made, sharing the existing Java checking code? Recommend yes, starting on Linux.
  2. Run the Java checker as one helper process per job, which needs Java on every worker, and turn to a no-Java build only if platforms object? Recommend yes.
  3. Write each output the contract declares to a temporary file first, and move it into place only once checked, so a refused write never damages the old data? Recommend yes.
  4. Count every read before a write as feeding it. Then, in a separate change to the conformance kit, stop requiring the second violation in scenario 20 from an adapter that cannot know which reads feed which write? Recommend yes.
  5. Offer the Linux operating-system restriction on writes (Landlock) as an opt-in setting at first, and make it the default later? Recommend yes.
  6. Read trustedSteps on this engine as places and programs a platform trusts not to carry governed data (log folders, caches, gzip)? Recommend yes.
  7. Wrap the standard library, pyarrow, pandas and Polars in the first version, and cover DuckDB and every other writer by reading files back from disk plus the operating-system restriction? Recommend yes.
  8. Name it the python adapter, in a new python-adapter module with its own Python package, and share the pyarrow type mapping with the Beam Python adapter? Recommend yes.
  9. Check each output against its declared kind, as an engine-neutral addition that every adapter declares a position on, built before the Python adapter? The kinds are a data asset or a readiness signal, with the signal naming the data assets it announces. Recommend yes; the open questions on it are at the end of D13.
  10. When a job starts, should Invaract remove a stale readiness marker for each signal the contract declares, so downstream jobs never see yesterday’s “ready” for today’s run? Recommend yes, as an opt-in setting.

The four requirements, one by one

Section titled “The four requirements, one by one”

The requirements this adapter is judged on first:

  1. confirm the job wrote where its contract says;
  2. have each output declare what it is (a data asset or a readiness signal), and confirm that;
  3. switch it on without changing the job;
  4. capture the schema of the files written.

Probes 10 to 13 were run for this section.

1. The job wrote where it said it would

Section titled “1. The job wrote where it said it would”

Verdict: yes, in two halves. Nothing lands outside the declared places, and every declared place is written in this run.

Nothing lands outside the declared places.

  • Writes that go through Python are seen before they happen, and refused: open, the csv and json modules, pandas’ CSV, Excel and Parquet writers, fsspec on local files, renames, moves and touches (probes 2, 3 and 10).
  • Writes made inside compiled code are not seen by Python at all. That covers pyarrow, Polars and DuckDB (probes 2, 6 and 10). There are two answers:
    • A wrapper on each catalogued function sees the write before it happens: pyarrow’s write functions, and Polars’ write_parquet, write_csv and the other Python methods.
    • DuckDB’s COPY ... TO 'path' is inside SQL text, so no wrapper can sensibly read it. On Linux, the operating-system restriction refuses every write outside the declared places, whatever makes it. Probe 13 showed it stopping pyarrow, Polars and DuckDB writes, a shell command, and a Python child running in its own virtual environment.

Every declared place is written in this run. This is checked when the job ends, as on Spark. It uses what the hook recorded, plus a look at the files at each declared place that changed since the job started, which also catches writers Python cannot see (probe 12).

Details that decide what “the place it said” means:

  • Write to a temporary file, then rename it into place is a common, careful pattern. The rename names the destination (os.rename ('data/out/.report.tmp', 'data/out/report.parquet'), probe 10), and counts as the write landing there. A rename onto a declared output is not refused, contrary to the first draft of D7.
  • Paths are compared once .. and symbolic links (shortcuts to another folder) are resolved. A write through linked/out/x.csv is a write to real/out/x.csv (probe 10).
  • Libraries write their own temporary files in the system temporary folder (tempfile, and openpyxl for Excel files, probe 10). That folder is trusted by default.
  • Cloud storage (S3, GCS) was not probed: there are no credentials here (UNVERIFIED).
    • Writes through fsspec are Python code and can be wrapped.
    • The boto3 and google-cloud-storage clients would need wrappers of their own.
    • The operating-system restriction does not cover network writes.

2. Each output says what it is, and Invaract confirms it

Section titled “2. Each output says what it is, and Invaract confirms it”

The contract labels each output, and a readiness signal names the asset it announces (D13 proposes the readinessFor field). Probe 12 built a small working prototype of the checks, with this contract:

  • report: a data asset, the folder data/out/report, columns id and amount, both int64;
  • report_ready: a readiness signal for report, the file data/out/report/_SUCCESS.

The job wrote its report with Polars, which Python cannot see.

CaseWhat the job didResult
awrote the report, then touched _SUCCESSallowed: “every asset it names was written in this run and matches”
btouched _SUCCESS first, then wrote the reportsignal refused: “its asset ‘report’ was not written in this run”
cwrote the report with DuckDB, id as text, then touched _SUCCESSsignal refused: “its asset ‘report’ has id: string, the contract says int64”
dwrote nothing new; yesterday’s report and marker were there; re-touched _SUCCESSsignal refused: “its asset ‘report’ was not written in this run”
eput only an empty file at the report’s place, then touched _SUCCESSsignal refused: “its asset ‘report’ holds an empty file”
fwrote the report, then a pyarrow table as _SUCCESScaught only at exit, after it landed: “readiness location holds a table, not a marker”; exit status 3

How it works. The readiness signal is the gate downstream jobs rely on, so that is where Invaract looks hardest:

  • It sees all three ways a marker is written: created, opened for writing, or re-touched (os.utime only, probe 9).
  • At that moment, it opens the asset’s files as they are on disk. Each must have been written in this run, be a data file, and have the declared columns.
  • Because it reads the files themselves, this works whichever library wrote them, DuckDB included (case c).

What it does not do.

  • It stops a new signal; it cannot withdraw an old one. In case d, yesterday’s _SUCCESS is still there. Downstream jobs should check the marker’s date, or Invaract should remove a stale marker for a declared signal when the job starts. That is a choice to make (decision 10).
  • A table written as the marker by a writer Python cannot see (case f) is caught only when the job ends. With a wrapper on that function, it would be refused before it landed.
  • “Written in this run” uses file modification times. On a network file system whose clock differs from the machine’s, or on an object store, that needs checking (UNVERIFIED).

4. The schema of the files written

Section titled “4. The schema of the files written”

There are two sources, and the recommendation is to use both:

  • From the call, before anything is written (wrappers). This is what allows a refusal before the data lands.
    • pyarrow tables: exact.
    • pandas: its own types are vague (object for text, probe 11). pandas’ own conversion to pyarrow gives the exact types, id: int64; name: string; amount: int64; at: timestamp[ns]; tier: dictionary<...>.
    • The csv module: names only.
  • From the file, after it is written (read back from disk). This is the truth, whatever wrote it. Probe 11 wrote eight files and read them back:
FileWritten byRead back

What this means.

  • Parquet, Avro and Feather files carry their exact schema, nested types and “may not be empty” included. The pyarrow type mapping Invaract already has covers what came back: large_list, large_string, dictionary, date32 (PyArrowSchemas.scala, lines 59 to 108).
  • CSV and JSON carry column names, never types. Their types can come only from the data the job handed over (pandas types), and the contract should say whether that is good enough or whether such a write is refused when it declares types.
  • Two surprises a contract author will meet:
    • pandas writes a non-default index as an extra column;
    • pandas never marks a column “may not be empty”, while DuckDB marks most of them.
  • The same read-back gives dry-run mode a real schema for every file the job wrote, so draft contracts are accurate whichever library the team uses.

5. When the job writes to a database: Postgres and BigQuery

Section titled “5. When the job writes to a database: Postgres and BigQuery”

A database write does not go through Python’s file opening, so the file mechanisms above do not apply. Probes 14 to 17 ran a real Postgres 16 server, and the real BigQuery client library (3.46.2) against a recording stand-in for BigQuery, since there are no Google credentials here.

What the hook sees (probes 14 and 17b):

How the job writesWhat the hook sees
Postgres through psycopg2, psycopg 3, or pandas to_sql (SQLAlchemy)nothing: these drivers talk to the server from compiled code
Postgres through pg8000 (a pure-Python driver)only the connection: socket.connect (..., ('127.0.0.1', 55432)). No SQL, no table
BigQuery through google-cloud-bigqueryevery request, before it is sent: http.client.send carries POST /bigquery/v2/projects/demo/datasets/gold/tables/report/insertAll and the body {"rows": [...]}

So the work falls to three other places.

  1. A wrapper on the database client, which sees each statement or request before it runs.

    • Postgres (probe 16). Wrapping psycopg2.connect so that every cursor is a checking one covered:

      • the job’s own SQL;
      • pandas to_sql.

      A SQL parser (sqlglot) named each statement’s target table and kind. Results:

      • INSERT INTO gold.other was refused (an undeclared table);
      • DELETE FROM gold.report with no WHERE was refused;
      • INSERT INTO gold.report was allowed.

      Postgres’s own EXPLAIN (it describes what a statement would do without running it) also names the tables read and their filters (probe 15): WRITE INSERT gold.report; READ gold.orders filter=(orders.amount > 0). EXPLAIN cannot explain TRUNCATE or CREATE TABLE AS; the parser names their targets.

      • The gap. A job that picks its own cursor type (cursor(cursor_factory=RealDictCursor)) got past the wrapper, and its insert into gold.other landed.

    • BigQuery (probe 17). Every write goes through one Python client object, and its requests say exactly what is written:

      CallWhat the request states
      load_table_from_dataframedestinationTable (demo.gold.report), writeDisposition (WRITE_TRUNCATE), the schema, sourceFormat: PARQUET
      insert_rows_jsonthe table in the path (.../tables/report/insertAll), and the rows
      query("INSERT INTO gold.report SELECT ...")the SQL text; BigQuery itself runs it
      query(..., destination=..., write_disposition=WRITE_APPEND)destinationTable and writeDisposition

      For SQL that BigQuery runs, BigQuery has its own dry run: the same query with dry_run=True runs nothing. The client then reads the statement type and the tables it reads from the answer (QueryJob.statement_type, referenced_tables and ddl_target_table, google/cloud/bigquery/job/query.py, lines 1258 to 1307). What a real BigQuery dry run returns for each statement type was not seen here (UNVERIFIED: no credentials).

  2. The database’s own permissions are the floor, as the operating-system restriction is for files. A Postgres role allowed only INSERT on gold.report was refused everything else by Postgres itself (probe 15):

    • insert into gold.other: ERROR: permission denied for table other;
    • delete from gold.report and truncate gold.report were refused the same way.

    BigQuery’s equivalent is the job’s service account (IAM). A platform team applies either through the credentials it gives the job, without touching the job.

  3. The database is the truth about the schema. Reading the table back gives its exact columns, types and “may not be empty”:

    • Postgres’s information_schema.columns: id bigint NO; amount bigint YES (probe 16);
    • BigQuery’s get_table: ('id', 'INTEGER', 'REQUIRED'), ('amount', 'INTEGER', 'NULLABLE') (probe 17).

    One surprise: pandas’ load into BigQuery sent every column as NULLABLE (probe 17), the same as with Parquet files.

What it means for the four requirements.

  • Where it wrote. A table is located by its name. That would be <database>/<schema>/<table> for Postgres (with the server’s address as its catalog location), and <project>/<dataset>/<table> for BigQuery, as the Beam adapters already write it. The wrapper refuses an undeclared table before the statement runs. Permissions refuse it even when the wrapper is bypassed.
  • What it is.
    • A data asset is a load or insert into a governed table.
    • A readiness signal is usually a row in a status table, such as INSERT INTO control.load_status VALUES ('report', 'READY', now()).
    • The wrapper sees both statements, in order, and whether each succeeded. So the rule “no ready row unless the asset was written and checked in this run” works the same as for files.
    • Updates, deletes and merges are visible too. That makes Invaract’s existing rules on row-level changes (for example forbid_unconditional_delete) checkable for these jobs, which they are not for files.
  • Save mode.
    • BigQuery states it outright (writeDisposition).
    • For Postgres it follows from the statements: INSERT is append, TRUNCATE then INSERT is overwrite, CREATE TABLE AS is “error if it exists”.
    • pandas’ if_exists="replace" drops and re-creates the table.
  • The schema.
    • Before the write: from a BigQuery load’s schema, or the INSERT’s column list and the table’s own columns.
    • After the write: from the table itself, exactly.
  • Switching it on. The wrappers come in the same package as everything else, so there is nothing new to install. Permissions are a second, independent switch the platform already holds.

What stays out of reach.

  • SQL hidden inside a stored procedure or function (CALL load_report()): the wrapper sees only the call. It must be refused, or trusted by name.
  • Drivers the package does not wrap: asyncpg, or a database driver for another engine.
  • Another program run by the job (psql, the bq command): refused unless trusted.
  • BigQuery multi-statement scripts, where a dry run may say little (UNVERIFIED).

How to read this document

Section titled “How to read this document”
  • What “conforming” means here. Invaract has a conformance suite: 55 small, engine-neutral jobs, called scenarios, that every adapter is run against. An adapter is the part of Invaract that knows one engine. It declares what it can and cannot do (its declaration), and each scenario must come out the way that declaration promises. Refusing safely is conforming. If an adapter says “I cannot check this”, the suite expects it to refuse any contract that depends on it, rather than let the job through unchecked. So a ❌ below is a limit to understand, not a failing grade.
  • Forecast marks.
    • ✅ expected to do the check and produce what the suite expects.
    • ⚠️ only partly, or with a workaround, or depends on something not yet verified.
    • ❌ cannot do the check, so the suite expects a safe refusal.
    • ➖ does not apply.
  • Confidence. High: shown by a probe I ran. Medium: each fact it rests on was probed, or a source says so, but the whole has not been assembled. Low: inferred. Nothing here has been run as an adapter.
  • “Probe”. A throwaway program I wrote and ran against real Python 3.11.17, pyarrow 25.0.1 and pandas 2.3.3 to see what they reveal. The programs are not committed; what they printed is quoted below. Each probe’s checking was a toy written for the probe, not Invaract’s checker. The probes show what can be seen and stopped, not Invaract’s real verdicts.
  • Words. Each technical term is explained where it first appears, and again in the glossary at the end.

1. What Invaract asks of an engine

Section titled “1. What Invaract asks of an engine”

The contract, and the check

Section titled “The contract, and the check”

A data contract is a small YAML file saying what a job may read, where it must write, and what the written data must look like:

Parquet is a common file format that stores a table together with its column names and types. The output’s schema is its list of column names and types; required: true means the column may never be empty. Invaract checks a job against the contract before the job writes anything. If the job reads something undeclared, writes somewhere else, or produces the wrong columns, the write is refused with a message saying what was checked, what failed and how to fix it. On Spark the check runs inside Spark just before each write. On Beam it runs once, just before the whole job is handed to the engine. Here it would run inside Python just before each write.

The engine-neutral model (the “IR”)

Section titled “The engine-neutral model (the “IR”)”

Every engine describes a job in its own way. Spark has a query plan: a tree of the operations a query performs, worked out before it runs. Beam has a pipeline graph: the job’s steps, with arrows for the data flowing between them. Invaract translates that description into one small engine-independent description of reads, filters, joins, groupings and writes, called the IR (intermediate representation). All the checking code works on the IR, so it is written once for every engine.

The Spark adapter builds the IR from Spark’s query plan; the Beam adapters build it from the pipeline graph. Plain Python has neither (section 2), so this adapter would build a small IR at each write, from what it has seen so far:

The middle box is opaque: Invaract knows a step is there, not what it does. The same is true of a Beam job’s own functions. The reads are every dataset the job opened before this write. The write carries everything the writing function was handed.

Capabilities, declarations and scenarios

Section titled “Capabilities, declarations and scenarios”

A capability is one thing the checking code can do: “check that a write lands where the contract says”, “check the columns’ types”, “enforce a required filter”. Each adapter’s declaration gives every capability (31 today) one of four statuses: supported, partial (some shapes only, with a note saying which), unsupported, or not-applicable (the engine has no such thing). Some capabilities are marked blocks if unsupported: if a contract relies on one the adapter cannot do, the job is refused (UNSUPPORTED_CONTRACT_FEATURE) rather than passed with that part unchecked. The scenarios then hold each adapter to its own declaration.

2. The engine in plain words

Section titled “2. The engine in plain words”

There is no engine. A plain Python data job is a script, a file of Python code that the interpreter (CPython, the standard Python program) runs from top to bottom:

Spark and Beam describe a job first and run it afterwards, and there is a moment between the two at which Invaract can look. A script has no such moment. Nothing describes the job before it runs: no plan, and no DAG (directed acyclic graph, the usual shape of a job description, steps joined by one-way arrows). The read happens when its line runs, then the filtering, then the write. Seen from inside the interpreter, the job is a sequence of events in time:

Where it can be stopped: at each write, while the script runs, by code that runs inside the same interpreter. A Python exception raised there aborts the write, and the job’s own error handling sees an ordinary error.

Libraries change the picture. The standard library’s file work goes through Python’s own open, which Python lets a hook watch. pyarrow, the library behind nearly all Parquet in Python (pandas uses it too), does its file work in compiled C++ code, which Python cannot watch (probe 2). The adapter therefore watches in two ways: a hook for everything that goes through Python, and wrappers around the library functions that write. Section 3 shows each.

3. How the adapter would get hold of a job

Section titled “3. How the adapter would get hold of a job”

Four things the engine produces were examined. The first was rejected as the main source; the other three together are the design.

The script’s syntax tree (rejected as the main source)

Section titled “The script’s syntax tree (rejected as the main source)”
  • What it is. The script’s text, parsed into a tree of its statements and expressions, which is what Python itself does before running it. It is called the AST (abstract syntax tree). It is like a sentence diagram of the code: it shows that line 11 calls pq.write_table with two arguments, but not what those arguments will hold when the line runs.
  • How we get hold of it. ast.parse(source). It is available before the job runs, so in principle a job could be refused before it starts. That would be a pre-submit gate, like Beam’s.
  • What it contains. Every call the script makes and its arguments as written: a fixed path such as 'data/out/report.parquet', a mode such as 'w', a header list such as fieldnames=['rows'].
  • What it leaves out. Anything decided as the script runs: a path read from the command line (sys.argv), an environment variable, a configuration file, a loop, a function in another module, a table whose schema is built three lines earlier. Most real jobs take their paths from their command line or configuration, so most real jobs would have to be refused as uncheckable. That is why this is not the main source.

Runtime audit events (the hook)

Section titled “Runtime audit events (the hook)”

  • What it is. The interpreter raises an audit event for sensitive actions (shown on 3.11; Python has had them since 3.8 by PEP 578, UNVERIFIED for the other versions here): opening a file, renaming or deleting one, starting another program, connecting to a database. A hook (a function registered with sys.addaudithook) is called with each event’s name and details, and can stop the action by raising an error. It is like a building’s door sensors: they report every door that opens, not what is carried through it.

  • How we get hold of it. sys.addaudithook(hook), called once when the interpreter starts (section 5 shows how that happens without changing the job). Events arrive while the job runs, at the moment of each action and before it happens, so a write can be refused before it starts (probe 3b). There is no function to remove a hook once it is added (probe 5 listed sys’s audit functions: only addaudithook and audit).

  • What it contains. For a file opened through Python (open, pathlib, csv and json on an opened file, pandas’ CSV reader and writer, shutil.copy):

    • its path;
    • its mode, which says whether it is being read, replaced (w), appended to (a) or created only if absent (x);
    • the operating system’s flags, which say the same.

    Renames, deletes and copies (os.rename, os.remove, shutil.copyfile) name both places. A sqlite3 database names its file, and starting another program names the program.

  • What it leaves out.

    • Everything written in compiled code: pyarrow’s reads and writes raise no event at all (probe 2).
    • What data passes through an open file: no columns, no format.
    • What a sqlite3 statement does to the database.

    The cost: columns and formats must come from the libraries themselves (next artefact), and pyarrow needs its own treatment.

The arguments of the library calls Invaract wraps

Section titled “The arguments of the library calls Invaract wraps”

  • What it is. Invaract replaces a library’s write function (pyarrow.parquet.write_table, csv.DictWriter, …) with a wrapper: a function of the same name that looks at its arguments, checks them, and then calls the original. The arguments are the most precise description of a write that exists, because they are what the library is about to write.

  • How we get hold of it. By assigning the wrapper in place of the original in the library’s module when the interpreter starts, before the job imports it. Each wrapped call arrives while the job runs, before anything is written (probe 3). The list of functions wrapped is the adapter’s catalogue, like the Beam adapters’ list of read and write steps.

  • What it contains.

    • For a pyarrow write: the destination, and the table’s full schema, with every column’s name, exact type, nested types, and whether it may be empty (not null).
    • For pandas: the same, because pandas’ Parquet write goes through pyarrow.parquet.write_table (probe 6).
    • For a csv.DictWriter: the column names (fieldnames), but no types, because a CSV file holds only text.
    • For a pyarrow read: the dataset’s location and its schema.

  • What it leaves out.

    • Any write function not in the catalogue. Probe 6 showed three pyarrow writes going through unseen and unrefused, because they write from compiled code and were not wrapped.
    • The types of a CSV or JSON write.
    • Anything about how the columns were computed.

    The cost: the catalogue must be kept complete for the libraries it claims, and anything outside it needs the next artefact as a safety net.

The operating system’s own restriction (Linux Landlock)

Section titled “The operating system’s own restriction (Linux Landlock)”
  • What it is. Landlock is a feature of the Linux kernel (the core of the operating system) that lets a running program give up rights it does not need, for good. Here that means “from now on, this process may create or change files only beneath these folders”. It is like handing in every key except the ones for the rooms you have business in. It sees every write, whichever library or language makes it.
  • How we get hold of it. Three system calls, made through Python’s ctypes when the interpreter starts, listing the contract’s output folders plus any trusted ones. From then on, a write anywhere else fails with “Permission denied” inside whatever code attempts it (probe 7). Available on this machine (Landlock version 7, kernel 6.18). Whether a given production host has it is UNVERIFIED.
  • What it contains. Nothing to inspect. It is a wall, not a window: it refuses writes outside the listed folders. It does not report them to Invaract, and it cannot check columns, formats or save modes.
  • What it leaves out.
    • Everything about a write’s content.
    • Any check finer than a folder: a single declared file inside a busy folder needs that folder’s write rights.
    • Every operating system other than Linux.

4. Key design decisions

Section titled “4. Key design decisions”

D1. Where does the check run?

Section titled “D1. Where does the check run?”
  • Options.
    • (a) Inside the interpreter, at each write, through the hook and the wrappers (section 3).
    • (b) Before the script runs, by reading its syntax tree.
    • (c) After the run, by looking at what files changed.
  • Recommendation. (a). Its enforcement point (where the check can stop a job) is in-engine-blocking, the same as Spark’s.
  • Why. (b) cannot see most real jobs’ paths (probe 1), so it would refuse nearly everything. (c) can only report damage already done. (a) sees each write with its real destination and data, and can stop it before it lands (probe 3).
  • What it costs.
    • Like Spark, it judges one write at a time. A declared output the job never writes is found only when the interpreter exits, after the other writes have happened, and reported then (check.outputsWritten partial, as on Spark).
    • A job can catch Invaract’s error and carry on. The refused write still does not happen, and the adapter can set a failing exit status at the end regardless (probe 3e).
  • What would change my mind. Jobs that are mostly fixed paths (generated scripts, notebooks exported as scripts). Then a syntax-tree pre-check could be added in front of (a), to refuse some jobs before they start. It would not replace (a).

D2. What is the adapter’s description of a job?

Section titled “D2. What is the adapter’s description of a job?”
  • Options.
    • (a) Build an IR at each write: every dataset read so far, then one opaque step (the Python code), then the write with everything the writing function was handed.
    • (b) Try to follow data through the program, tagging each table as it is read and tracing it to the write.
  • Recommendation. (a).
  • Why. It uses only facts the probes showed are available, and the checking code already handles an opaque step with reads beneath it: the Beam adapters rely on exactly that. (b) breaks as soon as the code makes a new table from an old one, which is almost every line of a data job.
  • What it costs. No filter, join or grouping is ever visible, so those rules are refused safely (section 7). Which reads fed which write is a guess (D4).

D3. How is a refused write kept from damaging the old data?

Section titled “D3. How is a refused write kept from damaging the old data?”
  • Options.
    • (a) Check at open only: the location and save mode there, the columns when the CSV writer is made.
    • (b) Stage every write to a declared output: open a temporary file next to it, check when it is closed, and move it into place only if the check passes.
    • (c) Check only writes whose columns are known before the file is opened (pyarrow), and refuse the rest.
  • Recommendation. (b) for writes through Python’s open. pyarrow and pandas Parquet writes need no staging, because the wrapper checks them before the file is opened.
  • Why. Opening a file to replace it empties it at that moment (probe 2’s flags). In probe 3d a CSV write to the declared place with the wrong header was refused, after open had already emptied yesterday’s report: the file was left empty. Probe 4 staged the same write. The refusal then left the old report intact, and a correct write was moved into place on close.
  • What it costs.
    • Invaract must replace Python’s open for declared outputs (builtins.open, which is the same object as io.open and is what pathlib calls).
    • Appending to a staged file means copying the existing file first.
    • A reader sees the old file until the write finishes, which is usually better.
  • What would change my mind. Very large appends, where the copy costs too much. Those could be checked at open instead, with the risk stated in the declaration.

D4. Which reads count, and which write do they feed?

Section titled “D4. Which reads count, and which write do they feed?”
  • Options.
    • (a) Every dataset read the process made before a write counts as feeding it.
    • (b) Only the reads made since the previous write.
    • (c) Tag the objects a read returns, and check whether the written object carries the tag.
  • Recommendation. (a). Then, in a kit change of its own, stop requiring per-write read attribution of an adapter that cannot know which reads feed which write. That change would add a capability for it, or key scenario 20’s second violation to an existing one.
  • Why.
    • Python does not record which data went into which write.
    • (a) never invents a missing input for a valid job.
    • (b) would refuse every job that reads everything first and then writes twice.
    • (c) loses the tag at the first computed column.
  • What it costs.
    • Scenario 18 conforms only because the kit’s job reads each input just before its write.
    • Scenario 20 is expected to diverge: the stray write is blocked, but its second violation (MISSING_INPUT) is not reported, because the orders were read earlier.
    • With the strict option (rejectUndeclaredInputs), a job that writes two outputs from two inputs can have the second write refused for reading the first one’s input.
  • Also: which reads count. Probe 6’s “reads so far” included the two .pth files Python reads at start-up. A dataset read is therefore any read through a catalogued reader, or any plain open of a file outside:
    • the interpreter’s own folders (sys.prefix, the installed libraries);
    • the script’s own code (.py files);
    • the places a platform names as trusted (D6).
  • What would change my mind. If the maintainers prefer no kit change, the adapter ships with a documented divergence, and its write-up cannot be marked complete.

D5. How do Python’s names become contract locations?

Section titled “D5. How do Python’s names become contract locations?”
  • Recommendation.
    • A location is the path the job named, made absolute against the job’s working folder. A relative declaration (such as data/out/report.parquet) then matches it by its ending, the existing rule in LocationMatching.
    • A file read from inside a folder the contract declares counts as reading that folder. This needs a small rule in the adapter, because the shared matching compares whole locations and a file inside a folder is not one.
    • A remote path pyarrow understands (s3://bucket/x) is used as given.
  • What it costs. Checking that the file-inside-a-folder rule cannot let a read of orders_backup/ count as orders/. It matches on whole folder names, the same /-boundary care the shared rule takes.

D6. How do Python’s types map to the contract’s?

Section titled “D6. How do Python’s types map to the contract’s?”
  • Recommendation.
    • pyarrow schemas use the pyarrow type mapping the Beam Python adapter already has (PyArrowSchemas). It covers nested types, time zones and types with no neutral equivalent, so it moves to a place both adapters share. The Python side sends the schema as structured data, rather than as printed text, for the new adapter.
    • pandas writes go through pyarrow and are mapped the same way.
    • CSV writes have names and no types, so a contract that declares types for a CSV output has the write refused as unverifiable, never passed. JSON and raw text have neither.
  • Why. CSV and JSON hold text. Whatever type a reader later infers is not something the job states.
  • What it costs. pandas marks every column as possibly empty unless the job passes schema= to to_parquet (probe 8). A contract with required: true columns written through pandas is then refused until the team adds that schema, which the user guide must say plainly.

D7. How are writes described, and what is refused as unverifiable?

Section titled “D7. How are writes described, and what is refused as unverifiable?”
  • Recommendation.
    • Format comes from the function that writes (write_table is parquet, the csv module or to_csv is csv, json.dump is json). A raw f.write states none, so a contract that declares a format for that output has the write refused.
    • Save mode comes from the open mode: w is overwrite, a append, x error. pq.write_table always replaces the file. write_to_dataset follows its existing_data_behavior option.
    • Refused as unverifiable (UNVERIFIABLE_WRITE):
      • a delete of a declared output (a rename or move onto one is followed instead: the destination is where the write landed, probe 10);
      • a sqlite3 database that is not a declared output, whose statements are not translated at first;
      • another program started by the job, unless the platform trusts it.
  • Why. Each of these changes data in a way Invaract cannot read. Failing closed (refusing what cannot be checked, rather than letting it through) is Invaract’s rule everywhere.
  • What would change my mind. Many jobs that call harmless programs. trustedSteps exists for that.

D8. What cannot be seen, and the policy

Section titled “D8. What cannot be seen, and the policy”
  • Recommendation.
    • Writes inside compiled code that the catalogue does not wrap cannot be seen by Python at all (probe 6), and no Python-side policy can refuse them.
    • On Linux, offer the operating-system restriction (probe 7): writes outside the contract’s output folders and the trusted places fail at the kernel. Make it opt-in at first, because jobs write to temporary folders and caches the platform will need to list. Make it the default once the trusted places are understood.
    • Elsewhere, the declaration says plainly that such writes are not seen.
  • Why. Without the restriction, a compiled library is an unguarded door. With it, the door is locked, though Invaract cannot say who tried it: the job fails with the library’s own “Permission denied” rather than Invaract’s message.
  • What it costs. A Linux-only guarantee, and a list of trusted places to maintain. Network writes (a database driver, an HTTP upload) are not covered either way. Landlock can also restrict network connections (UNVERIFIED in this survey).

D9. How does Python reach the Java checker?

Section titled “D9. How does Python reach the Java checker?”
  • Options.
    • (a) One helper process per job: Java, started in the background when the interpreter starts, and asked about each write over a pipe.
    • (b) java -jar once per write. That is about 0.9 s each, measured by the Beam Python adapter, so too slow for a script that writes many files.
    • (c) The checker compiled ahead of time into a program that needs no Java (GraalVM “native image”), shipped in the Python package.
  • Recommendation. (a) first, (c) if Java on the workers is a real obstacle.
  • Why. (a) reuses the existing checker and pays the Java start-up once, in parallel with the job’s own start.
  • What it costs. Java 11+ on every machine that runs a governed job. That is a much larger ask than Beam’s “where jobs are submitted”, and it is the biggest risk in this survey. If the helper cannot start, every write to a declared output is refused (“the check could not run”).
  • What would change my mind. A survey of the platforms’ worker images. If most lack Java, start with (c).

D10. How results are reported

Section titled “D10. How results are reported”
  • Recommendation.
    • The checker publishes the same validation events as every adapter, through the same notification sinks (the places events are sent: a log, a file, an HTTP endpoint, Kafka). The engine is named python, its version is the interpreter’s (3.11.17), and engineDetails carries the script’s path and the pyarrow and pandas versions.
    • The job’s own command line is not recorded, because it can hold secrets.
    • A refused write raises ContractViolation, a kind of PermissionError (Python’s standard error for “not allowed”), so a job’s existing error handling treats it as a failed write. The process ends with a failing status even if the job catches it.

D11. How CI proves it without secrets

Section titled “D11. How CI proves it without secrets”
  • Recommendation.
    • A conformance adapter that writes each scenario as a small Python script and runs it with the real interpreter, the real package and the real checker. This is the same way the Beam Python adapter runs real Python pipelines in CI.
    • Recorded write descriptions as fast unit-test fixtures for the Scala side.
    • A matrix over Python 3.9 to 3.13, and over pyarrow and pandas releases. Each release re-runs probe 6’s check that every catalogued function is still wrapped and no new write path appeared.
    • Nothing needs a cloud account.

D12. Language, packaging and naming

Section titled “D12. Language, packaging and naming”
  • Recommendation.
    • A new sbt module, python-adapter: the Scala checker, its declaration and its conformance tests.
    • A Python package (invaract-python, PREDICTED name) holding:
      • the hook, the wrappers and the staging;
      • the .pth file that starts them;
      • the launcher (section 5);
      • the client for the helper process.
    • The pyarrow type mapping moves out of beam-adapter so both Python adapters use it.
  • What it costs. More Python code than the Beam Python package, which was ~150 lines with no decisions in it. Here the hook, the catalogue and the staging are decisions. They need their own tests, lint and mutation testing (mutmut), because the repository’s Scala gates do not reach them.

D13. Classifying each output: a data asset or a readiness signal

Section titled “D13. Classifying each output: a data asset or a readiness signal”

The requirement: the contract confirms that the job wrote to each place it declared, and the team declares what it wrote or did there. Two kinds matter most:

  • a data asset: the governed table or files other teams consume;
  • a readiness signal: a marker such as _SUCCESS or READY, or a small status file, that tells downstream jobs the asset is complete.

What exists today.

  • The first half is there: check.location refuses a write to an undeclared place (OUTPUT_LOCATION_MISMATCH), and check.outputsWritten reports a declared output never written (MISSING_OUTPUT).
  • The second half is declared but never checked. Every output may carry type: DATA_ASSET or type: CONTROL, and CONTROL’s definition includes “a readiness/reconciliation signal” (contract/.../ContractModel.scala, DatasetType). But the role check covers inputs only. In docs/CONTRACT_MODEL.md’s words, “a declared output’s type carries no role-consistency check of its own”.
  • CONTROL also covers processing calendars and watermarks, so a readiness signal cannot be told apart from other control data, and nothing records which asset a signal announces.

Options.

  • (a) Keep type: CONTROL and add an output-only field naming the assets the signal announces, for example readinessFor: [report].
  • (b) Add READINESS as a fourth type.
  • (c) Leave the contract as it is and check only that a DATA_ASSET output receives tabular data.

Recommendation. (a), with three checks, each a blocking violation:

  1. A data asset must receive data. The write to a DATA_ASSET output must be a write with columns, such as a Parquet table. A touch, an empty file or a raw text write there is refused: “declared a data asset, but the job wrote a marker”.
  2. A readiness signal must not receive the data. A table written to a readiness output is refused. A marker, an empty file or a small status file passes. A status file may declare a schema like any output, and is then checked against it.
  3. A readiness signal comes after its asset. The signal is refused unless every asset it names was written earlier in the same job and passed its check. A refused or never-written asset therefore never gets a “ready” marker. This is the check that protects downstream consumers most.

Why (a). type is a closed set, and contract parsers hard-fail on a value they do not know. A fourth type would make every new contract unreadable by older Invaract releases. A new optional field is ignored by them. (c) leaves out the ordering check, which is the valuable one.

What plain Python can see (probes 2, 3 and 9):

  • The kind of each write is exact. A catalogued table writer (pyarrow, pandas, the csv module) means data. A touch, an open closed with nothing written, or a raw write of a few bytes means a marker or status. With staging (D3), the adapter also sees the final size and which writer produced the file.
  • Order is exact, because a script runs one line at a time and the adapter checks every write in the same process. When the marker is written, it already knows whether the report was written and passed.
  • The trap probe 9 found. Re-touching a marker that already exists raises only an os.utime event, with no open. The adapter must treat os.utime on a readiness location as a write of that signal. Otherwise a stale marker could be re-signalled unseen.
  • A data asset written through compiled code the catalogue does not wrap is never seen as written, so its readiness signal is refused. That fails closed, as it should.

Forecast for this adapter: supported, High confidence for the facts, Medium for the whole, since no adapter exists. Other engines differ, which is why this needs a capability every adapter declares:

  • Spark checks writes one at a time in order, so the ordering check fits it (Medium).
  • A Beam pipeline’s steps run in parallel unless the job orders them, so a marker step could start before the asset’s write finishes. Beam would likely declare the ordering check partial or unsupported (Low, UNVERIFIED).

What it costs. It is an engine-neutral change, made in its own pull request before the Python adapter:

  • the contract field and its validation;
  • the checks in verification-core, and two new violation types (for example OUTPUT_ROLE_MISMATCH and READINESS_BEFORE_ASSET);
  • a new Capability, so that every adapter takes a position;
  • new conformance scenarios: an asset written as a marker, a readiness signal written as a table, a signal before its asset, and a signal after its asset;
  • the user documentation.

Open questions for you.

  • May a readiness signal be only an empty marker, or also a small status file, or a row in a control table?
  • Is a signal written by a different process than the asset (an orchestrator’s next task, say) in scope? One process cannot see another’s checks, so that would need Invaract to keep a durable record of checked writes. Until it exists, such a signal would have to be refused or left unchecked.
  • Are there other things a team should declare it “did” at an output, such as deleting it, or publishing by moving a staged folder into place?

5. Switching it on without touching the job: external attachability

Section titled “5. Switching it on without touching the job: external attachability”

Verdict: Partly.

The mechanism. When Python starts, it reads every .pth file in its library folder (site-packages) and runs any line that begins with import (site.py, lines 200 to 201). Installing the package drops one such file. The import does nothing unless an Invaract setting is present in the environment. When one is, it adds the hook, the wrappers and, on Linux if asked, the restriction. Then the job starts as usual. Probe 5 ran the unmodified job of section 2 this way:

With no Invaract setting, the job ran exactly as before (exit status 0). With the setting and a wrong output, the write was refused and the process ended with status 3. A child Python process started by the job was checked too, because it inherits the environment and the same .pth file (probe 5).

Settings are environment variables rather than command-line flags because a script owns its own command line: its argument parser would reject flags it does not know.

The opt-in operating-system restriction (D8) is the one new switch. It belongs to this adapter rather than being a neutral setting, because only an in-process adapter on Linux has it.

How a job can get around it, and what is not possible.

  • python -S skips the .pth files, so nothing is installed. A job needing only the standard library then runs unchecked. (In probe 5, -S also hid pyarrow from that job, so it failed for its own reason.) python -I does not get around it (probe 5).
  • A job run in a Python environment the platform did not prepare (its own virtual environment, a private copy of Python’s library folder) has no package, and runs unchecked without a word. The launcher closes this.
  • A job that deliberately restores the original functions, or writes through ctypes or its own compiled code, escapes the wrappers. The hook stays: no function removes one. The operating-system restriction, where on, stays as well. Invaract’s checks are meant to catch mistakes, not a job written to evade them.
  • A machine without Java cannot check anything. Writes to declared outputs are then refused.

  1. Settle the unverified items (small). These are: Java on the platforms’ Python worker images; Landlock on their hosts; audit events on Python 3.9 to 3.13; database drivers and HTTP clients. This settles D8 and D9.

Glossary

Section titled “Glossary”
  • Interpreter (CPython): the program that runs a Python script, line by line.
  • Engine: the system that runs a data job (Spark, Beam). Plain Python has none; the interpreter plays its part.
  • Data contract / schema: the YAML file a job is checked against / the column names and types of a dataset.
  • Query plan, pipeline graph, DAG: an engine’s description of a job made before it runs. Plain Python has none of these.
  • IR: Invaract’s engine-neutral description of a job’s reads, filters, joins, groupings and writes.
  • Opaque step: a step Invaract knows is there but cannot see into (here, the team’s Python code).
  • Capability / declaration / status: one thing an adapter can or cannot do / its full list / supported, partial, unsupported or not-applicable.
  • Adapter: the part of Invaract that knows one engine and translates its jobs into the IR.
  • Conformance suite / scenario: the small engine-neutral jobs every adapter runs; an adapter conforms when each comes out as its declaration says.
  • AST (syntax tree): a script’s code parsed into a tree of statements, available before it runs.
  • Audit event / hook: an action Python announces (opening a file, starting a program) / a function called with each one, which can stop it.
  • Wrapper / catalogue: a function put in place of a library’s own to check its arguments first / the list of functions wrapped.
  • Compiled code: code turned into machine instructions (pyarrow’s C++), which Python’s hooks cannot see into.
  • Data asset / readiness signal: an output that is the governed data product itself (type: DATA_ASSET) / a marker or small status file telling downstream jobs an asset is complete (today type: CONTROL; D13).
  • Staging: writing to a temporary file and moving it into place only once checked.
  • Landlock: a Linux feature that lets a process give up file and network rights for good.
  • .pth file: a small file in Python’s library folder that Python reads, and may run a line of, at start-up.
  • Enforcement point: where the check runs; here in-engine-blocking, inside the interpreter before each write.
  • Fail closed: refuse what cannot be checked, rather than let it through.
  • Attach: switch Invaract on for a job, ideally without changing its code.
  • Lineage: which input columns each output column comes from.
  • Sink / source: where a write lands / where a read comes from. A notification sink is where Invaract’s events go.
  • Runner / transform (Beam words, for comparison): the engine a Beam pipeline runs on / one step of a pipeline.
  • OUTPUT_LOCATION_MISMATCH: a write lands somewhere other than the contract’s output.
  • MISSING_OUTPUT_FIELD / OUTPUT_FIELD_TYPE_MISMATCH / OUTPUT_FIELD_NULLABILITY_MISMATCH: a declared output column is missing, has the wrong type, or may be empty where the contract says it may not.
  • UNDECLARED_OUTPUT_COLUMN: with rejectUndeclaredFields, the output has a column the contract does not declare.
  • MISSING_INPUT / UNDECLARED_INPUT: a declared input is not read / an undeclared one is.
  • MISSING_OUTPUT: a declared output is never written.
  • OUTPUT_FORMAT_MISMATCH / OUTPUT_SAVE_MODE_MISMATCH: the write’s format or save mode differs from the contract’s.
  • UNVERIFIABLE_WRITE: an action changes data in a way Invaract cannot check, so it is refused.
  • UNSUPPORTED_CONTRACT_FEATURE: the contract relies on something this adapter declares it cannot check, so it is refused.
  • INVALID_CONTRACT: the contract itself is malformed.
